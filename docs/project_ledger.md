## 2. Architectural Decisions

| Component | Choice | Why |
|---|---|---|
| Backend | Go 1.22 | Single-binary, <15MB RAM/client, <10ms startup — cheap to host at density |
| Database | PostgreSQL 16.3 | Schema-per-tenant isolation + `SELECT ... FOR UPDATE` for ledgers/sequences |
| Multi-tenancy | Schema-per-tenant | Isolates tenant data, resolved dynamically per request |
| Branding | Custom ERP | Removed legacy sample branding for a clean, reusable system |

## 116. Stage 36.5 + 36.3 — declarative transform rules, and PIM import depth (2026-08-28, code + schema)

Opens Stage 36's remaining five top-level items (36.3-36.7 — import, export/syndication, transform rules, DAM depth, enrichment) with the two built in dependency order: 36.5 first (a shared value-transform seam), then 36.3 (import depth), which consumes it. Full item-by-item detail, including the scope calls made explicit before building, is in `micro_checklist.md` Stage 36.

- **36.5 — the gap was that a channel field mapping could only rename a value, never transform it.** `ChannelFieldMap` (Stage 16.1) maps a source field to a target field and passes the value through unchanged; there was no way to say "uppercase this" or "prefix the SKU" without writing Go. New `PIMTransformRule` (Master) holds an ordered list of steps drawn from a **closed vocabulary** (`trim`, `uppercase`, `lowercase`, `prefix`, `suffix`, `truncate`, `default_if_empty`, `find_replace_literal` — literal, not regex, `number_format`, `date_format`), the same shape and reasoning Stage 36.2.3's workflow conditions already established: a rule is authored in a form, and a form that accepts an expression is a remote-execution surface. `ApplyPIMTransformRule` is the one seam; `ChannelFieldMap` gained one additive `transform_rule` field so `BuildChannelPayload` (`engines/connector.go`) applies it when set, blank meaning today's exact passthrough. Verified live: `SKU-GOLD RING` came out of a trim→uppercase→prefix rule applied to an item named "Gold Ring" through a real channel-publish preview, and deactivating the rule mid-flight correctly failed the payload build loudly rather than silently falling back.
- **36.3 — six sub-items, all closing a gap in the pre-existing `BulkImportCSV`.** That engine already had dry-run preview, batching and create/update classification; what it lacked was a way to point it at a source whose column headers don't match this doctype's own field names, a way to trigger it on a schedule or from an external system, and any awareness that an Item can be a variant with a parent. `PIMImportTemplate` (column mapping + per-column transform rule + default value) and `PIMImportSchedule` (Drop Directory or API Hook) are two new doctypes; `RunPIMImportTemplate` remaps a source file through a template and hands it to the **same shared batching core** a plain CSV upload uses — a small refactor of `engines/import.go` (`csvRowsToDocData`/`runDocDataImport` split out of `BulkImportCSV`/`importBatch`) means the two paths cannot drift apart. Variant-parent-awareness (`pimVariantParentPreflight`) is wired into that shared core directly, so it applies to *every* Item import, not just a templated one. A native SFTP client was explicitly scoped out (would need a new dependency or hand-rolled wire-protocol work); a directory the worker scans doubles as an SFTP source once ops mounts it as a filesystem path. The API hook (`POST /api/v1/pim/import/hook`) authenticates with a header-carried per-schedule secret (SHA-256 digest-only storage, Stage 38.2a's shape) rather than a token-in-the-URL, because `middleware.go`'s `publicRoutes` is a deliberately small allowlist of exact path strings, not a prefix rule.
- **A real pre-existing bug found while adding this stage's own tests, unrelated to either feature**: `db.InitDB` never closed the previous connection pool before opening a new one. Harmless in production (called once), but the test suite calls it at the top of nearly every DB-touching test function in a package, and enough test files now exist that the accumulated leaked idle connections could exhaust Postgres's connection limit partway through `go test ./engines/...` — reproduced deterministically, fixed with one `if DB != nil { DB.Close() }`, benefits every existing and future test in the suite.

**Scope touched**: two new migrations (`db/migrations_stage36_5_transform_rules.sql`, `db/migrations_stage36_3_import_depth.sql`; 3 doctypes total, one additive field on `ChannelFieldMap`), five new engine files (`pim_transform.go`, `pim_import_template.go`, `pim_import_schedule.go` + their two test files), two new handler files, 8 new routes, one new worker (`StartPIMImportScheduleWorker`), one small refactor of the pre-existing `import.go` and `connector.go`, one one-line fix in `db/db.go`. No frontend surface yet — both sub-stages are API-only so far, the same pattern Stage 37.1.5 left its own two new routes in.

**Verified**: `go build ./...`, `go vet ./...`, `node --check public/app.js` clean; new `engines/pim_transform_test.go` and `engines/pim_import_test.go` (pure-function table tests for all 10 transform functions, template/schedule validator refusal/acceptance cases, the variant-preflight table, and a full drop-directory worker run exercised directly at the Go level since the real worker only fires hourly) all passing, and `go test ./... -p 1` **fully green** after the `db.InitDB` fix (the pre-existing `TestWMSP2/SlottingSuggestions` shared-DB flake reproduced once and cleared on retry, as previously documented — unrelated to this work). Both migrations applied directly to the dev database (ledger rows inserted matching `erp-server -migrate`'s own format) rather than via the global `-migrate` flag, to avoid also applying an unrelated already-pending migration from Stage 42.6's concurrent session — the same concurrent-session-safe apply approach §115 used. **Live over HTTP** on two throwaway servers (ports 9153 and 9163, both stopped and released, every fixture deleted afterwards): the transform-rule round-trip above, plus template create/list/mapping-preview, an unknown-field template refused by name, dry-run vs. real templated import, a transform-rule-wired column actually changing the stored value, a variant row with a missing parent refused by name, and the API hook running a real import with **zero authentication** (no bearer token, no session) — wrong token 404s, correct token imports, rotating invalidates the old one immediately. ## 114. Stage 35.7 — commercial bundles and physically stocked kits (2026-08-22, code + schema + UI)

All four Stage 35.7 items are complete. `ProductBundle` is intentionally not another manufacturing BOM: it describes a sellable commercial composition, with Virtual/Stocked fulfillment and Parent/Fixed/Component pricing. Validation pins every SKU to an active Item, forbids duplicate/self/nested components and keeps one active definition per bundle SKU.

Virtual availability has no balance to drift. The new sellable-SKU seam derives each component through the existing seven-term `computeATS`, divides by required component quantity and takes the limiting result. Network availability sums only bundles complete at one facility, rather than combining stranded parts across locations. That seam now feeds both `/availability` and channel ATS push. At order creation a Virtual line becomes attributed component SalesOrderLines before sourcing/reservation; the parent/fixed revenue is allocated exactly, while the SalesOrder retains the commercial bundle summary. A Stocked kit remains one normal stock/pick line.

Assembly and disassembly use one transaction for `BundleAssembly`, every component/kit availability mutation and every append-only `StockLedgerEntry`. Consumption checks ATS, not raw available stock, so reserved or held components cannot be stolen by the kit floor. A shortage leaves no partial movement or operation row; a unique request key makes transport retries safe. The OMS panel displays definitions and location ATS and drives stocked-kit operations through a WMS-gated route.

**Schema/concurrency**: additive `db/migrations_stage35_7_bundles_kits.sql` was applied surgically and ledger-recorded on dev, propagating both doctypes/fields/permissions/indexes to `tenant_default` and `tenant_new_schema`. ## 102. Stage 37.1.3-37.1.5 — multi-currency finished, and the 98.8% receivable understatement it uncovered (2026-08-16, code + schema + docs)

Asked to start building from the open parity backlog, whose first row is **Stage 37 — ERP core depth**, annotated "incl. finishing multi-currency (37.1.3-37.1.5)". That was the right place to start for a reason beyond ordering: 37.1 was the only half-built item in the list, and half-built multi-currency is not a missing feature, it is a live correctness liability. Full item-by-item detail in `micro_checklist.md` Stage 37.1. A concurrent session's Stage 42.1 work was uncommitted in this tree throughout — see the note at the end.

**The bug the stage existed to find.** 37.1.2 taught documents and postings to *carry* a currency and a rate, and stopped there. It never touched the settlement engines, so `PostSalesInvoice` read `total_amount` — which on a USD invoice is 1000, in *dollars* — and posted it straight into Accounts Receivable. **A USD 1,000 invoice at 83.00 booked a 1,000-rupee receivable instead of an 83,000 one.** The receivable, the ageing report, the credit exposure and the trial balance were each understated by 98.8%, silently, for any tenant that used the feature 37.1.2 shipped. Nothing failed; the numbers were simply wrong. The posting sites now read the `base_*` twin that stage already stamps, and `PayVendorInvoice` had the same defect on the payable side.

**The model, recorded once so it is not re-derived or "simplified" later.** A receivable is booked at the invoice-date rate and carried at that rupee value. The cash eventually received is worth a different number of rupees, and that difference is **realised** — it is cash, it has happened, it cannot reverse (4200 gain / 5600 loss). While the invoice sits open across a period end its carrying value is stale, so revaluing it to the closing rate recognises the movement so far as **unrealised** (4210 / 5610), tracked cumulatively on the document itself. **At settlement the realised figure is measured against the revalued carrying amount, not the original.** Total P&L across every period is then exactly (cash received − amount booked), however it splits between them; measuring against the original would double-count every rupee already recognised at a period end. Four accounts rather than two because realised and unrealised must never merge — one is cash, the other is an opinion that can reverse next month, and every auditor treats them differently. There is deliberately no reversing entry on day one of the next period: this codebase has no automatic reversal machinery, and a cumulative carrying amount reaches the same answer with one fewer moving part.

**The sign flips by side, and that is the thing most likely to be broken by a later edit.** When the foreign currency strengthens a receivable is worth *more* (gain) and a payable costs *more* to settle (loss). `resolveSettlementFX` is told which side it is on rather than inferring it from the amounts, and the tests assert both directions against the same numbers so a sign error cannot pass.

**Reuse rather than new mechanism, throughout.** `SettlementOptions` is variadic (the `PostingOptions` precedent), so all six existing callers of the four settlement engines needed zero changes. The revaluation posts through the existing `PostDoubleEntry` and therefore inherits the closed-period check and the idempotency key for free. All three of 37.1.5's reports are `ReportDefinition`s, so they arrive with the catalog's screen, parameter form, CSV/PDF export, scheduling and column redaction already attached — no frontend code at all. The migration adds four GL accounts and **no table and no column**: the revaluation state lives as engine-written JSON keys on the document, so a document never revalued is byte-identical to what it is today.

**`GET` previews the revaluation and `POST` commits it** — the split is the HTTP verb, not a `dry_run` flag on one endpoint. A GET cannot change the ledger however it is called, which is what makes it safe behind a button a controller will press repeatedly while checking the numbers, and safe against a retry, a prefetch or a double-click booking a second adjustment.

**Three bugs live verification caught that the tests could not have**, all on paths a unit test never travels:

- **An `ExchangeRate` with no end date was unsaveable** — an open-ended rate, which is how essentially every rate table is really maintained. `fmt.Sprintf("%v", nil)` is the four-character string `"<nil>"`, not `""`, so an omitted optional field arrived at validation as a *non-empty* value that then failed its format check, and the message blamed a field the user had never filled in.
- **A `Currency` whose document id was not its ISO code broke every invoice that selected it.** The `currency` field is a `Link`, so the generic check resolves against `documents.id`, while `ApplyDocumentCurrency` requires a three-letter ISO code — the only value satisfying both is one where id == code. The seeded INR row happens to be keyed that way, which is why nothing had noticed. It now refuses at authoring time, naming the id to use, rather than surfacing later on a different document as "Linked Currency record with ID \"USD\" does not exist" about a record sitting right there.
- **This stage's own first cut invented a foreign-currency amount.** `PostDoubleEntry` derives a missing per-account transaction amount as `functional / rate` — correct for a plain foreign posting, but on an FX line it fabricates a number: a 1,000-rupee revaluation at 84.00 recorded itself as USD 11.90, so summing `transaction_debit` reported an exposure of USD 1,011.90 against a real one of USD 1,000. An FX gain/loss line has no foreign value *by construction*, and a revaluation moves no foreign currency at all; both now post explicit zeros.

**The distinction the whole stage rests on: an approval is not a task.** This codebase already has a maker-checker approval engine, and it was tempting to model tasks on it. **Four decisions worth carrying forward.**

- **The task's state machine is the document `status` column, not a second field.** `handlers_core_doc_engine.go` already copies `data.status` into `documents.status`, so putting the vocabulary there means the generic list view, RBAC, soft delete, the audit trail, CSV export and every report understand a task's state without being taught. A parallel `task_status` field would have been one more thing only this module knew how to read.
- **Done is terminal, and that is a safety property rather than strictness.** A completed task may already have satisfied its workflow stage's exit condition and advanced the run past it, and there is no honest way to un-advance a run whose later stages have themselves created work. So the refusal names the alternative — a follow-up task, one button in the inbox — and the history stays truthful about what was actually finished.
- **The condition vocabulary is closed, and published from the same map the engine evaluates.** Stage conditions are seven named checks, each taking at most one operand, each implemented in Go. A workflow definition is authored by a category manager in a form, and a form that accepts an expression language is a remote-execution surface that also guarantees nobody can later tell what the definition does. `ListPIMWorkflowConditions` is generated from `pimWorkflowConditions` itself, so the form cannot offer a condition that never evaluates — and a test asserts the two cannot drift.
- **`AdvancePIMWorkflowRun` is idempotent, which is what makes three callers safe.** Run creation, every task completion, and an operator pressing Advance all call it, and none needs to know whether the others already did: on a run that cannot move it changes nothing but the recorded reason. Entry conditions are evaluated *before* leaving the current group, so a run held up by the next stage stays where it is with an explanation instead of being stranded between two stages. Advancing on task completion rather than from a sweeper is deliberate — a workflow whose progress waits on a cron feels broken to the person waiting on it.

**Reuse rather than new mechanism, throughout.** Product groups resolve through the *same* `ResolvePIMProductGroupItemCodes` seam 36.1.3's bulk edit and export use. Validation attaches at `ValidateDocument`'s shared exit, so a task written through the generic document API gets the same state machine the engine enforces. The three reports go through `RegisterReport`, arriving with the catalog's screen, parameter form, CSV export, scheduling and column redaction already attached. Bulk actions loop the single-item engines (the `BulkDecideApproval` precedent) so every per-item guard survives and a mixed selection reports exactly which rows refused. The inbox is a fourth tab in the existing PIM shell, so it needed no menu-map, view-router or menu-handler changes at all; templates and workflow definitions get their authoring surface from the generic doctype table.

**One endpoint was added because the feature is unusable without it.** `GET /api/v1/pim/assignable-users` exists because `/api/v1/admin/users` is Super Admin gated: a Store Manager who may create and reassign tasks could not otherwise see who to hand work to, and the assignee field degrades into a free-text box you spell from memory, where every typo is a task in nobody's inbox. It returns active users' username and role and nothing else, gated on the same *update* right that already lets you put a name on a task.

**Verified**: build/vet/`node --check` clean; the migration **applied** to the dev database and `-migrate-status` confirmed clean afterwards; seven new engine tests plus `go test ./... -p 1` fully green; every endpoint exercised over HTTP on a throwaway server (port 9107, stopped and released, all fixtures deleted); and a **real-browser pass** covering the inbox, the bulk bar, the detail modal, the run panel's state-dependent actions, and the Assign-task button on a real report row creating a real task — zero console errors, no horizontal overflow.

**Known limitation, stated rather than hidden**: editing a workflow definition while runs are mid-flight can orphan a run whose stored stage group no longer exists. Such a run is stopped with a named reason rather than silently restarted (restarting would re-create every task the product has already been through). Versioning definitions so in-flight runs keep travelling the shape they started on is the proper fix, and is not in 36.2's scope.

## 98. Stage 44 — per-tenant hostnames, and the domain that unblocked go-live (2026-08-14, code + schema + proxy config + docs)

User registered **wholeops.in** and asked to close the domain-gated items. Two things came out of it: the go-live path was unblocked, and the URL scheme they described turned out not to exist.

**The scheme was checked before it was built.** The ask was `clientbrandname.wholeops.in/oms`. Reading the code first showed neither half was real: `apiMiddleware` never looked at the `Host` header (tenant came from `X-Tenant-ID`, then `?tenant_id=`, then the bearer token's claim — one hostname served every tenant), and the SPA is hash-routed, so the module segment is `#oms`. Saying so before building was the point; the alternative was shipping something adjacent and calling it done. The host→tenant half was then built; the path-routing half is left open as a decision (44.6), because the hostname half already delivers the per-client branding and the hash form costs nothing.

**The design's load-bearing choice is that the token stays authoritative.** Host resolution sits *ahead* of `X-Tenant-ID` in the pre-auth chain — a hostname had to survive DNS and a certificate to arrive, those headers are whatever the caller typed — but it never overrides a token claim. A session for tenant A presented on tenant B's hostname is refused with the same generic 401 as any dead session. "Host wins" would have been a genuine cross-tenant escalation; this is the narrower guarantee that the claim still scopes every query and the hostname merely has to agree.

- **`public.tenants.host_slug`**, additive, backfilled from `tenant_id` **only where `tenant_id` is already a legal DNS label**. That guard earned itself immediately: on the dev DB `default` backfilled and `tenant_new` correctly did not, because `_` is illegal in a hostname. A blind backfill would have minted a slug that could never be served, surfacing much later as an unexplained certificate failure.
- **On-demand TLS without a custom Caddy binary.** Per-tenant certificates are issued on first handshake rather than listed in config, gated by a new `/internal/tls-ask` endpoint the app answers — Caddy proceeds only on a 2xx, so a hostname that is not a live tenant never reaches Let's Encrypt. The wildcard-certificate alternative needs a DNS-01 provider plugin and therefore `xcaddy` and a custom binary to keep patched, which is the exact trade 26.1.3a already rejected. **Validation caught a real trap**: current Caddy has *removed* `on_demand_tls`'s `interval`/`burst` throttle, so `ask` is the only gate left — which is why the handler fails closed on every path, including unset config and a DB-less startup.
- **CORS widened by shape, not by list.** https origins at the base domain or one label under it are accepted, so provisioning a tenant no longer needs a restart with a longer `CORS_ALLOWED_ORIGINS`. The suffix test is anchored on `"." + base`, so a domain someone else registers ending in the same letters (`acme.evilwholeops.in`) is not mistaken for ours — locked by a test rather than left to reading.
- **Inert unless configured.** The whole feature is off without `TENANT_BASE_DOMAIN`: host resolution returns no match, CORS falls back to the old exact-match allowlist, and the ask gate refuses everything. That is what keeps the localhost and SSH-tunnel paths unchanged, and it is tested rather than assumed.

**Verified**: `go build ./...`, `go vet` clean; 40 new subtests green; full `internal/server` and `db` packages green; migration applied to the dev DB and its backfill inspected; `caddy validate` returns `Valid configuration` for the rendered config on the droplet. **Not yet verified**: anything end-to-end over real TLS. `wholeops.in` was delegated to Cloudflare the same day and the `.in` registry had not published the new nameservers before this was written, so 44.7 stays open and this section does not claim a live pass it has not had.

**On the go-live side, DNS is finished and TLS is not.** DNS was set up Cloudflare-first (zone added, `app` and `*` A records at `139.59.17.16`, both grey-cloud) deliberately: because the `.in` registry had not yet published *any* nameservers, switching to Cloudflare then cost one delegation instead of two. That completed, and both names now resolve correctly from public resolvers.

`enable_tls.sh` was then run for the first time since it was written in Stage 26.1.1 — and **first execution found two bugs that would have hit whoever ran it first, not just this session.** An apostrophe inside `${PUBLIC_IP:-this box's public IP}` opened a quote bash never closed, killing the script at parse time with an `unexpected EOF` that pointed at the last line rather than the culprit. Then, with that fixed, the reload failed `permission denied` on the access log: the script chowned `/var/log/caddy` *before* running `caddy validate`, and validate does not merely parse — it provisions every module, including opening the log, as root. Chowning first cannot help a file that does not exist yet. Both fixed; the ordering now has a comment explaining why it is load-bearing. **The generalisable finding: `caddy validate` has side effects on disk and is not a dry run.** The script's own auto-rollback worked correctly through both failures, which is why neither cost anything.

**What blocked TLS was a DigitalOcean cloud firewall, and the diagnosis is the part worth carrying forward.** ACME failed on both challenge types with `Timeout during connect (likely firewall problem)` — yet `ss -tlnp` showed Caddy listening on `*:80` and `*:443` and `ufw` allowed both, so every signal available *on the box* said the box was fine. **`tcpdump` during an external connection attempt settled it: zero inbound packets arrived at all.** That is the decisive observation, because tcpdump sits below netfilter for inbound traffic — a local iptables DROP would still have shown the SYNs. Their total absence meant they were being discarded upstream. The DO console then confirmed it exactly: a firewall named `Test` with a single inbound rule for SSH/22, which was all the droplet had ever needed while the ERP was tunnel-only. **The reusable rule: when a port is open locally but dead externally, reach for tcpdump rather than re-reading the local firewall.** Caddy was reverted to `Caddyfile.holding` while this was outstanding, so it would stop retrying into Let's Encrypt's failed-validation quota (2 of 5/hour used).

**With 80/443 opened, `enable_tls.sh` succeeded and production went live on HTTPS — closing 26.1.1's last leftover.** `https://app.wholeops.in` now serves the ERP behind a valid Let's Encrypt certificate (expires 2026-11-12, renewed automatically by Caddy), with `CORS_ALLOWED_ORIGINS` set and the app restarted. **Verified from the dev machine rather than from the droplet**, which is the distinction that matters here — checking `127.0.0.1` would have proved nothing about the very layer that had been broken: health and version 200, SPA and its assets 200 with correct MIME types, `http://` 308 to https, a real `USERAC-0021` 401 envelope from `POST /api/v1/login` (so TLS → Caddy → Go → error catalog all work end to end), `/api/v1/debug/panic` 404 confirming `ENV=production` still holds, all six security headers present and `Server`/`X-Powered-By` stripped. The SSH tunnel was left working.

**Stage 44 itself was deliberately not deployed in the same motion.** The bring-up used the pre-Stage-44 single-host Caddyfile already on the box, because installing the `on_demand_tls` config against a binary with no `/internal/tls-ask` route would have meant an ask gate that refuses every hostname. 26.1.3b (Cloudflare orange-cloud + `TRUSTED_PROXY_CIDRS` + origin lockdown) remains `[ ]`, and is now pure activation.

## 87. Stage 26.6.11 — tax-exempt / nil-rated / zero-rated goods (2026-08-09, code + schema + docs)

## 85. Stage 34.1-34.3 built, the first production DR drill, and nightly backups finally switched on (2026-08-07, code + schema + ops + docs)

The user asked to clear everything actionable. That was two things: Stage 34's buildable half (34.1-34.3), and 26.11.3's restore drill. Both landed; both turned up something the checklist did not know. The drill's finding — that production had no nightly backup — was then signed off and fixed the same day (26.11.7). Item detail in `micro_checklist.md` (34.1-34.3, 26.11.3, 26.11.7).

- **34.2's premise was wrong, and the honest implementation was the interesting decision.** The item said "join `CompetitorPrice` to our `Item`/price list". **There is no price list.** `Item` has no price field of any kind, and the POS cashier types the sale price by hand into an editable input that starts at 0. So "our price" is resolved at report time as the last price we *actually transacted at*, newest wins across `SalesOrderLine.unit_price` and `POSCart items[].sale_price`. The alternative — inventing a price master — is a real feature with real product decisions behind it (per channel? per customer group? effective dates?) and had no business being slipped in under a competitor-pricing item. The cost is stated rather than hidden: a SKU never sold reports `Position = "No price on file"` with null gap columns, not a fabricated zero that would rank top of the gap list.
- **Registering `CompetitorPrice` as a Master doctype rather than a Transaction was what made it cost zero frontend code.** The Setup flyout and the generic doctype table both filter on `document_type = 'Master'`, so Master is what inherits the list, the New form and the Bulk Import button. A Transaction doctype would have been unreachable from the UI entirely — the exact trap `CycleCountLine` hit and had to be worked around with bespoke JavaScript. The rows are timestamped observations, so "Master" is a mild semantic stretch; the UI consequence decided it.
- **Following the documented import path literally exposed a bug in 89 doctypes.** `GenerateCSVTemplate` omits `id`/`status` from the header it emits, and `ValidateDocument` skips the mandatory check for those same two system fields — but `missingMandatoryColumns` did neither, so **any** doctype with a mandatory `status` rejected its own generated template with "missing mandatory column(s): status". Brand, Color, Customer, Vendor, Location, Employee, `CycleCountLine` — 89 in total. The tempting fix was to make `CompetitorPrice.status` optional and move on; the right one was the shared choke point, which repaired all 89 at once. This only surfaced because the verification downloaded the template and uploaded it, instead of hand-writing a CSV that happened to include `status`.
- **The undercut worker's de-duplication is the part that makes it usable rather than noise.** An hourly worker that alerts whenever a competitor is cheaper re-alerts on the same standing undercut every hour forever. State lives in `public.competitor_undercut_state.last_run_at` (the `patch_intake_state` shape), so only observations *recorded since the last cycle* can alert — one observation, at most one alert. The threshold setting defaults to **0 = disabled**, so a tenant that never loads competitor prices is never alerted about them.
- **The DR drill passed, but only after three blockers that each would otherwise have been met mid-incident.** The script **had never been deployed** (`deploy.ps1` ships the binary and `public/`, not `deploy/`). Its own documented `sudo -u erp` invocation **can never work**, because production's `erp` role correctly has no CREATEDB and the script derived its admin connection from `DATABASE_URL` — fixed with an optional `DRILL_ADMIN_URL` override rather than by granting the app role CREATEDB, which would weaken the running system in order to test a backup. And the superuser **cannot read `/opt/erp/backups`** (`drwxr-x--- erp:erp`), so the newest backup had to be staged elsewhere — including rewriting the `.sha256` sidecar's absolute path, because `sha256sum -c` resolves the path recorded *inside* the file and otherwise fails a perfectly good copy with a misleading "corrupted".
- **The drill's most important output was not the drill.** It passed — checksum verified, `pg_restore` clean, all three sampled tables matching live exactly. But the box had **no nightly backup at all**: two manual-looking files taken around deploys, an empty crontab, no systemd timer, `install_backup_cron.sh` never run. A backup that restores is only useful if a recent one exists, and `hypercare_plan.md`'s "two consecutive failed nightly backups" rollback trigger cannot fire when there is no nightly backup to fail. Left for explicit sign-off rather than installed, since a read-only drill is not licence to change production's configuration — **sign-off came the same day, and the cron is now live** (below).
- **The same env-file trap from §85's own deploy notes had a second victim, and it was the backup cron.** The line `deploy/backup.sh` had carried in its header since day one — `0 2 * * * /bin/bash -c 'source /etc/erp/erp.env && backup.sh'` — **can never work**, for exactly the reason `deploy.ps1`/`migrate.sh` hit earlier: `/etc/erp/erp.env` is a systemd `EnvironmentFile` (bare `KEY=value`, no `export`), so `source` sets `DATABASE_URL` as a shell variable and `backup.sh`, a child process, never sees it. Fixed to `set -a; . file; set +a` in `install_backup_cron.sh`, `backup.sh`'s header, `deploy/README.md` (which was still instructing a hand-paste of the broken line, and whose quick-reference `migrate`/`backup` rows had the same defect) and `backup_restore.md`. Worth naming as a class rather than a bug: **`source` is not `export`, and every consumer of this env file that spawns a child has to know that.** The one-line fix is cheap; finding it three times is not.
- **It was found only because the installer runs a real backup instead of trusting the crontab.** That step-5 immediate run is the difference between discovering this now and discovering it during a restore, since the failure mode is a silent non-zero exit at 02:00 into a log nobody reads. A second bug surfaced the same way: run as root from `/root` (0700), step 5 drops to `erp`, which cannot traverse that cwd, so the retention `find` exited non-zero and failed the whole run under `set -e` **even though the dump had succeeded** — a working install that looked broken. Fixed with `cd /`.
- **"The cron line exists" was still not accepted as proof.** `erp`'s shell is `/usr/sbin/nologin` and cron's `PATH` is `/usr/bin:/bin`, both narrower than the `sudo` environment the manual verification inherits — so a manual run proves `backup.sh` works, not that *cron* can run it. A temporary `* * * * *` entry pointed at a scratch `BACKUP_DIR` was left to fire on its own and did (`CRON[131799]: (erp) CMD ...`), producing a valid backup, then removed. The newest backup was finally decrypted with the box's own `BACKUP_ENCRYPTION_KEY` and piped to `pg_restore --list` (valid archive, `dbname: custom_erp`, 286 TOC entries) — the only check that proves the key on the box actually opens what the box writes, which a checksum does not.
- **Still not solved, and stated rather than buried: nothing alerts when a backup fails.** The job appends to `/var/log/erp-backup.log`; hypercare's rollback trigger still depends on a human reading it each morning. An *empty* log is a distinct failure from an *error* in it — one line per successful night means no new line proves the job never ran. That wiring belongs to 20.2's webhook. Off-box copies remain deliberately absent for want of storage credentials, so losing the droplet still loses the backups.
- **Production runs PostgreSQL 14.23; dev runs 16.3.** Found while inspecting the droplet, and it retroactively validated a choice made hours earlier for portability reasons: the price-gap query deliberately avoids PG16-only `pg_input_is_valid` in favour of a `LIKE '[%'` guard. Had it used the tidier function, 34.2 would have built and tested clean on dev and failed on production.

## 82. Clearing the decision-gated backlog: MFA recovery, backups, supplier portal, smoothness (2026-08-05, code + schema + docs)

Review of open item 32.4 concluded it was a real bug already fixed by `0bee663` and already deployed — so the only genuinely unblocked item was closed before this session started. - **32.5 — MFA recovery (the lockout hole).** Single-use recovery codes (10 × 50 bits, SHA-256 hashed, never stored raw — high-entropy codes need no bcrypt and a fast hash makes redemption one indexed lookup instead of a loop), accepted at `/auth/mfa/verify` in place of a TOTP code, burnt by a single conditional `UPDATE` so concurrent logins cannot double-spend one. Plus the two adjacent gaps the item named, without which codes alone still leave a user stranded with a dead authenticator: **re-enrollment** (new secret parks in `users.mfa_pending_secret` so the *existing* device keeps working until the new one is confirmed — an abandoned attempt cannot itself cause the lockout) and **admin reset** (`POST /api/v1/admin/users/reset-mfa`, which clears enrollment and codes and forces re-enrollment at next login rather than disabling MFA). Re-auth on both self-service flows is by password, not TOTP, deliberately: the person who needs those screens is the one whose authenticator is already gone. Display-once UI with copy/download and an acknowledgement gate; a recovery-code login raises a toast naming the remaining count.
- **26.4.10 — Supplier portal, as a limited-role login.** A second portal app would have meant a second auth system, session story, deployment and set of security rules, for what is substantively a form an outside party fills in and an internal reviewer approves. New `SupplierSubmission` doctype mirroring `ProductContent`'s fields; QC via the existing maker-checker engine. **The real work is row-level scoping**, because doctype-level RBAC alone would let every supplier read every other supplier's submissions — enforced at `handleGenericDoc`, the one choke point every read and write already passes through, in all three of list, single-read and write. On create the supplier code is *overwritten* from the session (never picked by the payload); on update the *stored* code is checked, since the payload is attacker-controlled. Approval produces `ProductContent` as **Draft**, never Approved — otherwise an outside party's text could reach a live sales channel with no internal publish decision.
- **26.1.6 — Tenant-scoped export.** Extends the existing backup engine (`deploy/backup.sh --tenant`, `manage.ps1 export-tenant`) rather than adding a second one, so encryption, checksum sidecars and retention cannot drift apart. On-demand only: the nightly whole-DB backup already contains every tenant. Guards the schema name against existing as well as matching a pattern, because `pg_dump --schema` does not fail on a typo — it silently produces an empty dump.
- **32.3 — Backup cron.** The gap was never the backup script; it was that the script documented its cron line *in a header comment* nobody ran, which is how the droplet reached 2026-08-04 with an empty `/opt/erp/backups`. `deploy/install_backup_cron.sh` (idempotent via a marker comment, preflights every failure mode the box actually hit, and **runs one backup immediately** — a cron line existing is not evidence a backup works) plus `deploy/restore_drill.sh`, the Linux counterpart of a drill that previously existed only on the Windows dev machine. 14-day on-box retention per the user's decision. **Not run on production** — the user chose to deploy themselves, so production has no backups until they run it.

## 80. Stage 31.1.9 — One-click print wired into the last three screens (2026-08-05, code)

## 79. Stage 33 — Dialog viewport fit & responsive form layout (2026-08-04, code)

User report with a screenshot of the New Location dialog, its header cut off at the top of the frame and no Save button anywhere: *"Nothing is visible here. So, set up. Make it more 2 column or 3 if required so it will be visible. All screen and config it should auto adjust with 100% to any percent 40% or whatever. If 120% also it should get auto adjusted."* Item-by-item mechanics in micro_checklist.md Stage 33.

- **The multi-column request was the fix the user could see; the actual defect was that no dialog in the app could scroll.** `.modal-container` had no `max-height` and no scroll region at all, and `body` is `overflow: hidden`. A form taller than the viewport was therefore centred by the overlay's flexbox and clipped off **both** ends — the classic flex-centring overflow — so the first fields *and* the footer holding Save/Cancel were unreachable, with nothing on the page able to scroll to them. That is why "nothing is visible": not a column-count problem but an unbounded box. Fixed structurally — the container is a flex column bounded by `calc(100dvh - 40px)`, header and footer are `flex: 0 0 auto`, and `.modal-body` takes the overflow with `flex: 1 1 auto; min-height: 0; overflow-y: auto`. `min-height: 0` is the load-bearing declaration; without it a flex child will not shrink below its content and the container overflows again exactly as before.
- **The `<form>` wrapper broke the flex chain, and only measurement caught it.** With the container fixed, the harness still failed every case at or below 1280x720. In `index.html` most dialogs wrap body+footer in a `<form>`, so the **form** is the container's flex child rather than `.modal-body` — it stayed a content-sized block, the body never received leftover height to scroll in, and the footer was clipped as before. Written as `.modal-container > form` so the handful of JS-built modals that put `.modal-body` directly in the container are untouched. Worth recording because the container fix *looks* complete when read, and reading is what would have shipped it.
- **The generic document form is now an intrinsic grid rather than a breakpoint list.** `openDynamicModal()` serves every master and document create/edit screen and has an unbounded field count — Item renders ~20. `#dynamic-modal-body` became `grid-template-columns: repeat(auto-fit, minmax(min(240px, 100%), 1fr))`: no media queries anywhere, which is precisely what answers "40%, 100%, 120%, whatever" in one rule — browser zoom only changes the CSS-pixel viewport, and both the grid and the `dvh` bound are recomputed from it, so there is no zoom level with special handling and none to forget. The `min(240px, 100%)` inner bound is what stops a single column from overflowing a heavily-zoomed narrow viewport.
- **Kept surgical in both directions.** The grid is scoped to `#dynamic-modal-body`, so the table and summary modals that share `.modal-body` keep their existing single-column block layout; and the wide container is opt-in above 4 fields, so a 3-field master still renders in today's 520px dialog (where the 240px grid minimum yields one column on its own) instead of two-thirds of an empty row. JS learned exactly one new fact — the field count — plus a `.form-group-wide` marker so the JSONTable/JSONMap line editors from 30.5.3 span the full row rather than being squeezed into a 240px track. Column count itself stays entirely in the stylesheet.
- **The same bug lived in the second dialog system and was fixed with it.** `.custom-dialog-box` (`showCustomAlert`/`showCustomConfirm`/`showApiError`/`showCustomPrompt`) had the identical structure and the identical unbounded height, so a long `showApiError` detail list clipped its own OK button off-screen. Verified with a 40-row error list.

Against `HEAD` the 120%/140%/200%/300%/short cases all put Save *below* the viewport bottom — `save=[720,757]` in a 720px-tall window — with `scrolls=false`, which is the user's screenshot reproduced as a number. A second harness serves the **real `index.html`+`app.js`** over HTTP and confirms the new rules leaked into nothing: `add-field`, `edit-prefix`, `add-label` and `bulk-import` still measure `cols=1 display=flex w=520`. (Geometry was asserted via `getBoundingClientRect`, not eyeballed from screenshots — with no backend the login screen sits at `z-index: 500` over the dialogs, so the screenshots of the real page show the login card while the measurements underneath remain valid.)

## 78. Stage 32.1 — Interaction responsiveness: the sidebar hover defect (2026-08-04, code)

User report after using the deployed app: *"The interface is not at all smooth. I have to click many times. Then it is working. Hover is also not working. I have to click on arrow then it is showing permanently else it is going away."* Item-by-item mechanics in micro_checklist.md Stage 32.1.

- **One line explains the entire hover complaint.** The sidebar's flyout logic had accumulated a careful-looking delay ladder — a switch dwell, a longer "aim grace" for the diagonal reach, a hide grace, a hover bridge across the 8px gap — and the test that chose between the two dwells was `flyoutPointerTrail.dx > 0 && r.left >= flyoutPointerTrail.x`. The panel always sits to the right of the sidebar, so the second half is true for essentially **every** pointer position in the nav, and the decision collapsed to "is the pointer moving right at all" — sampled frame-to-frame, which at 120Hz is a sub-pixel delta made mostly of hand jitter. Hovering a module while another menu was open therefore waited **500ms on roughly half of all approaches, chosen at random by noise**.
- **The reported symptom follows from that mechanically, and is worth stating because it is what makes the bug feel like the app ignoring you.** Nothing happens for half a second, so you move toward where the menu should be. That leaves the row — which cancels the pending open *and* schedules the hide. No menu ever appears. Clicking the arrow calls `show()` directly and bypasses the whole ladder, so clicking becomes the only thing that reliably works: precisely "I have to click on arrow then it is showing permanently else it is going away."

- **A pending open now re-evaluates instead of running to term.** The delay was picked once at `pointerenter`, and the `pointermove` handler was guarded by `!flyoutOpenTimer` — so once a timer was armed, every subsequent move was a no-op and a pointer that had stopped aiming still served the full grace. Separately, the sheet had **no `:active` state anywhere** — a button that looks unchanged the instant it is pressed reads as "didn't register", which is the direct cause of "I have to click many times", and on a submit the extra click is a duplicate request rather than a cosmetic problem.

## 77. Stage 31.1 — QZ Tray silent printing (2026-08-03, code + schema + docs)

User request, framed from marketplace operations: *"For Myntra and other Marketplaces OMS, I want to crack QZ print automation"*, with Myntra support's own setup mail attached, and the clarification that it should be **one-click print for all** — from the ERP as well as for the marketplace documents the channels supply. Three scope questions were put to the user first (what it drives, how QZ is authorised per PC, and what the label hardware is); the answers were one-click across both, self-signed/fully silent, and support all printer types. Item-by-item mechanics in micro_checklist.md Stage 31.1.

- **The whole feature rests on one protocol detail, and it was verified from QZ's source rather than assumed.** QZ Tray rejects a wrongly-signed call *silently* — it just falls back to prompting on every label, which reads as "QZ is flaky" rather than as a bug. The trap is that `qz-tray.js` hashes the request and hands the **hash** to the backend to sign, so the obvious backend implementations (sign the JSON; sign the raw digest bytes) both look right and both fail. `qz/auth/Certificate.java:363` settles it: `verifier.update(getBytesUtf8(sha256Hex(data)))` under `SHA512withRSA` — the signed bytes are the UTF-8 bytes of the **lowercase hex string**, over the JSON `{"call","params","timestamp"}` in that key order (`PrintSocketClient.java:218`). Both facts are pinned by tests, including a negative test asserting that signing the raw digest bytes does *not* validate.
- **No new dependency, per the repo's first principle.** The official client is ~150KB and carries its own promise shim, its own SHA-256 and remote-relay logic this deployment does not use; what was actually needed is a WebSocket, a hash and a signature, so `public/qz-print.js` is ~330 lines of vanilla JS. The one non-obvious consequence: `crypto.subtle` does not exist outside a secure context, and a packing bench reached at `http://192.168.x.x` is exactly that case — so a pure-JS SHA-256 fallback is mandatory, not defensive. It was checked against Node's `crypto` on 8 vectors plus 300 random-length fuzz cases, specifically across the 55/56/64-byte padding boundaries where a hand-written SHA-256 goes wrong.
- **Reused the `Printer` Master instead of adding a registry.** The doctype already existed (code/name/location/status, module key `stickers`, already validated by `engines/stickers.go`'s DEVICE-0298 check), so Stage 31.1 adds six fields to it — `qz_printer_name`, `print_role`, `printer_language`, label width/height, DPI — and the whole configuration screen comes free from the generic Master machinery. `print_role` is what makes printing one-click: the server resolves role → printer, so no operator ever picks one. The routes share the existing `stickers` module key for the same reason Stage 30.7 flagged — a new key 403s every existing tenant until their plan is edited.
- **Marketplace labels are passed through byte-for-byte, never re-rendered.** A channel-issued PDF goes to the printer exactly as supplied, because re-rendering a courier's label risks altering a barcode they have to scan. Physical sizing is applied as driver options (4x6 → 101.6 × 152.4mm) rather than by touching the document. ERP-native shipping labels *are* generated, and gained something the old path could not do: `engines/marketplace.go`'s `GenerateShippingLabel` explicitly returned plain text ("not a real symbology/PDF"), so on a thermal printer the AWB now goes out as a genuine Code 128 symbol.
- **The signing endpoint is deliberately not a blind oracle.** QZ's own reference backends sign whatever arrives, which lets any authenticated caller get arbitrary content signed by the server key. This one accepts exactly one SHA-256 hex digest and nothing else, so it can only ever emit signatures over hash-shaped values. It also means only the 64-char digest leaves the browser — a 5MB marketplace PDF is hashed locally and never re-uploaded merely to be signed.
- **Degrades instead of breaking.** If QZ Tray is not installed or not running, `qzTryPrint` returns false and every caller falls back to the existing `@media print` sheet. Non-thermal sticker printers take the same route by design, signalled by the server as `fallback: "browser"`. Nobody is ever blocked from printing because the bridge is down.
- **Verified**: `go build ./...`, `go vet ./...`, `node --check` clean; 7 new Go tests green (signature validates under the reproduced `Certificate.java` algorithm; raw-digest signing rejected; non-hash input refused; ZPL control-character escaping; payload shapes). The client was then run end-to-end against a **mock QZ Tray** implementing that same verification with the real generated key material — 15 assertions covering handshake order (unsigned `getVersion` → certificate → signed calls), message shape, the exact signed string and its key order, print params, and a negative control proving a tampered signature is rejected. **Not verified live against a real printer or a real QZ Tray**, and the DB-backed endpoints were not exercised — no PostgreSQL or Docker is available on this machine (see micro_checklist.md 31.1 for exactly what that leaves open).

## 76. Stage 30.5.5 — Retiring `Stores`, folding its fields into `Location` (2026-08-02, code + schema + docs)

The last open item in Stage 30, and the only one that was blocked on a product decision rather than on work. `Stores` was promoted in the sidebar and documented as "your shop/warehouse locations", but it had **zero Link references and zero Go references** — nothing in the system could select one. A user following the manual created their shop somewhere no transaction could see it.

Three options were put to the user; they chose to retire it and fold its fields in. The deciding fact was that the four fields only `Stores` had — address, city, contact_phone, manager — were **write-only by construction**. There was nowhere else in the product to record a shop's address or phone at all, so the cheaper "keep it, just hide it" option would have left a real gap sitting behind a removed menu entry.

**The migration's ordering is the whole risk.** Both `documents` and `doctype_fields` declare `REFERENCES doctype_meta(name) ON DELETE CASCADE`, so removing the `Stores` doctype row before its documents had moved would silently cascade-delete every one of them. The file therefore adds the columns, moves the data, and only then removes the doctype — with the removal guarded on there being nothing left to lose, so a partial migration leaves the doctype standing rather than taking the data with it.

The move is an `UPDATE`, not an `INSERT` + `DELETE`: `documents.id` is the primary key and is unique across *all* doctypes, so a Stores row's id cannot collide with a Location's, no id remapping is possible or needed, and re-pointing `doctype` in place preserves the row's provenance. ## 67. Stage 29.8 — the last two loophole items closed: status-transition map + JWT session staleness (2026-07-29, code)

Both remaining items in `ERP_LOOPHOLES_ANALYSIS.md` were blocked on a decision rather than on work — one marked `[needs design decision]`, the other deferred by standing policy. The user asked to be asked; they chose opt-in-strict enforcement scoped to transactional doctypes **and** masters, a middleware live-state re-check over a jti denylist, and multi-key signing rotation. Item mechanics in micro_checklist.md Stage 29.8.

- **The transition map extends what already existed rather than adding a second mechanism.** `StatusTransitionRule` (Stage 26.12.9) already had exactly the right shape and an admin screen; it was simply capped at four OMS entities and only ever read for order cancellation. Widening `entity` to free text (validated in code, so a doctype added tomorrow is governable without a migration) plus one `doctype_meta.strict_status_transitions` boolean was the whole schema change. Enforcement went on `ValidateTransactionalRules` — the single choke point every generic-doc write already passes — so coverage is by construction rather than by remembering to add a call. Rejections reuse `GLOBAL-0019`, which the error catalog already defined as "Invalid status transition"; no new code was invented for a scenario that was already named.
- **Opt-in strict is what makes it shippable.** A globally fail-closed map would have to be complete on day one or it takes production down, including the engine-driven paths that write statuses in SQL. Fail-open-unless-flagged means the 64 seeded doctypes are enforced and everything else behaves exactly as before, and any doctype can be un-flagged instantly if a matrix turns out wrong.
- **Generating beats listing, and testing proved why.** The masters' `Active`↔`Inactive` pairs and the approval-engine edges are derived from each doctype's own live `options` string. The explicit transactional matrices were first hand-written from `db/migration.sql` — and testing them against a **clone of the dev database** before touching anything showed four doctypes had since gained statuses (`PurchaseOrder`: `Pending Approval`/`Rejected`; `ProductionOrder`: `In Process`; `TransferOrder`: `Packed`; `CycleCountLine`: `Recount Requested`), with a real PurchaseOrder sitting in `Pending Approval` that strict mode would have frozen permanently. The same check found a `SalesInvoice` in status `Active` — not even one of its declared options — which no rule could ever free, since a rule can't name a `from_status` the schema doesn't know. That produced a deliberate escape: a write **leaving** an undeclared status is always allowed, because the destination is still constrained by `ValidateDocument`, so it can only move legacy debris back into a legal state, never into a made-up one. Neither bug would have been visible from reading the code.
- **Session staleness: the honest gap was bigger than "revocation".** `ParseToken` is pure HMAC and never touched the database, so every claim was frozen at issue time. Deactivating a user blocked new logins but left their existing token working for up to `JWT_EXPIRY_HOURS` (24h by default) — the QC report's "Deactivate Employee → login blocked ✅" was true and incomplete. A jti denylist, the obvious answer, would have fixed deactivation and done nothing at all for the role half: a demoted user's token was never revoked in the first place and keeps asserting the old role. Re-reading the user's row per request (30s cache, `AUTH_STATE_CACHE_SECONDS`) fixes both, needs no new table, no logout endpoint and no expiry sweeper, and makes the database authoritative for role and location too. A database failure returns a retryable 503 rather than a 401 — mistaking a replica hiccup for a mass deactivation would turn a blip into an outage.
- **Key rotation, without trusting the payload to pick the key.** `JWT_SECRET_<n>`: highest number signs, all configured keys verify, so rotation is add-key → wait one token TTL → delete-old-key with nobody logged out. Plain `JWT_SECRET` is unchanged and, with no numbered key set, the emitted token is byte-identical to before — the feature is inert until opted into. Verification tries every key rather than selecting by the token's own `kid`, deliberately: `kid` sits inside the payload and is attacker-controlled until the HMAC has already passed, so using it to choose the trust anchor means trusting unverified input to pick what verifies it. With a handful of keys the extra comparisons are microseconds. `kid` is still emitted so ops can tell which key signed a token; it is simply never load-bearing.
- **Two existing tests were wrong and were fixed, not accommodated.** Both minted tokens for user ids with no row in `users` — now correctly a dead session. One even documented itself as "indistinguishable at the JWT layer from a token a real successful login would have issued", which stopped being true; both now seed the row a real login would have required.

**Verified**: `go build ./...` + `go vet ./...` clean; 19 new engine subtests and 2 end-to-end wiring tests (a deactivated user's still-valid token → 401 `GLOBAL-0009`; an `RFQ` `Draft`→`Closed` → 422 `GLOBAL-0019` with the stored document provably unchanged, while the listed `Draft`→`Sent` still succeeds). Full suite green across 5 consecutive runs with strict mode live on all 64 flagged doctypes. One transient failure in an unrelated robotics test appeared once and did not reproduce in five subsequent runs — consistent with this repo's known shared-DB fixture-debris flakiness, not with anything in this change.

Then live-verified over real HTTP against a throwaway server instance (:8099, real dev DB, stopped afterwards): the blocked and allowed RFQ transitions behaved as above with the stored row confirmed unchanged on the rejection; an active token served 200, the *same* token returned 401 once the account was deactivated, and — after reactivating and demoting HR/Admin→Cashier — that same token was refused 403 on an HR/Admin endpoint while still claiming HR/Admin in its own payload, which is the concrete demonstration that the denylist approach would have left that half open. Key rotation was walked end to end as documented: with keys 1 and 2 both configured, tokens signed by either were accepted (`kid=1`/`kid=2` visible in the claims); after deleting `JWT_SECRET_1` and restarting, the key-1 token was rejected 401 and the key-2 token still served 200 — i.e. the retirement step is what actually retires, exactly as `deploy/erp.env.example` tells an operator.

## 66. Stage 29.7 — QC exhaustive-report follow-ups: gl_postings reporting index + production sslmode docs (2026-07-29, code + docs)

User asked for the two non-blocking observations in `QC_EXHAUSTIVE_REPORT.md` (O1 index, O2 sslmode) to be fixed, plus any other open items. Item-by-item mechanics in micro_checklist.md Stage 29.7.

- **O1 — the recommendation as written did not work, and measuring is what surfaced that.** QC asked for a composite `(account_code, created_at)` on `gl_postings` to stop the trial balance full-scanning at 10M+ rows. Built it, seeded a throwaway database with 1M postings, and the planner produced a *byte-identical* Seq Scan plan with the index present and absent. The reason is structural: these reports need `debit`/`credit` for every matching row, so a non-covering index buys a heap visit per row — strictly more expensive than the seq scan it would replace, which is why the planner correctly refused it. Shipping the literal recommendation would have added write cost to every GL posting and bought nothing. The index that ships is `(account_code, created_at) INCLUDE (debit, credit, cost_center)`; the payload is what flips the plans to index-only scans (`Heap Fetches: 0`). `cost_center` earns its 8MB because `GetCostCenterPL` groups by it; `department` is deliberately excluded — nothing groups by it, so it would be dead weight on every row.
- **The index alone is still inert — the date predicates had to change with it.** Nine gl_postings report queries wrote their range as `created_at::date BETWEEN $1 AND $2`. The cast wraps the indexed column in a function call, so the date could never enter an `Index Cond`; the queries scanned every posting for an account and threw most away with a filter. Rewritten to the equivalent half-open `created_at >= $1::date AND created_at < ($2::date + 1)` across `finance_reports_stage26.go`, `gl_cost_center.go`, `reports.go` and `report_definitions.go`, with the convention written down once at the top of `finance_reports_stage26.go` so the next query inherits it instead of re-introducing the cast. Index and rewrite are one change in two files' worth of edits — neither half is worth shipping alone. At 1M rows: P&L for a quarter 87ms/2,480 buffers → 5ms/162; cash flow 109ms/20,402 → 4ms/933; cost-centre P&L 95ms/20,359 → 9ms/158.
- **Equivalence was proved, not assumed.** Every rewritten predicate was run side by side with its original against the seeded data: zero differing rows on P&L and balance sheet, matching totals on cash flow, GST net balance, GST drill-down and the statutory export, and an explicit boundary case confirming a posting at `23:59:59.999` on the final day is still counted while `00:00:00` the next day is not — the one thing a half-open rewrite can plausibly get wrong.
- **A latent duplicate-index trap, found by testing the tenant path.** `ProvisionTenantSchema` clones with `LIKE ... INCLUDING ALL`, which copies indexes but **does not preserve their names** — a tenant provisioned after this migration carries the index under a server-generated name. A name-only `CREATE INDEX IF NOT EXISTS` would therefore not recognise it and would build a second, redundant copy on that tenant's ledger, doubling the write cost of every posting. The backfill loop matches on index *definition* instead. (The pre-existing `gl_postings_idempotency_key_idx` clones the same way, so this is a general property of the provisioning path, not something this migration introduced.)
- **O2 — sslmode.** `deploy/erp.env.example` now states why the shipped `sslmode=disable` is valid *only* for a same-box loopback DB, what to use off-box (`require` minimum, `verify-full` + `sslrootcert=` preferred), and how to check what was actually negotiated via `pg_stat_ssl`. It also records a driver-specific gotcha worth knowing: lib/pq's default when `sslmode` is omitted is `require`, **not** psql/libpq's `prefer` — verified in `lib/pq@v1.12.3/ssl.go`, where `mode == ""` shares a branch with `SSLModeRequire`. `deploy/README.md` A2 gained a matching callout at the step where the reader decides where Postgres lives, since that is where the decision is actually made.
- **What O1 does not fix, stated plainly.** `GetTrialBalance` aggregates the entire ledger with no date filter, so it must touch every row by definition and no index can help; bounding it to a period or as-of date is the real fix and is a product decision, now logged as 29.7.4. `GetStatutoryGLExport` filters on date alone with no `account_code`, so an account-leading index cannot seek for it — left to seq-scan deliberately, since it is an async background CSV export nobody waits on, and a second index would tax every posting write to speed it up (29.7.5).

**Verified**: `go build ./...` + `go vet ./engines/...` clean; `go test ./... -p 1` fully green, including the finance GL-totals test that has historically been flaky. Migration applied to two throwaway databases and to the dev DB across both its tenant schemas — applies clean, re-runs are no-ops, a schema without `gl_postings` is skipped, and a tenant provisioned post-migration inherits the index without a re-run duplicating it.
