## 1. Project Genesis

Started as a static, client-side HTML dashboard. Brand/Style data lived in a mock `db.js` and `localStorage`. No real database, no multi-tenancy, no numbering safety, no observability.

---

## 2. Architectural Decisions

| Component | Choice | Why |
|---|---|---|
| Backend | Go 1.22 | Single-binary, <15MB RAM/client, <10ms startup — cheap to host at density |
| Database | PostgreSQL 16.3 | Schema-per-tenant isolation + `SELECT ... FOR UPDATE` for ledgers/sequences |
| Multi-tenancy | Schema-per-tenant | Isolates tenant data, resolved dynamically per request |
| Branding | Custom ERP | Removed legacy sample branding for a clean, reusable system |

## 4-10. Phase 1-7 Build Records

- **Phase 1 — Numbering, Translation, Audit**
  - `engines/numbering.go`: `<Prefix><Sep><Store><Sep><FY><Sep><Number>`, row-locked (`SELECT ... FOR UPDATE`) against duplicates.
  - `engines/labels.go`: exact-match UI string translation via a DOM `TreeWalker`.
  - `engines/logs.go`: audit log writer + panic recovery (stack trace → DB, correlation UUID, HTTP 500).
- **Phase 2 — DocType Engine, Dynamic Forms, Bulk Import**
  - `engines/doctype.go`: registers custom document schemas + field metadata dynamically.
  - `public/app.js`: renders any doctype's fields (Data/Number/Select/Link) into one dynamic modal.
  - `engines/import.go`: CSV import with case-insensitive field mapping, validation, and a cell-level error report.
- **Phase 3 — Industry Profiles**
  - `public/profiles/`: Jewelry, Food & Beverage, Automobile, Clothing presets — swaps field definitions/sequences/vocabulary per tenant.
- **Phase 4 — Finance, Fulfillment, Returns**
  - `engines/finance.go`: balanced double-entry postings (Cash+COGS debit / Sales+Inventory credit at checkout).
  - `engines/fulfillment.go`: picking tasks with auto re-routing on reject; Return Anywhere with balanced refund postings.
- **Phase 5 — Scale Test**
  - `engines/scale.go`: 2,000-store concurrency simulation — ~456 TPS @ 100 workers, 0 conflicts, ledger balanced.
- **Phase 6 — Marketplace**
  - `engines/marketplace.go`: settlement reconciliation (validates payout math, posts GL) + carrier dispatch tracking.
- **Phase 7 — Optimization**
  - `engines/optimization.go`: replenishment suggestions, sales forecasting, SLA-breach monitor.
  - **Bug fixed (2026-07-12)**: velocity queries checked `status = 'completed'`, a status the system never writes. Fixed to `IN ('Paid', 'Settled')`.

## 48. Stage 26.12.2 — Allocation/Sourcing Engine (2026-07-25, code)

Continuing the Stage 26.12 OMS Maturity Sprint from §47's Order Engine, per its own "Next" pointer.

- **`engines.ResolveAllocationPlan`** (`engines/sourcing.go`) is the new Allocation/Sourcing Engine: reads every Active `AllocationRule` (26.12.9) scoped to a channel or globally (blank `channel`), tried in ascending-priority order until one strategy produces a usable plan. `qualifyingLocations` factors `FindBestFulfillmentNode`'s own per-location ATS scan into one shared helper so every single-location strategy below reuses it instead of repeating it.
  - **Highest ATS** - the pre-existing default, re-expressed over the shared helper.
  - **Nearest Pincode** - `abs(orderPincode−locationPincode)`, the design note's own validated distance proxy (`docs/specs/oms_master_blueprint_reference.md` §12: "a real geo/zone lookup would be a genuine improvement, not just a port"). Needed a new field: `Location.pincode` (`db/migrations_stage26_12_2_allocation_sourcing.sql`, additive/optional) - nothing on the Location master carried this before, so the strategy had no per-location data to compare against a `SalesOrder.shipping_address`'s own extracted pincode.
  - **Lowest Workload** - fewest open `FulfillmentTask` rows (status not Dispatched/Rejected, the two terminal states `TransitionTaskStatus` already recognizes) at a qualifying location, as a workload proxy.
  - **Oldest Stock** - earliest `inventory_availability.updated_at` among a location's relevant SKU rows. No per-batch received-date exists anywhere in this schema, so `updated_at` is the closest available proxy - documented as such with the same "proxy, not a real port" caveat the design note gives Nearest Pincode.
  - **Split Shipment** - the only strategy allowed to spread an order's lines across more than one location: each line is sourced independently (its own highest-ATS qualifying location). Every other strategy requires a single location to cover every line or it doesn't produce a plan at all - split-shipment only ever happens when a rule explicitly authorizes it, per the design note's own framing ("more than one group present *and* the channel disallows partial shipment → hold the order" - inverted here into "only the Split Shipment strategy may return more than one location").
  - **Manual** - always fails to produce a plan and stops the search immediately without trying lower-priority rules (it means "route this channel to a human," not "skip me if I don't fit"); the practical pattern is configuring it as the lowest-priority catch-all so richer rules get a chance first.
- **Fallback / allocation-exception behavior**: when a tenant has configured zero `AllocationRule` rows at all, `ResolveAllocationPlan` falls back to the exact pre-26.12.2 Highest-ATS/HO behavior (`FindBestFulfillmentNode`, which never fails), so an unconfigured tenant sees no behavior change - same "usable before any admin config" precedent `isCancellationBlocked` (§47) already set. Once at least one rule *is* configured, exhausting every rule without a plan returns `(nil, nil)` - the checklist's "allocation exception" case. No new table for the "exception queue" the checklist item calls for: `CreateSalesOrder`/`ReleaseOrderHold` hold the order with a new `HoldAllocationFailed` (`ALLOCATION_FAILED`) code, mirroring `validateOrderChain`'s existing "return a routable code, don't reject" contract - the resulting On-Hold `SalesOrder` rows filtered by `hold_reason` *are* the queue, same "reuse the doctype list view" precedent 26.12.1's hold routing and 26.12.7's planned dashboard both use.
- **Per-line allocation, not per-order**: `CreateSalesOrder`/`ReleaseOrderHold` (`engines/orders.go`) previously computed one shared `locationCode` for the whole order. Both now use `plan.LineLocations[i]` per line - the schema already supported this (`SalesOrderLine.location_code` is per-line, from 26.12.1), it just wasn't being exercised, since a single-strategy engine never needed to differ per line. Found and fixed a small pre-existing scope gap in `ReleaseOrderHold` while reworking it: it re-sourced *every* line on the order (including already-Reserved/Dispatched ones) through `FindBestFulfillmentNode` even though it only ever applied the result to Pending lines - harmless before (a no-op for the non-Pending ones besides the wasted lookup), but wrong now that per-line allocation is real, since re-running allocation over already-settled lines would waste capacity checks against demand that's already reserved elsewhere. Fixed by scoping the allocation call to only the lines still Pending.
- **Reallocation-on-reject left untouched**: the design note's other §12 callout (`fulfillment.go`'s `TransitionTaskStatus` reroute path) asks for "reserve-at-new-location-then-verify, roll back to the old reservation on failure." Read the existing code closely before changing anything: the release-old / reserve-new sequence already runs inside one `tx.Begin()`/`defer tx.Rollback()`/`tx.Commit()` boundary, so a failed new-location reservation already rolls back both halves atomically - the design note's requirement was already met by this repo's own transactional convention, just expressed differently than the retired prototype's own reserve-then-verify code did it. No change was the correct call here, not an oversight.

## 49. Stage 26.12.3 — Fulfillment Pick/Pack (2026-07-25, code)

Continuing the Stage 26.12 OMS Maturity Sprint from §48's Allocation/Sourcing Engine, per its own "Next" pointer.

- **Cross-checked `engines/wms.go` before writing anything**, per the design note's own explicit warning not to duplicate its bin-level pick-list structure. Concluded the two are genuinely orthogonal, not overlapping: `GenerateBinPickList` (Stage 20.18) answers "which bin do I physically walk to for this SKU" - a `bin_stock`-backed concern that only applies to warehouse locations with bins configured. This item answers a different question entirely: "did the picker/packer actually gather and box the right units for this task" - a concern that applies to every `FulfillmentTask` regardless of whether its location has bins at all. Building this as a bin-aware system would have coupled two independent things for no real benefit; the two now sit side by side, each doing its own job.
- **New file `engines/fulfillment_pickpack.go`** (not added to `fulfillment.go` - keeps `CreateFulfillmentTasks`/`TransitionTaskStatus` completely untouched, same file-per-concern split `orders.go` got from `sourcing.go` in §47): three new additive per-line JSON fields on `FulfillmentTask.items` - `picked_qty`, `packed_qty`, `short_qty` - alongside the pre-existing `sku`/`qty`. No table/column migration needed; a task created before this Stage just reads zeros for the new fields on first touch.
  - `ScanPickItem`/`ScanPackItem` share the same scan-resolution shape: resolve the scanned string against `Item.barcode` first, falling back to `Item.code` on a miss (the same degrade-gracefully convention §44's GRN barcode preview already established), then match against the *first* task line for that SKU still short of its stage target. A scan for a SKU not on the task at all, or a line already fully settled for that stage, is rejected with a message naming the actual resolved product (§12: "not just 'invalid scan'") - deliberately two different messages ("not part of this task" vs. "duplicate scan") so a picker/packer gets an actionable reason, not a generic bounce.
  - The blueprint's hard rule that packed quantity can never exceed picked quantity (§6) was **not** implemented as a separate guard - it falls directly out of `ScanPackItem`'s own match condition (`packed_qty < picked_qty`). A line at `packed_qty == picked_qty` simply can't match again; packing ahead of picking is structurally impossible rather than checked-and-rejected. Cheaper and can't drift out of sync with the matching logic the way a parallel check could.
  - `ShortPickLine` marks a line's *entire* remaining shortfall as short in one call (§12: "no partial-short-then-more-picking modeled" - the picker isn't asked how much is short, only that the rest can't be found), gated on a mandatory, category-matched `ReasonCode` via the exact same `requireActiveReasonCode` helper the Order Engine's Hold/Cancel actions already use (§47) - reused directly, not reimplemented. Needed one small additive migration (`db/migrations_stage26_12_3_pick_pack.sql`): `ReasonCode.category`'s Select options grew a "Short Pick" value alongside the existing Cancellation/Hold/Return/Allocation Exception/Other, since none of those fit.
  - `CompletePackTask` is the explicit, blockable completion action the checklist calls for (§12: "block pack completion on any exact-qty mismatch, not just a shortfall") - not something that happens implicitly the moment scans line up. Checks two distinct invariants per line, both required: pick resolution (`picked_qty+short_qty == qty` - no line silently left untouched) and exact pack match (`packed_qty == picked_qty` - not merely "no more than"). Only once every line clears both does the task move to `Packed`.
  - **Status vocabulary**: deliberately did *not* add finer-grained intermediate statuses ("Picked", "Packing") beyond what `db/migration.sql` already registered for `FulfillmentTask.status` (`Pending,Picking,Packed,Dispatched,Rejected`) - that Select's options already anticipated exactly this granularity and no more. Both the pick and pack stages now live under "Picking" (set the moment any pick progress happens - a scan or a short-pick) until `CompletePackTask` explicitly sets "Packed". A schema change to add "Picked"/"Packing" as separate values would have added ceremony nothing else in the codebase would have consumed.
- **New endpoints** (`internal/server/handlers_wms.go`, `routes.go`): `POST /api/v1/wms/pick-scan`, `.../pack-scan`, `.../short-pick`, `.../pack-complete` - added right alongside the existing putaway/pick-list/condition-transition floor-ops routes, same `moduleGate("wms",...)` gate, same role-open convention (no role gate beyond module entitlement - matches how those sibling routes are already scoped, since a distinct warehouse-operator role doesn't exist in this repo yet).
- **Deliberately out of scope**: auto-generating an invoice from a completed pack task, which the retired standalone OMS prototype did and §12 flagged as "worth preserving." Didn't port it because there's nothing real to generate it from yet - the Order Engine (26.12.1) has no `SalesOrder`→Shipment→Invoice wiring at all today; that chain is 26.12.4/26.12.5's job, and this item would have had to invent a shape for it that those items might then have to unwind.
