|---|---|---|

## 76. Stage 30.5.5 — Retiring `Stores`, folding its fields into `Location` (2026-08-02, code + schema + docs)

The last open item in Stage 30, and the only one that was blocked on a product decision rather than on work. `Stores` was promoted in the sidebar and documented as "your shop/warehouse locations", but it had **zero Link references and zero Go references** — nothing in the system could select one. A user following the manual created their shop somewhere no transaction could see it.

Three options were put to the user; they chose to retire it and fold its fields in. The deciding fact was that the four fields only `Stores` had — address, city, contact_phone, manager — were **write-only by construction**. There was nowhere else in the product to record a shop's address or phone at all, so the cheaper "keep it, just hide it" option would have left a real gap sitting behind a removed menu entry.

**The migration's ordering is the whole risk.** Both `documents` and `doctype_fields` declare `REFERENCES doctype_meta(name) ON DELETE CASCADE`, so removing the `Stores` doctype row before its documents had moved would silently cascade-delete every one of them. The file therefore adds the columns, moves the data, and only then removes the doctype — with the removal guarded on there being nothing left to lose, so a partial migration leaves the doctype standing rather than taking the data with it.

The move is an `UPDATE`, not an `INSERT` + `DELETE`: `documents.id` is the primary key and is unique across *all* doctypes, so a Stores row's id cannot collide with a Location's, no id remapping is possible or needed, and re-pointing `doctype` in place preserves the row's provenance. The four fieldnames were kept byte-identical so not one key inside a stored `data` blob had to be rewritten.

**The dev DB held zero Stores documents**, so applying the migration there proved only the empty path. The move was therefore exercised separately against a real Postgres — a throwaway program built a scratch schema carrying the same CASCADE declarations, seeded it, ran the real migration file and asserted the result: 15/15, including idempotence and the guard correctly refusing to cascade-delete an unmoved document. Plus 8 live browser checks and a re-run of the 30.5.8 suite (26/26).

USER_SOP §21 was **repurposed** from "Stores" to "Locations" rather than deleted, so section numbering and the module index stay stable, and it carries a note for anyone working from an older printout. The UAT check was inverted: it now asserts the screen's *absence*, so an older build fails it instead of quietly passing. **Stage 30 closes with this.**

## 75. Stage 30.5.8 — The picker consistency sweep (2026-08-02, code)

The audit item read as four unrelated chores: three screens missing a typeahead their siblings had, a 103-entry Location list with no structure, Employee picked with a `<select>` on five screens and a typeahead on a sixth, and icon-only buttons with no accessible name. They shared one cause — **there was no single place to be consistent in**. All 42 picker call sites configured `attachTypeahead` themselves, so "how a Location is chosen" was a decision made fifteen separate times, which is precisely how three screens came to be missing it without anyone noticing.

So the fix is structural before it is cosmetic. Every bespoke call site now goes through one door, `attachLinkTypeahead()`, which merges per-doctype defaults from a single `TYPEAHEAD_DOCTYPE_OPTS` table and delegates to the unchanged engine. The generic record form's Link field and a JSONTable's link column go through the same door, so a Location Link on any of the 53 Setup doctypes is now grouped without that screen having been edited — and any future picker improvement lands everywhere at once. The table is presentation only; a doctype absent from it takes the plain default, which is the safe direction to fail.

Two opt-in options carry it: `groupBy` (Location groups by `type`, with **first-appearance group order rather than a hardcoded `Store,Warehouse,HO` list**, so a tenant adding a fourth type gets it grouped for free) and `showAllOnFocus` (browse, not just search). The non-obvious constraint is that `highlight()`/`pick()` index into `items` — so grouping reorders that array itself, not merely the DOM, and headings are deliberately not `.typeahead-item`; otherwise arrow-keying past a heading would silently select the wrong record.

**Employee settled on the typeahead**, the control ~35 other pickers already use. `showAllOnFocus` preserves the one thing the `<select>` did better, and 30.5.1's empty-state guidance actually improves — a static hint becomes a focus-triggered row linking to where an Employee is created. The stored value is byte-identical and validation is untouched (Link fields are refused server-side with META-0198 regardless of control). It also deleted a real cost: the entire Employee list was being fetched on every HR tab render just to build `<option>`s, including for the eight tabs that never showed a picker.

The accessibility half went wider than the item's wording. `title` alone is the weakest accessible-name fallback and several screen readers skip it, so aria-labels were added to the seven `renderDocTable` row actions, the Approval Rules pair, and the five `index.html` modal-close buttons — and, most consequentially, to `copyableCell()`, one helper rendering ~30 copy chips per record list that each announced only "Copy, button". Fixed once at the helper, it names the value.

**Verified**: 6 unit tests over the grouping helpers (run against the shipped source, not a copy) and 26 live browser checks against a real Store Manager session, covering multi-type grouping, keyboard traversal across heading boundaries, unregressed type-to-search, all five converted employee pickers, and every icon-only button on a record list. `go vet`/`go build` clean. One incidental bug was caught by the run's uncaught-error assertion and fixed: `renderExecDashboard` dereferenced a possibly-detached container, throwing on every login where the user navigated away before Reports — now `DEFAULT_VIEW` — finished loading.

## 74. Stage 30.5.11 — Retiring the Dashboard landing screen (2026-08-01, code + docs)

User's call, made looking at the screen: *"Dashboard not required. Everything it is showing from config."* It was accurate — the screen held four derived stat cards (registered record types, audit-log count, active tenant, a hardcoded "Operational" pill) over nine shortcut tiles into **Database Schema Design, Dynamic Labels, Prefix Configs, Extension Hooks, Activity Log, Configuration, System Status, Tenant Entitlements** and **Tenant Usage**, every one of which the Settings module already lists. It owned no business data; it was a second front door to configuration.

Removed whole: the sidebar entry, `renderDashboard()`, its router branch and click handler, its `STATIC_VIEW_MENU_IDS` row, and the `.dashboard-grid`/`.dashboard-card`/`.card-content` rules. `.dashboard-stats-row` is a different class that Finance, the Reports exec dashboard, System Status and Tenant Usage all still use, and stays.

**The landing view is one new `DEFAULT_VIEW` constant, set to `reports`** rather than a literal repeated at each fallback. Reports is the only defensible universal choice: it is the single destination with neither a role gate (`MENU_PERMISSION_MAP` marks it `open`) nor an entitlement gate (no `MENU_MODULE_MAP` entry), so it renders for every role in every tenant — and its first tab is Stage 26.10.3's executive dashboard, which answers the same "what is going on" question with live figures instead of configuration links.

**The one way this could have shipped broken** was invisible to any fresh-profile test: `restoreLastView()` replays a saved view name, and every browser that had ever used the app carries `{"view":"dashboard"}` in `erp_nav_state`. Without a guard, existing users — and *only* existing users — would have restored into a router branch that no longer exists, i.e. a permanently blank screen. A saved `dashboard` now falls through to `DEFAULT_VIEW`.

Docs corrected in the same pass, including §73's own screenshot-derived count: the sidebar has **eleven** top-level entries now, three of them flyout-less. `USER_SOP.md` §2 was rewritten from "Dashboard" to "Where you land after signing in"; `UAT_CHECKLIST.md` §2 now asserts the screen's *absence*, so an older build fails the check rather than quietly passing.

**Verified**: `node --check` clean; live in a real headless browser as `cashier1` (the most restricted role) against a throwaway server on :8231 — 6/6 checks, covering the fresh-profile landing, the stale-`dashboard` reload, the absence of the menu entry, and a clean console in both. The exec dashboard rendered correctly for that role, falling back to an order-count trend under column masking. Screenshotted. Server stopped and port released afterwards.

## 72. Stage 30.8 — The project brain map (2026-08-01, tooling + docs)

User request: a graphify-driven diagram of the entire project, in its own folder under `docs/`, that "may behave like a brain", is appended to as the system grows, and is easy to update. Built as `docs/brain/` — `BRAIN.md` (7 Mermaid diagrams + a card per region), `brain.html` (interactive, self-contained), `brain.map.json` (the only hand-edited file) — generated by a new stdlib-only `cmd/brainmap`. Item-by-item mechanics in micro_checklist.md Stage 30.8.

- **The design decision that makes it maintainable is the three-input split.** The map says which regions exist; the *working tree* says which files exist; the *graph* says what calls what. Only the first is hand-written, so the picture cannot drift away from the code the way a hand-drawn architecture diagram does — and because the second input is the tree rather than the graph, a new file that no region claims is named in the run output and in BRAIN.md §6 instead of being silently absent. "We will append if new is added" is therefore enforced by the tool, not by anyone remembering. Most new files need no edit at all: `engines/wms_cycle_count.go` is claimed by WMS's existing `engines/wms*.go` the moment it exists.
- **Measuring coverage against the tree rather than the graph turned out to matter more than expected.** graphify parses 246 of 345 files; it has no extractor for `.sql`, JSON, PowerShell or Markdown, and `tree_sitter_sql` is not installed, so **all 71 migration files contribute zero nodes**. Had coverage been measured against the graph it would have read 100% while a third of the repo — including the entire schema — was invisible. Persistence & Migrations now correctly shows 71 files against 15 symbols, and BRAIN.md says plainly why a region can be substantial and still look sparse.
- **Two rounds of the diagram being accurate but useless, both fixed by admitting what the graph cannot see.** First: the Cortex floated unconnected, because the SPA is JavaScript and the server is Go and nothing links them statically — so 8 `declared_links` now state those boundaries by hand, drawn as thick `==>` arrows, each carrying a note on why it cannot be extracted. Second: **99% of cross-region relationships are `INFERRED`** (graphify resolves calls within a file exactly and across files by name), so the original "dot the edge when mostly inferred" rule dotted every single edge and encoded nothing. Now dotted means *entirely* inferred and solid means at least one relationship was parsed from source, with the 99% figure stated outright in the legend. The map's shape is reliable in aggregate; any individual edge is a lead to grep, which is what `CLAUDE.md` already says about `[INFERRED]`.
- **A third diagram exists because the honest one was a hairball.** Every region talks to Persistence and the Error Catalog — true, and the point of them, but it means those two nodes dominate and hide everything else. §2b redraws the same map with the three universal hubs removed, which is the only view where module-to-module wiring (OMS→Inventory, PIM→Connectors, Manufacturing→WMS) is legible.
- **Verification was done by rendering, not by reading.** All 7 Mermaid blocks were parsed with the real mermaid@11 parser in a headless browser, and `brain.html` was rendered in headless Chromium in both light and dark. That caught two defects a read-through would not have: Go's nil slices serialise as `null` and broke every `.length` read on page load, and the lobe-band backgrounds were painting over the connection lines. Lobe colours were validated with the dataviz palette validator rather than picked by eye.
- **One Windows-specific finding worth carrying forward**, since it will bite anything else in this repo that writes files from a freshly built binary: **Controlled Folder Access is enabled on this machine**, so Defender refuses writes under `Documents\` from unrecognised executables — and reports the refusal as `ERROR_FILE_NOT_FOUND`, i.e. Go says "the system cannot find the file specified" about a directory that demonstrably exists. Isolated by testing writes inside and outside `Documents\` and from PowerShell versus Go. `update-brain.ps1` works around it (generate into `%TEMP%`, copy in with PowerShell, which Windows trusts); the generator detects the case and names the cause rather than leaving the next person chasing a phantom missing directory.

## 71. Stage 30.7 — Config sweep ("nothing hardcoded") + POS offer engine (2026-08-01, code)

Two requests the user framed as separate and which were built as such: every module's operational config surfaced on the Configuration page and *properly wired* ("if I change it should immediately change everywhere"), and offer configuration for POS, set up in the ERP and reflected at the till. Two scope questions were put to the user first — which offer families to support (answer: all four) and what to do about platform safety limits (answer: expose them, but do it properly) — and the build followed those answers. Item-by-item mechanics in micro_checklist.md Stage 30.7.

- **The framework was already right; it was simply barely populated.** Stage 28.1 had built exactly the correct thing — declare a setting once (module/label/type/default), read it via `GetSetting*` at the point of use, and a fully generic Configuration screen renders it with no frontend work. The gap was that only **7 settings** had ever been registered while ~30 operational constants were still literals in Go. This Stage took it to **36 across 12 modules**. Because every existing consumer already read per-use and `SetSetting` invalidates the cache on write, the user's "changes everywhere immediately" requirement needed no new plumbing at all — it needed the constants to actually be settings. That property was then demonstrated live rather than asserted: changing the list-page cap moved a live endpoint from 3 rows to 2 in the same process, no restart.
- **Two things had to be added to the framework before the sweep could be honest.** Tolerances and money thresholds (2%, ₹50, ₹21,000) had no representable type, so a float type was added — with `Min`/`Max` unified to `*float64` so one bound pair serves both numeric types rather than growing a parallel set of fields. And `tokenTTL()` already honored a `JWT_EXPIRY_HOURS` env var, which meant a naive setting would have rendered an editable control that a deployment silently overrode — a dead knob, worse than the constant. `SettingIsOverridden` distinguishes "an admin actually set this" from "this equals the default", making the precedence explicit: admin edit → env var → default.
- **Platform limits were exposed with teeth, not left in code.** Asked whether page-size caps, per-tenant concurrency and batch sizes should be editable, the user said do it properly but don't hardcode it. Each is now a setting carrying a registry `Min`/`Max` the validator enforces at save time, so a mistyped page cap is rejected with a specific message instead of exhausting memory. Verified live: `999999` against a max of `10000` was refused.
- **One of the user's own examples turned out not to exist, and another turned out to exist but be unreachable.** PO/GRN "edit days" had no time-based rule anywhere — only amendment-reason and post-receipt checks — so that is new enforcement, attached generically at `ValidateTransactionalRules`' existing choke point (a doctype → setting-key map) rather than bolted onto two doctypes by hand, and defaulted to 0/no-limit so no existing tenant changes behaviour. Conversely the Pine Labs and Unicommerce base URLs were *already* per-tenant DB config with working endpoints — they simply had **no screen at all**, so they were surfaced as an Integrations section on the Configuration page. Deliberately not copied into the settings registry: two sources of truth for one URL is precisely the drift this Stage exists to remove.
- **The offer engine is one doctype, four families, evaluated server-side.** `Offer` is a flat-schema Master, so create/list/edit come free from the generic doctype machinery and the only new engine code is the evaluator. `offer_type` selects among Percentage Off / Flat Off / Buy X Get Y / Bundle Price — the same shape Campaign's `trigger_type` already established — with thresholds, coupon codes, customer tiers, validity windows, caps, priority and stacking as orthogonal conditions. Two rules are deliberate and tested: cheapest units go free in BOGO while the *most expensive* are bundled first (so adding an item can never raise the bill), and the running total is floored at the bill so no stack can drive a sale negative.
- **The POS preview never sets the price.** The screen calls a preview endpoint so the cashier can see what applies, but `handleCheckout` re-runs the same evaluator against the tenant's own `Offer` rows. A tampered client cannot invent a discount, and an offline cart replayed later is priced against the rules as they stand when it lands. What was applied is persisted onto the cart for the receipt and audit trail, for the same reason the GST breakdown already is.
- **The live run earned its keep.** Testing over real HTTP (which required completing a full MFA/TOTP enrollment to get an HR/Admin session) caught a bug no unit test would have: the new doctype had been given a fresh `pos` module key, but POSCart and POSSession are mapped to `sales`, and the module gate 403s any doctype whose key no plan grants — every Offer request would have failed with SAAS-0191 on every existing tenant. Separately, a `TestWMSP2` failure was briefly and wrongly attributed to this Stage's WMS change; re-running showed it flaky under shared-DB fixture state and green 3/3 with the change in place, and the full suite is clean.
- **Verified**: `go build`/`go vet`/`node --check` clean; full `go test ./... -p 1` green; 21 new tests across two files. Live: 36 settings over the wire, immediate propagation demonstrated end-to-end, guardrails and float validation enforced, and an ERP-created offer applying at the POS on the next call with thresholds, coupon gating, priority and unmatched-code reporting all correct. All live fixtures and the scratch tooling were removed afterward.

For the current build tracker, see **[docs/micro_checklist.md](micro_checklist.md)**.

## 70. Stage 30.6 — Server-issued document numbers (2026-08-01, code)

User request, made from the Purchase Orders screen: *"PO number will be auto created. I will create po sequence. Same of GRN and all other transaction."* Two scope questions were put to the user before building (how wide, and what shape the numbers take); both were answered, and the work followed those answers. Item-by-item mechanics in micro_checklist.md Stage 30.6.

- **The numbering engine already existed; nothing was calling it.** `engines.GenerateSequence` — a row-locked `sequence_counters` table plus an admin-editable `prefix_configs` series, with a Prefix Configurations screen already shipped — has been in the tree since Stage 1 and already numbered Purchase Requisitions, Payslips, CSV imports and RFQ/PO-on-conversion. The 13 bespoke create screens simply never used it and asked the user to type a number instead. So this was a wiring job at one choke point, not a new subsystem: a doctype → series registry (`engines/document_numbering.go`) invoked from `handleGenericDoc`'s POST branch, right beside the Purchase Requisition call that already did exactly this, and ahead of `ValidateDocument` because the fields it fills are mandatory.
- **What was actually broken was silent data loss, not typing effort.** The typed number was sent as the document `id`, and the documents table upserts on `ON CONFLICT (id)`. Two makers who picked the same PO number did not get an error — the second save overwrote the first, invisibly. Live-reproduced before the fix and now pinned by a test that submits the same form twice and asserts two distinct documents.
- **Two traps found by reading the schema rather than assuming it.** `PurchaseOrder` has *two* mandatory number fields (`po_number` and `code`) from two overlapping historical registrations, so both must be filled or the save fails validation. `ASN`'s `po_number` field, despite the name, holds the *referenced PO's* number — numbering it would have detached every ASN from its purchase order. The registry is per-field for exactly this reason, and both cases are regression-tested.
- **`reset_frequency` was dead config for the entire life of the project.** It was read and then never used; the counter bucket was always whatever financial year the caller passed. Making it real meant deriving the visible period segment and the counter bucket *together* — a series that resets on a period it does not display would re-issue last year's numbers, and since the number is the id, that is a rejected save rather than a cosmetic wart. Same reasoning governs the new `include_store` toggle: turning the store segment off also collapses the per-store counters, or two stores would be handed the same visible number.
- **The generic record form is driven by the server, not a second list.** Rather than copy the doctype registry into JavaScript, `GetDocTypeMeta` now stamps an `auto_generated` flag onto the field metadata the form already fetches, computed from the same registry that assigns the number. Adding a doctype to the registry updates the generic form for free.
- **Scope held deliberately.** An explicit `id` in a request body is still honored as an upsert, because that is this API's existing contract (`ProductContent`'s composite-id save and Stage 29.8's transition test both rely on it) and numbering it would convert updates into duplicate documents. No create screen sends an id any longer, so the user-facing guarantee stands; only a deliberate API caller can still choose one. Engine-created doctypes (orders, shipments, returns, settlements) were left alone.

## 67. Stage 29.8 — the last two loophole items closed: status-transition map + JWT session staleness (2026-07-29, code)

Both remaining items in `ERP_LOOPHOLES_ANALYSIS.md` were blocked on a decision rather than on work — one marked `[needs design decision]`, the other deferred by standing policy. The user asked to be asked; they chose opt-in-strict enforcement scoped to transactional doctypes **and** masters, a middleware live-state re-check over a jti denylist, and multi-key signing rotation. Item mechanics in micro_checklist.md Stage 29.8.

- **The transition map extends what already existed rather than adding a second mechanism.** `StatusTransitionRule` (Stage 26.12.9) already had exactly the right shape and an admin screen; it was simply capped at four OMS entities and only ever read for order cancellation. Widening `entity` to free text (validated in code, so a doctype added tomorrow is governable without a migration) plus one `doctype_meta.strict_status_transitions` boolean was the whole schema change. Enforcement went on `ValidateTransactionalRules` — the single choke point every generic-doc write already passes — so coverage is by construction rather than by remembering to add a call. Rejections reuse `GLOBAL-0019`, which the error catalog already defined as "Invalid status transition"; no new code was invented for a scenario that was already named.
- **Opt-in strict is what makes it shippable.** A globally fail-closed map would have to be complete on day one or it takes production down, including the engine-driven paths that write statuses in SQL. Fail-open-unless-flagged means the 64 seeded doctypes are enforced and everything else behaves exactly as before, and any doctype can be un-flagged instantly if a matrix turns out wrong.
- **Generating beats listing, and testing proved why.** The masters' `Active`↔`Inactive` pairs and the approval-engine edges are derived from each doctype's own live `options` string. The explicit transactional matrices were first hand-written from `db/migration.sql` — and testing them against a **clone of the dev database** before touching anything showed four doctypes had since gained statuses (`PurchaseOrder`: `Pending Approval`/`Rejected`; `ProductionOrder`: `In Process`; `TransferOrder`: `Packed`; `CycleCountLine`: `Recount Requested`), with a real PurchaseOrder sitting in `Pending Approval` that strict mode would have frozen permanently. The same check found a `SalesInvoice` in status `Active` — not even one of its declared options — which no rule could ever free, since a rule can't name a `from_status` the schema doesn't know. That produced a deliberate escape: a write **leaving** an undeclared status is always allowed, because the destination is still constrained by `ValidateDocument`, so it can only move legacy debris back into a legal state, never into a made-up one. Neither bug would have been visible from reading the code.
- **Session staleness: the honest gap was bigger than "revocation".** `ParseToken` is pure HMAC and never touched the database, so every claim was frozen at issue time. Deactivating a user blocked new logins but left their existing token working for up to `JWT_EXPIRY_HOURS` (24h by default) — the QC report's "Deactivate Employee → login blocked ✅" was true and incomplete. A jti denylist, the obvious answer, would have fixed deactivation and done nothing at all for the role half: a demoted user's token was never revoked in the first place and keeps asserting the old role. Re-reading the user's row per request (30s cache, `AUTH_STATE_CACHE_SECONDS`) fixes both, needs no new table, no logout endpoint and no expiry sweeper, and makes the database authoritative for role and location too. A database failure returns a retryable 503 rather than a 401 — mistaking a replica hiccup for a mass deactivation would turn a blip into an outage.
- **Key rotation, without trusting the payload to pick the key.** `JWT_SECRET_<n>`: highest number signs, all configured keys verify, so rotation is add-key → wait one token TTL → delete-old-key with nobody logged out. Plain `JWT_SECRET` is unchanged and, with no numbered key set, the emitted token is byte-identical to before — the feature is inert until opted into. Verification tries every key rather than selecting by the token's own `kid`, deliberately: `kid` sits inside the payload and is attacker-controlled until the HMAC has already passed, so using it to choose the trust anchor means trusting unverified input to pick what verifies it. With a handful of keys the extra comparisons are microseconds. `kid` is still emitted so ops can tell which key signed a token; it is simply never load-bearing.
- **Two existing tests were wrong and were fixed, not accommodated.** Both minted tokens for user ids with no row in `users` — now correctly a dead session. One even documented itself as "indistinguishable at the JWT layer from a token a real successful login would have issued", which stopped being true; both now seed the row a real login would have required.

**Verified**: `go build ./...` + `go vet ./...` clean; 19 new engine subtests and 2 end-to-end wiring tests (a deactivated user's still-valid token → 401 `GLOBAL-0009`; an `RFQ` `Draft`→`Closed` → 422 `GLOBAL-0019` with the stored document provably unchanged, while the listed `Draft`→`Sent` still succeeds). Full suite green across 5 consecutive runs with strict mode live on all 64 flagged doctypes. One transient failure in an unrelated robotics test appeared once and did not reproduce in five subsequent runs — consistent with this repo's known shared-DB fixture-debris flakiness, not with anything in this change.

Then live-verified over real HTTP against a throwaway server instance (:8099, real dev DB, stopped afterwards): the blocked and allowed RFQ transitions behaved as above with the stored row confirmed unchanged on the rejection; an active token served 200, the *same* token returned 401 once the account was deactivated, and — after reactivating and demoting HR/Admin→Cashier — that same token was refused 403 on an HR/Admin endpoint while still claiming HR/Admin in its own payload, which is the concrete demonstration that the denylist approach would have left that half open. Key rotation was walked end to end as documented: with keys 1 and 2 both configured, tokens signed by either were accepted (`kid=1`/`kid=2` visible in the claims); after deleting `JWT_SECRET_1` and restarting, the key-1 token was rejected 401 and the key-2 token still served 200 — i.e. the retirement step is what actually retires, exactly as `deploy/erp.env.example` tells an operator.

## 66. Stage 29.7 — QC exhaustive-report follow-ups: gl_postings reporting index + production sslmode docs (2026-07-29, code + docs)

User asked for the two non-blocking observations in `QC_EXHAUSTIVE_REPORT.md` (O1 index, O2 sslmode) to be fixed, plus any other open items. Item-by-item mechanics in micro_checklist.md Stage 29.7.

- **O1 — the recommendation as written did not work, and measuring is what surfaced that.** QC asked for a composite `(account_code, created_at)` on `gl_postings` to stop the trial balance full-scanning at 10M+ rows. Built it, seeded a throwaway database with 1M postings, and the planner produced a *byte-identical* Seq Scan plan with the index present and absent. The reason is structural: these reports need `debit`/`credit` for every matching row, so a non-covering index buys a heap visit per row — strictly more expensive than the seq scan it would replace, which is why the planner correctly refused it. Shipping the literal recommendation would have added write cost to every GL posting and bought nothing. The index that ships is `(account_code, created_at) INCLUDE (debit, credit, cost_center)`; the payload is what flips the plans to index-only scans (`Heap Fetches: 0`). `cost_center` earns its 8MB because `GetCostCenterPL` groups by it; `department` is deliberately excluded — nothing groups by it, so it would be dead weight on every row.
- **The index alone is still inert — the date predicates had to change with it.** Nine gl_postings report queries wrote their range as `created_at::date BETWEEN $1 AND $2`. The cast wraps the indexed column in a function call, so the date could never enter an `Index Cond`; the queries scanned every posting for an account and threw most away with a filter. Rewritten to the equivalent half-open `created_at >= $1::date AND created_at < ($2::date + 1)` across `finance_reports_stage26.go`, `gl_cost_center.go`, `reports.go` and `report_definitions.go`, with the convention written down once at the top of `finance_reports_stage26.go` so the next query inherits it instead of re-introducing the cast. Index and rewrite are one change in two files' worth of edits — neither half is worth shipping alone. At 1M rows: P&L for a quarter 87ms/2,480 buffers → 5ms/162; cash flow 109ms/20,402 → 4ms/933; cost-centre P&L 95ms/20,359 → 9ms/158.
- **Equivalence was proved, not assumed.** Every rewritten predicate was run side by side with its original against the seeded data: zero differing rows on P&L and balance sheet, matching totals on cash flow, GST net balance, GST drill-down and the statutory export, and an explicit boundary case confirming a posting at `23:59:59.999` on the final day is still counted while `00:00:00` the next day is not — the one thing a half-open rewrite can plausibly get wrong.
- **A latent duplicate-index trap, found by testing the tenant path.** `ProvisionTenantSchema` clones with `LIKE ... INCLUDING ALL`, which copies indexes but **does not preserve their names** — a tenant provisioned after this migration carries the index under a server-generated name. A name-only `CREATE INDEX IF NOT EXISTS` would therefore not recognise it and would build a second, redundant copy on that tenant's ledger, doubling the write cost of every posting. The backfill loop matches on index *definition* instead. (The pre-existing `gl_postings_idempotency_key_idx` clones the same way, so this is a general property of the provisioning path, not something this migration introduced.)
- **O2 — sslmode.** `deploy/erp.env.example` now states why the shipped `sslmode=disable` is valid *only* for a same-box loopback DB, what to use off-box (`require` minimum, `verify-full` + `sslrootcert=` preferred), and how to check what was actually negotiated via `pg_stat_ssl`. It also records a driver-specific gotcha worth knowing: lib/pq's default when `sslmode` is omitted is `require`, **not** psql/libpq's `prefer` — verified in `lib/pq@v1.12.3/ssl.go`, where `mode == ""` shares a branch with `SSLModeRequire`. `deploy/README.md` A2 gained a matching callout at the step where the reader decides where Postgres lives, since that is where the decision is actually made.
- **What O1 does not fix, stated plainly.** `GetTrialBalance` aggregates the entire ledger with no date filter, so it must touch every row by definition and no index can help; bounding it to a period or as-of date is the real fix and is a product decision, now logged as 29.7.4. `GetStatutoryGLExport` filters on date alone with no `account_code`, so an account-leading index cannot seek for it — left to seq-scan deliberately, since it is an async background CSV export nobody waits on, and a second index would tax every posting write to speed it up (29.7.5).

**Verified**: `go build ./...` + `go vet ./engines/...` clean; `go test ./... -p 1` fully green, including the finance GL-totals test that has historically been flaky. Migration applied to two throwaway databases and to the dev DB across both its tenant schemas — applies clean, re-runs are no-ops, a schema without `gl_postings` is skipped, and a tenant provisioned post-migration inherits the index without a re-run duplicating it.
