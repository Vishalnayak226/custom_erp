## 2. Architectural Decisions

| Component | Choice | Why |
|---|---|---|
| Backend | Go 1.22 | Single-binary, <15MB RAM/client, <10ms startup — cheap to host at density |
| Database | PostgreSQL 16.3 | Schema-per-tenant isolation + `SELECT ... FOR UPDATE` for ledgers/sequences |
| Multi-tenancy | Schema-per-tenant | Isolates tenant data, resolved dynamically per request |
| Branding | Custom ERP | Removed legacy sample branding for a clean, reusable system |

## 97. The dev cluster converted to UTF-8, closing the 20.6 defect (2026-08-13, database + one test + docs)

User asked for the three defects §96 recorded to be fixed. Two were already fixed in the tree and were re-verified rather than re-asserted: the SPA's relative asset paths (no relative `src`/`href` remains in `index.html`, no relative `fetch` in `app.js`) and the OpenAPI dynamic-schema trap (the paged envelope is inlined per endpoint, `PublicPage` is not a cached component). The third was real and outstanding.

**The dev cluster was WIN1252, so `₹` could not be stored and the migration runner stopped dead at Stage 37.1** — blocking 37.1.2, 38.2, 38.3 and 35.3.7 from ever reaching the database the tests actually run against. Fixed by conversion, not by weakening the migration: a currency master that cannot hold a currency symbol would have been the wrong repair.

- **Method**: `pg_dump --encoding=UTF8` → `CREATE DATABASE ... ENCODING 'UTF8' LOCALE_PROVIDER icu ICU_LOCALE 'en-US' TEMPLATE template0` → restore → `ALTER DATABASE ... RENAME`. **ICU `en-US` rather than `C`** is the decision worth recording: `C` collation is the path of least resistance on Windows and would have silently changed every text `ORDER BY` in the application to byte order, sorting uppercase before lowercase. PostgreSQL 16's ICU provider keeps the linguistic ordering the old `English_United States.1252` collation had.
- **Proven lossless before the swap, not after**: 127 tables compared with exact `count(*)` (not `reltuples` estimates) plus an `md5` checksum over the concatenated contents of `tenant_default.documents` — both identical. Only then were the databases renamed.
- **Reversible**: the originals are kept as `custom_erp_win1252_backup` / `custom_erp_test_win1252_backup`. Nothing was dropped. `custom_erp_test` was converted too, since it is the restore-drill target and would have hit the identical wall on the next drill.
- **Confirmed after**: all 5 blocked migrations applied; `₹` stored as 1 char / 3 bytes; CJK, Arabic and emoji now storable (verified server-side by byte length, because the Windows console mangles the *display* and would otherwise look like a failure); the startup `[WARN] server_encoding` line is gone, which is the same condition `ENV=production` hard-stops on; `go test ./... -p 1` green against the converted database.

**What the conversion revealed.** With the 35.3.7 migration finally applied to a database holding real history, `custom_erp` turned out to have **5,395 sweepable reservations out of 5,419** — 99.6% of every reservation in it was holding stock against a line that had been cancelled or deleted. The sweeper drained it to zero with no negative `reserved` counts. That is the leak the stage was written for, measured rather than argued.

It also **caught a wrong assumption in the sweeper's own test**. The sweep is batched at 500 rows per call — deliberate, so one long transaction cannot hold locks the live order path needs — so a single call on a database with a five-thousand-row backlog never reaches a freshly inserted fixture. The test passed against a pristine throwaway database and failed against the real one. The test now drains in a bounded loop, which is what the 5-minute worker does over successive ticks, and fails rather than hangs if the sweep ever stops converging. The batching itself was correct and was not changed.

**The cluster itself was finished on 2026-08-13** (same day, recorded here rather than as a separate section because it closes the same defect). The conversion above fixed the two application databases, but left the thing that *mints* new ones: a bare `CREATE DATABASE` copies `template1`, and `template1` was still WIN1252 — so every new database on this box was still born unable to hold `₹`. `template1` was pristine (nothing in it but `plpgsql`), so it was dropped and recreated from `template0` with the same `ENCODING 'UTF8' LOCALE_PROVIDER icu LOCALE 'en-US'` clause the application databases got, which touched no user data. The clause was proven on a throwaway database *before* `template1` was dropped, so the cluster was never left without one. **Verified the way that actually matters**: a database created with no encoding clause whatsoever now comes out UTF8 + ICU `en-US` and stores `₹`, CJK and emoji correctly (4 chars / 13 bytes).

- **`template0` is still WIN1252, and that is correct, not an oversight.** It cannot be re-encoded without `initdb`, and it does not need to be: it is precisely the template a *differing* encoding may legally be copied from, which is exactly what makes every explicit `TEMPLATE template0 ENCODING 'UTF8'` clause in this repo work regardless of the cluster default.
- **The `postgres` maintenance DB is still WIN1252, deliberately.** It is not what new databases are copied from, so it mints nothing broken. It holds 20 empty tables and a single `test-tenant` row — debris from the retired standalone WMS project — and recreating it would have destroyed those schema objects for no encoding benefit. Left alone by explicit decision.
- **The two WIN1252 backups are retained by explicit decision**, pending a live UI pass against the converted database. `custom_erp_win1252_backup` (62 MB) and `custom_erp_test_win1252_backup` (15 MB). `ditos_erp` is an unrelated database and was never touched.

## 96. Stages 35.3.7 / 36 / 37.1.2 / 38 / 39 — the platform layer: public API, Knowledge Center, multi-currency (2026-08-12, code + schema + docs)

User handed over a ranked gap list and an explicit build order, deduplicated across the two: finish 36.1.3 and 36.7.2, build 38.3/38.5/38.9 together, open the first read-only 38.1 routes, build 38.8, land 39.2-39.7 as one safe unit, then 37.1.2 — plus 35.3.7, the correctness gap they ranked first. All eight built. Item-by-item detail in `micro_checklist.md`.

**One theme runs through the whole batch: attach behaviour at the choke point that already exists.** The currency stamp hangs off `ValidateDocument`, so the generic API, CSV import and every engine get it without a sweep. Group bulk edit resolves to ids and hands them to the *existing* `BulkUpdateDocuments`, inheriting its cap, validation, variant-uniqueness and re-approval rules rather than reimplementing them. The group export refactors `GetSearchFeedExportCSV` into a shared row reader so two exports cannot disagree about a product. The public API's OpenAPI spec is generated from the same route table the server registers from. None of these needed a second way of doing anything.

- **35.3.7 — reservations become attributable, and the table finally gets swept.** `inventory_reservation` gains nullable `order_id`/`line_id`; releasing a line now releases *that line's* row, with the old (sku, location, quantity) heuristic surviving only for pre-migration rows. **The sweeper deliberately refuses to expire an order's reservation on time alone** — `inventory.reservation_ttl_seconds` is a cart-hold TTL, and applying it to a confirmed order would release stock out from under a live order the moment it queued longer than the TTL, which is a far worse bug than the leak being fixed. Unattributed holds expire on `expires_at`; attributed ones only when their line is gone, deleted or no longer holding stock. The test asserts the negative case first.
- **36.1.3 / 36.7.2 — two seams that existed but had no callers.** The product-group resolver and the content-assist endpoint were both built earlier with no production consumer. Groups now drive bulk edit and CSV export from one modal on the Item screen; the Workbench has an **Assist** button that fills the content form and never posts, which is exactly the human-in-the-loop guarantee 26.4.11's design rests on.
- **38.3 + 38.5 + 38.9 — one mechanism, not three.** A public request is admitted, de-duplicated and recorded by the same middleware pass, and the traffic log is what makes the daily quota survive a restart. Built together because shipping any one alone leaves the surface unbounded, unsafe to retry, or unobservable. `publicAPIMiddleware` is a *second* middleware rather than a branch in `apiMiddleware`: a human session presents a JWT and inherits a role, an integration presents an opaque key and holds only its explicit scopes, and folding them together is precisely how a public route inherits a human's permissions.
- **38.1 — four read-only endpoints, each a curated projection.** Not a document dump: publishing the generic document shape would turn every future internal field into an accidental public contract. No cost or margin on a product; availability without the held-back buckets; order tracking that accepts the caller's own channel order id. Paging clamped at 200. Read-only by choice — the idempotency spine is already underneath for when writes are curated.
- **38.8 — the spec cannot drift.** One declarative route table read by both the registration loop and the generator; schemas reflected from the declared Go response types. Renaming a json tag changes the published contract in the same commit.
- **39.2-39.7 — a Knowledge Center that is authenticated by construction.** The generated output goes to `internal/kb/content/` and is embedded in the binary, *not* to `public/`, because anything under `public/` is served straight off disk by `http.FileServer` — so "authenticated by default" is a property of where the content lives rather than a check someone can forget. The public subset is rebuilt narrowed, never filtered in the browser, since an index listing an internal article's title has already leaked it. Stdlib only: no static-site generator, no bundler, no search service.
- **37.1.2 — dual currency without touching a single report.** `gl_postings.debit`/`credit` keep meaning functional currency, because every report, trial balance and GST return sums them and none is being taught about currency; the transaction amounts arrive in new columns beside them. A real correctness fix falls out: approval slabs are written in the tenant's currency and would have compared a USD 100 invoice against an INR threshold.

**Three defects found and fixed outside the nominal scope, all worth remembering:**

1. **The SPA could not boot on any two-segment URL.** `index.html` referenced its assets relatively, so `/help/<article>` resolved `styles.css` to `/help/styles.css`, got the SPA shell back, and the browser refused every stylesheet and script on MIME grounds. Single-segment product prefixes like `/wms` never exposed it; the first two-segment URL did. Five references made absolute, which also hardens `/wms/<anything>` and every future deep link.
2. **The dev database could no longer take migrations — since fixed (see §97).** `migrations_stage37_1_currency_foundation.sql` seeds `₹` and the local cluster was **WIN1252** — the 20.6 defect, finally biting. Migrations stop at the first failure, so everything from 37.1 onward was blocked there. The migrations themselves were fine: all 92 apply cleanly to UTF-8, which is where this session's verification ran. `db/migrate.go` now recognises SQLSTATE 22P05 and explains it instead of leaving someone debugging their SQL.
3. **A latent OpenAPI trap, caught before it shipped.** A type whose shape depends on its example value (the paged envelope's `interface{} Data`) must not be cached as a named component: two endpoints returning `PublicPage` carry different `Data`, and one named schema could only describe one of them while silently mis-documenting the other.

**Verified**: `go build`/`go vet`/`node --check` clean; `go test ./... -p 1` fully green across all four packages; every new endpoint exercised over real HTTP on a throwaway UTF-8 database and server (port 9101 — both destroyed afterwards, along with the seeded fixtures), including the full 429/quota/traffic-log cycle; and a real-browser Playwright pass over the Knowledge Center shell, search, contextual drawer, the Group Actions modal and the Assist button — **zero console errors**, no horizontal overflow. `cmd/minttoken` was added to the tree because every verification pass otherwise rewrites the same throwaway token minter.

**Concurrent-session note**: §95 (Stage 43) records that this session's in-flight `registerPublicAPIV1Routes` blocked `internal/server`'s compile mid-flight. That is resolved — the package builds and its tests pass. File sets are otherwise disjoint; **stage only reviewed files, never `git add -A`.**

## 95. Stage 43 — Go-live blocker sweep: the buildable half of the parked items (2026-08-12, code + docs)

User handed back eight parked items from `go_live_decisions.md` — escalation contacts and the alert webhook, connector/GSP/e-way/payment-terminal credentials, Cloudflare zone access, a pen-test vendor, UAT participants and hypercare sign-off, real QZ Tray printer verification, the competitor-scraping legal call, and the data mart — with "build from this which is possible… skip which needs decision for now."

Five of the eight are genuinely credential- or decision-shaped and stay open. Three had ungated repository work behind them, and the operating lesson is that **"blocked on a vendor" is not the same as "blocked on everything"** — one of the three turned out to be a live security defect that had been sitting in the tree the whole time, parked behind an item nobody could close.

- **43.1 Token claim delimiter smuggling — fixed.** The P1 that `pentest_scope.md` §4 names first, closed in-house instead of waiting for 26.11.1's vendor. Token payloads are a flat `k=v&k=v` string built with `fmt.Sprintf`, and every value in one comes from a column with no character restrictions, so a `&` or `=` in a username or location code changed the payload's *shape* — and the server then signed the forged result, so it arrived with a valid HMAC. Four cases, each written as a failing test first: `purpose=extension` smuggled through a username made `apiMiddleware` skip the Stage 29.8 live user-state re-check (so **deactivating that account stopped ending its session**); a location code overrode `role` and `tenant`, which are emitted before it under a last-write-wins parser; an MFA-challenge token could be given the `role` claim `SignPurposeToken` deliberately omits; and an `=` in a value silently dropped the claim entirely, emptying `Resolved-Username` in the audit trail. Both write paths are `requireHRAdmin`-gated, so the honest severity is insider persistence/escalation rather than anonymous remote escalation. Fixed by escaping values at the one choke point all three issuers share (`claimVal`/`url.QueryEscape`, with `SplitN` + unescape on parse), backward-compatible with tokens already in flight.
- **43.2 Nightly-backup failure and absence now alert.** Closes 26.11.7's own still-open note and clears one of `hypercare_plan.md`'s two stated preconditions. `deploy/backup.sh` gained ERR/EXIT traps that POST failures to the same `OPS_ALERT_WEBHOOK_URL` the Go server uses, sending only the failing command's first word so credential-bearing arguments never leave the box; and `StartBackupFreshnessMonitor` watches the backup *artifact's* age hourly, which is the half a script cannot cover — 26.11.3 found production had never run a nightly backup at all, and a cron that never fires produces no failure to report. Deliberately not exposed on `/api/v1/health`, which is public and would hand an unauthenticated caller the backup schedule and paths.
- **43.3 `X-Forwarded-For` parsed right-to-left.** §5 pre-specified this as the code-side prerequisite for Cloudflare while recording "no ungated repository work pending" — this was the part that was ungated. `clientIP` took the left-most entry, which is the end of the header a client writes; the app was correct in practice only because `deploy/Caddyfile` replaces forged headers, leaving a silent total bypass of the 5/min/IP auth limit one config line away. Now walks right-to-left past known proxies (loopback + private ranges, extensible via the new `TRUSTED_PROXY_CIDRS`), which also makes Cloudflare activation an env-var change rather than a code change.

**Verified**: `go build ./...`, `go vet`, `go test ./engines/ -p 1` clean; the backup webhook confirmed end-to-end against a mock receiver (real POST, valid JSON, names the failing stage, no secrets). `internal/server`'s 10 `TestClientIP` cases passed before a concurrent session's in-flight Stage 38 Public API work started blocking that package's compile (`registerPublicAPIV1Routes` referenced but not yet defined) — unrelated to this stage, to be re-run once it lands. Per-item detail in micro_checklist.md Stage 43, including the table of which parked items stay open and why.

## 94. Stage 38/39 foundations — scoped API identities and safe Markdown rendering (2026-08-11, code + one unapplied migration + docs)

User asked to start Platform & Extensibility and the Knowledge Center while the shared tree still contained concurrent Stage 35-42 work. Both starts were therefore taken at dependency foundations that add no live surface: external credentials before public routes, and a renderer before generated static help.

**Stage 38 — an integration identity that is not a person.** The repo already had `SignExtensionToken`, but that is deliberately a short-lived read token for exactly one doctype and cannot be rotated or revoked individually. It was not widened. New `api_credentials` is a tenant-local raw security table rather than a generic document, because generic document APIs expose stored JSON and a credential digest should never be retrievable. A key contains 256 bits from `crypto/rand`; plaintext is returned exactly once and only a SHA-256 digest plus operator-visible prefix is stored. SHA-256 is appropriate here because the input is high-entropy random material, not a human password. Scopes come from a small allowlist, expiry is optional, authentication uses constant-time comparison, and every malformed/unknown/revoked/expired/mismatched case returns the same error so prefixes cannot be enumerated.

New private Super Admin routes issue, list, atomically rotate and revoke credentials. Rotation inserts the replacement and revokes the predecessor in one transaction; issue/rotate responses use `Cache-Control: no-store`; list responses never contain plaintext or digest; lifecycle actions use the existing audit log. `engines.ProvisionTenantSchema` now clones the table for future tenants. The contract and first scope catalog are fixed in `docs/specs/public_api_v1.md`, but **no `/api/public/v1` business route exists yet**. This is the key safety boundary: per-credential limiting (38.3) and mutation idempotency (38.5) come before a key is accepted on external traffic. OAuth2 client credentials also remain open rather than being implied by the opaque-key implementation.

**Stage 39 — render safely before serving anything.** New `internal/kb` is a stdlib-only Markdown renderer covering the planned headings/lists/tables/fenced-code/links/emphasis/images/admonitions vocabulary. It produces stable duplicate-safe heading anchors, escapes all raw HTML, and allowlists URL schemes rather than trying to blacklist every script spelling. Tests cover the vocabulary plus script/data URLs, raw HTML, invalid UTF-8, malformed emphasis and an unclosed code fence. `cmd/genkb` and `public/help/` were deliberately not created: generated files under the existing static root would become public before 39.6's authenticated-by-default access path exists.

**Concurrency and verification.** New migration `db/migrations_stage38_2_api_credentials.sql` was executed in PostgreSQL inside `BEGIN`/`ROLLBACK` and is not applied or recorded. An end-to-end engine test created a uniquely named scratch tenant/schema, exercised issue → authenticate → rotate → old-key rejection → revoke → new-key rejection, then removed both; follow-up queries confirmed zero scratch rows/schemas. The first aggregate suite run caught one real pre-migration issue: `ProvisionTenantSchema` tried to clone `api_credentials` while its intentionally-unapplied template table did not exist. It now skips only that new table during the pre-migration window and clones it normally afterward; the exact engine/server provisioning tests pass. A later aggregate run surfaced the pre-existing WMS slotting fixture transiently empty; its exact test passed immediately in isolation and the final full `engines` package passed. Final bounded package runs are green for `db`, `engines`, `internal/kb`, `internal/server` and every `cmd`, with `go build ./...`, `go vet ./...` and `node --check public/app.js` clean. No process was restarted, no public route or frontend file was changed, and no unrelated concurrent file was replaced.

## 93. Stage 35 release train R1 — the OMS becomes a real product (2026-08-11, code + schema + docs)

User asked to work the open plan phase by phase. The open plan is the Parity Master Plan's Stages 35-39, and its own sequencing puts release train **R1 = 35.1 + 35.2 + 35.3** first, because those three items exist to clear the three structural debts everything downstream assumes are gone. All three are now closed. Full item-by-item detail in `micro_checklist.md` Stage 35.

**The plan's premise was checked before it was built on, and was partly stale.** `ImportChannelSalesOrder` already routed Shopify and Unicommerce onto `CreateSalesOrder` (commit `efed245`, 2026-07-27), and 35.1.4's notification wiring was already in place in `evaluateOrderShipmentClosure` and `RecordDeliveryEvent`. Building 35.1 as written would have re-done work that existed. What was actually open was different, and worse:

- **35.1.1** The two legacy importers (`ImportChannelOrder`, `ImportUnicommerceOrder`) never created the POSCart their own comments promised — they wrote reservations plus a `channel_order_mapping` row and *no document at all*, so a legacy channel import left stock reserved against nothing. Both are now thin adapters onto the SalesOrder path, keeping their `ORDER_ALREADY_IMPORTED` replay contract. The loose-map adapter also fixes a latent qty-0 bug (`item["qty"].(int)` never matches a `json.Unmarshal`'d `float64`).
- **35.1.2** The **BigCommerce webhook verified, audited, and then discarded every order**. Its hook body carries only `{scope, data:{type,id}}`, so `ImportBigCommerceOrder` now reads the order back over the v2 API and imports it (credential-gated, 26.2.x shape; answers 200 on failure so a bad SKU can't cost the store its subscription). The **Magento poller counted changed orders and logged the number** — it now imports them. The `unicommerce.order.imported` outbox event, dropped by the 26.12.1 rewire, is restored.
- **35.1.3** Decision: no backfill. New `orphaned-channel-orders` report lists pre-35.1 debris. Building it exposed a real defect — a dangling mapping row was honoured without checking the order existed, which made every legacy channel order *permanently un-importable*; now guarded, with `DO UPDATE` so the table converges on truth.
- **35.2** New `engines/oms_console.go` + `handlers_oms_console.go` + 8 routes. The old screen pulled four doctypes in full and joined them in the browser; filtering, counting and joining moved to SQL, and the browser now gets one page plus facet counts. Faceted list with saved views, one-call order detail (9 sections), report-backed tiles, bulk actions with per-order outcomes, and global search across order id / channel order id / AWB / phone / name / SKU.
- **35.3** New `engines/order_mutations.go` + `handlers_order_mutations.go` + 7 routes: item-level hold, order edit re-validated through the *same* `validateOrderChain`, switch facility (reserving at the destination before releasing at the source), priority honoured by a real pick worklist, and split into fulfilment groups rather than into a second order. All six gated through Stage 29.8's existing `lookupStatusTransitionRule` — `isCancellationBlocked`'s inline copy was consolidated onto it rather than a second reader being added.

**Two bugs found and fixed outside R1's nominal scope, both worth remembering:**

1. **SLA breach detection had never fired.** `documents.created_at` is a bare `TIMESTAMP` holding the database server's *local* wall clock, but `lib/pq` returns it tagged UTC. `GetSLABreaches`' `time.Since(created_at)` therefore reported every open task as 330 minutes *in the future* on this Asia/Calcutta deployment, so `elapsed > threshold` was false for anything younger than 5.5h plus the threshold. Elapsed time is now computed in SQL. The console's SLA tile reads **230** where it would have read 0. The test fixture that "proved" the old behaviour was inserting `time.Now().UTC()` — a frame nothing else in the application writes — so it agreed with the buggy reader and disagreed with every real row.
2. **`.stats-grid` and `.stat-value` do not exist in `styles.css`.** The old OMS screen used both; that is why its tiles rendered as full-width stacked bars with an unstyled number. Corrected to the real `dashboard-stats-row` / `.stat-val`.

**Verified**: `go build`/`go vet`/`node --check` clean, `go test ./... -p 1` fully green, every new endpoint exercised over HTTP on a throwaway server (:8097, stopped and released, scratch accounts deleted), and a real-browser Playwright pass — 4 tiles, 7 facets, working pager, detail modal with 7 actions and all 9 sections, zero console errors, no horizontal overflow.

**Known limitation, recorded rather than hidden**: `inventory_reservation` has no order or line reference, so reservations can only be matched to an order by (sku, location) pair — correct in aggregate, not provably per-line under concurrency. And nothing anywhere sweeps that table: `expires_at` is written and indexed but never read, so reservations are effectively permanent. Carried as 35.3.7.

**A concurrent session was live in this tree throughout** (Stage 36.1/37.1, §92 below). File sets are disjoint — that session owns `engines/pim_*`/currency and its own migrations; this one owns `engines/oms_console.go`, `order_mutations.go`, `channel_orders.go`, `sourcing.go`, `unicommerce.go`, `connector_bigcommerce.go`, `connector_magento.go`, `oms_reports.go`, `optimization.go`, `orders.go` and `db/migrations_stage35_2_oms_console.sql`. **Stage only those files — never `git add -A` here.**

## 92. Stage 36.1 / 37.1 foundations — Product Groups and effective-dated currency rates (2026-08-11, code + schema + docs)

User explicitly asked to start both Stage 36 and Stage 37 while protecting the ongoing session and partially completed work. The implementation therefore begins at each stage's dependency foundation, is additive, avoids `public/app.js`, and leaves both new migrations unapplied. This request also resolves parity-plan decisions D6 and D7: multi-currency, multi-entity, Projects and Service are real build scope, to be taken in plan order rather than skipped as speculative.

**Stage 36.1 — usable product groups without a parallel UI framework.** New `PIMProductGroup` is a normal PIM Master, so existing generic forms, CSV import, audit history and role permissions do the administrative work. Static groups store validated Item links. Dynamic groups use four typed fields—family, completeness-below, missing attribute and item status—mapped to the Report Catalog's existing flat parameter vocabulary; filled filters are ANDed and recalculated from current product data on every resolve. There is deliberately no saved query language or materialised membership to secure and refresh. `ResolvePIMProductGroupItemCodes` is the common downstream seam, `GET /api/v1/pim/product-groups/{id}/members` provides a permission-checked read path, and the registered **PIM Product Group Readiness** report makes current membership/completeness/missing fields usable from the existing Reports screen. This closes 36.1.1, 36.1.2 and the readiness-report part of 36.1.3; bulk actions, task assignment and export consumers remain open.

**Stage 37.1 — exchange-rate truth before posting behaviour.** New `Currency` and `ExchangeRate` Finance Masters carry ISO currency metadata, Spot/Average/Closing rate types, effective date windows and Manual/Imported provenance. INR alone is seeded because that was the application's existing implicit base; foreign currencies are not guessed. Partial unique indexes prevent ambiguous currency codes and duplicate active rate starts. A shared resolver accepts record IDs or currency codes, selects the latest applicable direct rate, safely inverts a reverse rate, returns identity for the same currency and emits `FIN-0021` when no rate exists. Validation is attached at `ValidateDocument`, so API saves and generic CSV imports share it. No existing financial document or posting path consumes these rates yet—37.1.2 remains the explicit point where transaction and functional amounts begin—so the foundation is non-behavioural for current work.

**Concurrency and verification.** New migrations are `db/migrations_stage36_1_product_groups.sql` and `db/migrations_stage37_1_currency_foundation.sql`. Each was executed through PostgreSQL inside an explicit `BEGIN`/`ROLLBACK`, including all tenant-propagation blocks and indexes, and neither was recorded or applied. Focused tests cover validation, static/dynamic resolution, the readiness report, effective dating, direct/inverse rates and the missing-rate failure. Final `go build ./...`, `go vet ./...` and `go test ./... -p 1` are clean. ## 85. Stage 34.1-34.3 built, the first production DR drill, and nightly backups finally switched on (2026-08-07, code + schema + ops + docs)

The user asked to clear everything actionable. That was two things: Stage 34's buildable half (34.1-34.3), and 26.11.3's restore drill. Both landed; both turned up something the checklist did not know. The drill's finding — that production had no nightly backup — was then signed off and fixed the same day (26.11.7). Item detail in `micro_checklist.md` (34.1-34.3, 26.11.3, 26.11.7).

- **34.2's premise was wrong, and the honest implementation was the interesting decision.** The item said "join `CompetitorPrice` to our `Item`/price list". **There is no price list.** `Item` has no price field of any kind, and the POS cashier types the sale price by hand into an editable input that starts at 0. So "our price" is resolved at report time as the last price we *actually transacted at*, newest wins across `SalesOrderLine.unit_price` and `POSCart items[].sale_price`. The alternative — inventing a price master — is a real feature with real product decisions behind it (per channel? per customer group? effective dates?) and had no business being slipped in under a competitor-pricing item. The cost is stated rather than hidden: a SKU never sold reports `Position = "No price on file"` with null gap columns, not a fabricated zero that would rank top of the gap list.
- **Registering `CompetitorPrice` as a Master doctype rather than a Transaction was what made it cost zero frontend code.** The Setup flyout and the generic doctype table both filter on `document_type = 'Master'`, so Master is what inherits the list, the New form and the Bulk Import button. A Transaction doctype would have been unreachable from the UI entirely — the exact trap `CycleCountLine` hit and had to be worked around with bespoke JavaScript. The rows are timestamped observations, so "Master" is a mild semantic stretch; the UI consequence decided it.
- **Following the documented import path literally exposed a bug in 89 doctypes.** `GenerateCSVTemplate` omits `id`/`status` from the header it emits, and `ValidateDocument` skips the mandatory check for those same two system fields — but `missingMandatoryColumns` did neither, so **any** doctype with a mandatory `status` rejected its own generated template with "missing mandatory column(s): status". Brand, Color, Customer, Vendor, Location, Employee, `CycleCountLine` — 89 in total. The tempting fix was to make `CompetitorPrice.status` optional and move on; the right one was the shared choke point, which repaired all 89 at once. This only surfaced because the verification downloaded the template and uploaded it, instead of hand-writing a CSV that happened to include `status`.
- **The undercut worker's de-duplication is the part that makes it usable rather than noise.** An hourly worker that alerts whenever a competitor is cheaper re-alerts on the same standing undercut every hour forever. State lives in `public.competitor_undercut_state.last_run_at` (the `patch_intake_state` shape), so only observations *recorded since the last cycle* can alert — one observation, at most one alert. The threshold setting defaults to **0 = disabled**, so a tenant that never loads competitor prices is never alerted about them.
- **The DR drill passed, but only after three blockers that each would otherwise have been met mid-incident.** The script **had never been deployed** (`deploy.ps1` ships the binary and `public/`, not `deploy/`). Its own documented `sudo -u erp` invocation **can never work**, because production's `erp` role correctly has no CREATEDB and the script derived its admin connection from `DATABASE_URL` — fixed with an optional `DRILL_ADMIN_URL` override rather than by granting the app role CREATEDB, which would weaken the running system in order to test a backup. And the superuser **cannot read `/opt/erp/backups`** (`drwxr-x--- erp:erp`), so the newest backup had to be staged elsewhere — including rewriting the `.sha256` sidecar's absolute path, because `sha256sum -c` resolves the path recorded *inside* the file and otherwise fails a perfectly good copy with a misleading "corrupted".
- **The drill's most important output was not the drill.** It passed — checksum verified, `pg_restore` clean, all three sampled tables matching live exactly. But the box had **no nightly backup at all**: two manual-looking files taken around deploys, an empty crontab, no systemd timer, `install_backup_cron.sh` never run. A backup that restores is only useful if a recent one exists, and `hypercare_plan.md`'s "two consecutive failed nightly backups" rollback trigger cannot fire when there is no nightly backup to fail. Left for explicit sign-off rather than installed, since a read-only drill is not licence to change production's configuration — **sign-off came the same day, and the cron is now live** (below).
- **The same env-file trap from §85's own deploy notes had a second victim, and it was the backup cron.** The line `deploy/backup.sh` had carried in its header since day one — `0 2 * * * /bin/bash -c 'source /etc/erp/erp.env && backup.sh'` — **can never work**, for exactly the reason `deploy.ps1`/`migrate.sh` hit earlier: `/etc/erp/erp.env` is a systemd `EnvironmentFile` (bare `KEY=value`, no `export`), so `source` sets `DATABASE_URL` as a shell variable and `backup.sh`, a child process, never sees it. Fixed to `set -a; . file; set +a` in `install_backup_cron.sh`, `backup.sh`'s header, `deploy/README.md` (which was still instructing a hand-paste of the broken line, and whose quick-reference `migrate`/`backup` rows had the same defect) and `backup_restore.md`. Worth naming as a class rather than a bug: **`source` is not `export`, and every consumer of this env file that spawns a child has to know that.** The one-line fix is cheap; finding it three times is not.
- **It was found only because the installer runs a real backup instead of trusting the crontab.** That step-5 immediate run is the difference between discovering this now and discovering it during a restore, since the failure mode is a silent non-zero exit at 02:00 into a log nobody reads. A second bug surfaced the same way: run as root from `/root` (0700), step 5 drops to `erp`, which cannot traverse that cwd, so the retention `find` exited non-zero and failed the whole run under `set -e` **even though the dump had succeeded** — a working install that looked broken. Fixed with `cd /`.
- **"The cron line exists" was still not accepted as proof.** `erp`'s shell is `/usr/sbin/nologin` and cron's `PATH` is `/usr/bin:/bin`, both narrower than the `sudo` environment the manual verification inherits — so a manual run proves `backup.sh` works, not that *cron* can run it. A temporary `* * * * *` entry pointed at a scratch `BACKUP_DIR` was left to fire on its own and did (`CRON[131799]: (erp) CMD ...`), producing a valid backup, then removed. The newest backup was finally decrypted with the box's own `BACKUP_ENCRYPTION_KEY` and piped to `pg_restore --list` (valid archive, `dbname: custom_erp`, 286 TOC entries) — the only check that proves the key on the box actually opens what the box writes, which a checksum does not.
- **Still not solved, and stated rather than buried: nothing alerts when a backup fails.** The job appends to `/var/log/erp-backup.log`; hypercare's rollback trigger still depends on a human reading it each morning. An *empty* log is a distinct failure from an *error* in it — one line per successful night means no new line proves the job never ran. That wiring belongs to 20.2's webhook. Off-box copies remain deliberately absent for want of storage credentials, so losing the droplet still loses the backups.
- **Production runs PostgreSQL 14.23; dev runs 16.3.** Found while inspecting the droplet, and it retroactively validated a choice made hours earlier for portability reasons: the price-gap query deliberately avoids PG16-only `pg_input_is_valid` in favour of a `LIKE '[%'` guard. ## 79. Stage 33 — Dialog viewport fit & responsive form layout (2026-08-04, code)

User report with a screenshot of the New Location dialog, its header cut off at the top of the frame and no Save button anywhere: *"Nothing is visible here. So, set up. Make it more 2 column or 3 if required so it will be visible. All screen and config it should auto adjust with 100% to any percent 40% or whatever. If 120% also it should get auto adjusted."* Item-by-item mechanics in micro_checklist.md Stage 33.

- **The multi-column request was the fix the user could see; the actual defect was that no dialog in the app could scroll.** `.modal-container` had no `max-height` and no scroll region at all, and `body` is `overflow: hidden`. A form taller than the viewport was therefore centred by the overlay's flexbox and clipped off **both** ends — the classic flex-centring overflow — so the first fields *and* the footer holding Save/Cancel were unreachable, with nothing on the page able to scroll to them. That is why "nothing is visible": not a column-count problem but an unbounded box. Fixed structurally — the container is a flex column bounded by `calc(100dvh - 40px)`, header and footer are `flex: 0 0 auto`, and `.modal-body` takes the overflow with `flex: 1 1 auto; min-height: 0; overflow-y: auto`. `min-height: 0` is the load-bearing declaration; without it a flex child will not shrink below its content and the container overflows again exactly as before.
- **The `<form>` wrapper broke the flex chain, and only measurement caught it.** With the container fixed, the harness still failed every case at or below 1280x720. In `index.html` most dialogs wrap body+footer in a `<form>`, so the **form** is the container's flex child rather than `.modal-body` — it stayed a content-sized block, the body never received leftover height to scroll in, and the footer was clipped as before. Written as `.modal-container > form` so the handful of JS-built modals that put `.modal-body` directly in the container are untouched. Worth recording because the container fix *looks* complete when read, and reading is what would have shipped it.
- **The generic document form is now an intrinsic grid rather than a breakpoint list.** `openDynamicModal()` serves every master and document create/edit screen and has an unbounded field count — Item renders ~20. `#dynamic-modal-body` became `grid-template-columns: repeat(auto-fit, minmax(min(240px, 100%), 1fr))`: no media queries anywhere, which is precisely what answers "40%, 100%, 120%, whatever" in one rule — browser zoom only changes the CSS-pixel viewport, and both the grid and the `dvh` bound are recomputed from it, so there is no zoom level with special handling and none to forget. The `min(240px, 100%)` inner bound is what stops a single column from overflowing a heavily-zoomed narrow viewport.
- **Kept surgical in both directions.** The grid is scoped to `#dynamic-modal-body`, so the table and summary modals that share `.modal-body` keep their existing single-column block layout; and the wide container is opt-in above 4 fields, so a 3-field master still renders in today's 520px dialog (where the 240px grid minimum yields one column on its own) instead of two-thirds of an empty row. JS learned exactly one new fact — the field count — plus a `.form-group-wide` marker so the JSONTable/JSONMap line editors from 30.5.3 span the full row rather than being squeezed into a 240px track. Column count itself stays entirely in the stylesheet.
- **The same bug lived in the second dialog system and was fixed with it.** `.custom-dialog-box` (`showCustomAlert`/`showCustomConfirm`/`showApiError`/`showCustomPrompt`) had the identical structure and the identical unbounded height, so a long `showApiError` detail list clipped its own OK button off-screen. Verified with a 40-row error list.
- **Verified in Chromium at eight viewport sizes, and the before/after is the point.** One harness drives the real `styles.css` against the DOM `openDynamicModal` builds, across viewports standing in for **zoom 40% → 300%** plus a deliberately short 1400x380 window: 3 columns down to 1097px, 2 at 768px, 1 at 520px, container inside the viewport and **Save reachable in every case**, body scrolling exactly when it needs to. Against `HEAD` the 120%/140%/200%/300%/short cases all put Save *below* the viewport bottom — `save=[720,757]` in a 720px-tall window — with `scrolls=false`, which is the user's screenshot reproduced as a number. A second harness serves the **real `index.html`+`app.js`** over HTTP and confirms the new rules leaked into nothing: `add-field`, `edit-prefix`, `add-label` and `bulk-import` still measure `cols=1 display=flex w=520`. (Geometry was asserted via `getBoundingClientRect`, not eyeballed from screenshots — with no backend the login screen sits at `z-index: 500` over the dialogs, so the screenshots of the real page show the login card while the measurements underneath remain valid.)
- **Not deployed.** Per 32.1.8 the user's `localhost:8080` is the droplet, so none of this reaches them until the tree ships; frontend-only, no migration or rebuild needed. Tracked as micro_checklist.md 33.2, awaiting their go-ahead.

## 78. Stage 32.1 — Interaction responsiveness: the sidebar hover defect (2026-08-04, code)

User report after using the deployed app: *"The interface is not at all smooth. I have to click many times. Then it is working. Hover is also not working. I have to click on arrow then it is showing permanently else it is going away."* Item-by-item mechanics in micro_checklist.md Stage 32.1.

- **One line explains the entire hover complaint.** The sidebar's flyout logic had accumulated a careful-looking delay ladder — a switch dwell, a longer "aim grace" for the diagonal reach, a hide grace, a hover bridge across the 8px gap — and the test that chose between the two dwells was `flyoutPointerTrail.dx > 0 && r.left >= flyoutPointerTrail.x`. The panel always sits to the right of the sidebar, so the second half is true for essentially **every** pointer position in the nav, and the decision collapsed to "is the pointer moving right at all" — sampled frame-to-frame, which at 120Hz is a sub-pixel delta made mostly of hand jitter. Hovering a module while another menu was open therefore waited **500ms on roughly half of all approaches, chosen at random by noise**.
- **The reported symptom follows from that mechanically, and is worth stating because it is what makes the bug feel like the app ignoring you.** Nothing happens for half a second, so you move toward where the menu should be. That leaves the row — which cancels the pending open *and* schedules the hide. No menu ever appears. Clicking the arrow calls `show()` directly and bypasses the whole ladder, so clicking becomes the only thing that reliably works: precisely "I have to click on arrow then it is showing permanently else it is going away."
- **Replaced with a real trajectory test rather than a longer delay.** Velocity is now sampled over a 90ms window (not one frame), a deliberate reach must cover 12px horizontally, and the pointer's projected crossing point must land inside the panel's **vertical** span before any grace applies. Because the test finally distinguishes "cutting the corner towards the open menu" from "moving down the sidebar", the blanket dwell that was compensating for it could drop from 140ms to 60ms and the grace from 500ms to 220ms. The delay ladder got shorter *and* the corner problem it existed for is better handled.
- **A pending open now re-evaluates instead of running to term.** The delay was picked once at `pointerenter`, and the `pointermove` handler was guarded by `!flyoutOpenTimer` — so once a timer was armed, every subsequent move was a no-op and a pointer that had stopped aiming still served the full grace. Dwell is measured from a `hoverStart` stamp and recomputed on each move, so the wait only ever counts down. Timer cancellation also gained an owner, so leaving row B can no longer cancel an open that row C scheduled.
- **The second half of "not at all smooth" was the transition timings.** Every hover state in the sheet ran on `transition: all var(--transition-speed)` — 250ms, the duration intended for sidebar-width and panel slides. Interaction feedback has to land inside the ~100ms that reads as instant; at 250ms the UI visibly lags the cursor. Added `--transition-fast`/`--transition-med`/`--ease-out` and pointed the hot paths at them, with named properties instead of `all` (which was also animating padding and border-width on `.menu-item.active`). Separately, the sheet had **no `:active` state anywhere** — a button that looks unchanged the instant it is pressed reads as "didn't register", which is the direct cause of "I have to click many times", and on a submit the extra click is a duplicate request rather than a cosmetic problem.
- **Verified live in Chromium against the real files, not by reasoning.** The harness serves `public/` statically and seeds an `erp_token`; `setupModuleFlyouts()` runs synchronously at the top of `init()` before the first `await`, so the nav binds fully even though every API call 404s without a backend. 12 assertions, 5 consecutive clean runs. **The same suite was then run against `HEAD`** to prove the diagnosis: a jittery approach over 6 runs went **`[2, 81, 3, 445, 70, 477]`ms before → `[4, 1, 4, 2, 7, 4]`ms after**, and "hover a module, wait a beat, then reach for the menu" produced **no menu at all before → the menu after**. Worth recording one methodological point: a straight synthetic pointer path down the sidebar has `dx == 0` and so **never trips the old bug** — the first version of the harness passed against the broken code. Reproducing it required simulating a hand that wobbles, which is exactly the input the old test could not cope with.
- **The most important finding of the session was not a code defect at all: the user was never running this code.** After 32.1 shipped, the report persisted — "hover in POS is not showing continuously, in localhost:8080". `localhost:8080` is held by `Open-ERP.cmd`, which runs `ssh -N -L 8080:127.0.0.1:8080 root@139.59.17.16`: **the app under test is a DigitalOcean droplet**, and it was still serving a **Stage-28-era build from 2026-07-27** — `app.js` 589KB against the tree's 658KB, with `menu-flyout-bridge` absent entirely. The tell was in the screenshot before any code was read: a **Dashboard** entry that Stage 30.5.11 deleted, and "Point of Sale"/"Accounting" for what the tree renamed to "POS"/"Financial Accounting" on 2026-07-26. Generalised rule, now in `ai_handover.md` §6: **verify what is actually deployed before debugging a UI report** — the deployed build can be weeks behind, and every minute spent reading correct code is wasted.
- **The "AllocationRule needs two clicks" report was the pre-28.5 defect, and the user's own screen recording contained the proof.** No ffmpeg on the machine, so frames were pulled by loading the mp4 in Edge via Playwright (the bundled Chromium lacks H.264) and screenshotting the `<video>` at intervals. The frame at 15.25s shows **Stock's flyout open under the pointer while the page and the highlighted row are both HR** — a menu belonging to one module while the app sits on another. That is exactly the shape of the bug Stage 28.5 fixed: `hideTimer` was per-container but `closeSubmenus()` is global, so module A's already-armed 200ms timer fires *after* module B's menu has opened and closes it; the menu disappears from under the pointer and the click lands on the page behind. Setup is the worst case — longest list, anchored lowest, so `maxHeight = availableBelow` forces internal scrolling and a long pointer journey. Replaying that gesture mechanically: **deployed build 0/6 first clicks registered, local tree 6/6.**
- **Deployed to production the same day**, on the user's explicit instruction to ship the whole tree including the unverified QZ work after the risk was put to them. ## 77. Stage 31.1 — QZ Tray silent printing (2026-08-03, code + schema + docs)

User request, framed from marketplace operations: *"For Myntra and other Marketplaces OMS, I want to crack QZ print automation"*, with Myntra support's own setup mail attached, and the clarification that it should be **one-click print for all** — from the ERP as well as for the marketplace documents the channels supply. Three scope questions were put to the user first (what it drives, how QZ is authorised per PC, and what the label hardware is); the answers were one-click across both, self-signed/fully silent, and support all printer types. Item-by-item mechanics in micro_checklist.md Stage 31.1.

- **The whole feature rests on one protocol detail, and it was verified from QZ's source rather than assumed.** QZ Tray rejects a wrongly-signed call *silently* — it just falls back to prompting on every label, which reads as "QZ is flaky" rather than as a bug. The trap is that `qz-tray.js` hashes the request and hands the **hash** to the backend to sign, so the obvious backend implementations (sign the JSON; sign the raw digest bytes) both look right and both fail. `qz/auth/Certificate.java:363` settles it: `verifier.update(getBytesUtf8(sha256Hex(data)))` under `SHA512withRSA` — the signed bytes are the UTF-8 bytes of the **lowercase hex string**, over the JSON `{"call","params","timestamp"}` in that key order (`PrintSocketClient.java:218`). Both facts are pinned by tests, including a negative test asserting that signing the raw digest bytes does *not* validate.
- **No new dependency, per the repo's first principle.** The official client is ~150KB and carries its own promise shim, its own SHA-256 and remote-relay logic this deployment does not use; what was actually needed is a WebSocket, a hash and a signature, so `public/qz-print.js` is ~330 lines of vanilla JS. The one non-obvious consequence: `crypto.subtle` does not exist outside a secure context, and a packing bench reached at `http://192.168.x.x` is exactly that case — so a pure-JS SHA-256 fallback is mandatory, not defensive. It was checked against Node's `crypto` on 8 vectors plus 300 random-length fuzz cases, specifically across the 55/56/64-byte padding boundaries where a hand-written SHA-256 goes wrong.
- **Reused the `Printer` Master instead of adding a registry.** The doctype already existed (code/name/location/status, module key `stickers`, already validated by `engines/stickers.go`'s DEVICE-0298 check), so Stage 31.1 adds six fields to it — `qz_printer_name`, `print_role`, `printer_language`, label width/height, DPI — and the whole configuration screen comes free from the generic Master machinery. `print_role` is what makes printing one-click: the server resolves role → printer, so no operator ever picks one. The routes share the existing `stickers` module key for the same reason Stage 30.7 flagged — a new key 403s every existing tenant until their plan is edited.
- **Marketplace labels are passed through byte-for-byte, never re-rendered.** A channel-issued PDF goes to the printer exactly as supplied, because re-rendering a courier's label risks altering a barcode they have to scan. Physical sizing is applied as driver options (4x6 → 101.6 × 152.4mm) rather than by touching the document. ERP-native shipping labels *are* generated, and gained something the old path could not do: `engines/marketplace.go`'s `GenerateShippingLabel` explicitly returned plain text ("not a real symbology/PDF"), so on a thermal printer the AWB now goes out as a genuine Code 128 symbol.
- **The signing endpoint is deliberately not a blind oracle.** QZ's own reference backends sign whatever arrives, which lets any authenticated caller get arbitrary content signed by the server key. This one accepts exactly one SHA-256 hex digest and nothing else, so it can only ever emit signatures over hash-shaped values. It also means only the 64-char digest leaves the browser — a 5MB marketplace PDF is hashed locally and never re-uploaded merely to be signed.
- **Degrades instead of breaking.** If QZ Tray is not installed or not running, `qzTryPrint` returns false and every caller falls back to the existing `@media print` sheet. Non-thermal sticker printers take the same route by design, signalled by the server as `fallback: "browser"`. Nobody is ever blocked from printing because the bridge is down.
- **Verified**: `go build ./...`, `go vet ./...`, `node --check` clean; 7 new Go tests green (signature validates under the reproduced `Certificate.java` algorithm; raw-digest signing rejected; non-hash input refused; ZPL control-character escaping; payload shapes). The client was then run end-to-end against a **mock QZ Tray** implementing that same verification with the real generated key material — 15 assertions covering handshake order (unsigned `getVersion` → certificate → signed calls), message shape, the exact signed string and its key order, print params, and a negative control proving a tampered signature is rejected. **Not verified live against a real printer or a real QZ Tray**, and the DB-backed endpoints were not exercised — no PostgreSQL or Docker is available on this machine (see micro_checklist.md 31.1 for exactly what that leaves open).

## 76. Stage 30.5.5 — Retiring `Stores`, folding its fields into `Location` (2026-08-02, code + schema + docs)

The last open item in Stage 30, and the only one that was blocked on a product decision rather than on work. `Stores` was promoted in the sidebar and documented as "your shop/warehouse locations", but it had **zero Link references and zero Go references** — nothing in the system could select one. A user following the manual created their shop somewhere no transaction could see it.

Three options were put to the user; they chose to retire it and fold its fields in. The deciding fact was that the four fields only `Stores` had — address, city, contact_phone, manager — were **write-only by construction**. There was nowhere else in the product to record a shop's address or phone at all, so the cheaper "keep it, just hide it" option would have left a real gap sitting behind a removed menu entry.

**The migration's ordering is the whole risk.** Both `documents` and `doctype_fields` declare `REFERENCES doctype_meta(name) ON DELETE CASCADE`, so removing the `Stores` doctype row before its documents had moved would silently cascade-delete every one of them. The file therefore adds the columns, moves the data, and only then removes the doctype — with the removal guarded on there being nothing left to lose, so a partial migration leaves the doctype standing rather than taking the data with it.

The move is an `UPDATE`, not an `INSERT` + `DELETE`: `documents.id` is the primary key and is unique across *all* doctypes, so a Stores row's id cannot collide with a Location's, no id remapping is possible or needed, and re-pointing `doctype` in place preserves the row's provenance. The four fieldnames were kept byte-identical so not one key inside a stored `data` blob had to be rewritten.

**The dev DB held zero Stores documents**, so applying the migration there proved only the empty path. The move was therefore exercised separately against a real Postgres — a throwaway program built a scratch schema carrying the same CASCADE declarations, seeded it, ran the real migration file and asserted the result: 15/15, including idempotence and the guard correctly refusing to cascade-delete an unmoved document. Plus 8 live browser checks and a re-run of the 30.5.8 suite (26/26).

USER_SOP §21 was **repurposed** from "Stores" to "Locations" rather than deleted, so section numbering and the module index stay stable, and it carries a note for anyone working from an older printout. The UAT check was inverted: it now asserts the screen's *absence*, so an older build fails it instead of quietly passing. **Stage 30 closes with this.**

## 75. Stage 30.5.8 — The picker consistency sweep (2026-08-02, code)

The audit item read as four unrelated chores: three screens missing a typeahead their siblings had, a 103-entry Location list with no structure, Employee picked with a `<select>` on five screens and a typeahead on a sixth, and icon-only buttons with no accessible name. They shared one cause — **there was no single place to be consistent in**. All 42 picker call sites configured `attachTypeahead` themselves, so "how a Location is chosen" was a decision made fifteen separate times, which is precisely how three screens came to be missing it without anyone noticing.

So the fix is structural before it is cosmetic. Every bespoke call site now goes through one door, `attachLinkTypeahead()`, which merges per-doctype defaults from a single `TYPEAHEAD_DOCTYPE_OPTS` table and delegates to the unchanged engine. The generic record form's Link field and a JSONTable's link column go through the same door, so a Location Link on any of the 53 Setup doctypes is now grouped without that screen having been edited — and any future picker improvement lands everywhere at once. The table is presentation only; a doctype absent from it takes the plain default, which is the safe direction to fail.

Two opt-in options carry it: `groupBy` (Location groups by `type`, with **first-appearance group order rather than a hardcoded `Store,Warehouse,HO` list**, so a tenant adding a fourth type gets it grouped for free) and `showAllOnFocus` (browse, not just search). The non-obvious constraint is that `highlight()`/`pick()` index into `items` — so grouping reorders that array itself, not merely the DOM, and headings are deliberately not `.typeahead-item`; otherwise arrow-keying past a heading would silently select the wrong record.

**Employee settled on the typeahead**, the control ~35 other pickers already use. `showAllOnFocus` preserves the one thing the `<select>` did better, and 30.5.1's empty-state guidance actually improves — a static hint becomes a focus-triggered row linking to where an Employee is created. The stored value is byte-identical and validation is untouched (Link fields are refused server-side with META-0198 regardless of control). It also deleted a real cost: the entire Employee list was being fetched on every HR tab render just to build `<option>`s, including for the eight tabs that never showed a picker.

The accessibility half went wider than the item's wording. `title` alone is the weakest accessible-name fallback and several screen readers skip it, so aria-labels were added to the seven `renderDocTable` row actions, the Approval Rules pair, and the five `index.html` modal-close buttons — and, most consequentially, to `copyableCell()`, one helper rendering ~30 copy chips per record list that each announced only "Copy, button". Fixed once at the helper, it names the value.

**Verified**: 6 unit tests over the grouping helpers (run against the shipped source, not a copy) and 26 live browser checks against a real Store Manager session, covering multi-type grouping, keyboard traversal across heading boundaries, unregressed type-to-search, all five converted employee pickers, and every icon-only button on a record list. `go vet`/`go build` clean. One incidental bug was caught by the run's uncaught-error assertion and fixed: `renderExecDashboard` dereferenced a possibly-detached container, throwing on every login where the user navigated away before Reports — now `DEFAULT_VIEW` — finished loading.

## 72. Stage 30.8 — The project brain map (2026-08-01, tooling + docs)

## 67. Stage 29.8 — the last two loophole items closed: status-transition map + JWT session staleness (2026-07-29, code)

Both remaining items in `ERP_LOOPHOLES_ANALYSIS.md` were blocked on a decision rather than on work — one marked `[needs design decision]`, the other deferred by standing policy. The user asked to be asked; they chose opt-in-strict enforcement scoped to transactional doctypes **and** masters, a middleware live-state re-check over a jti denylist, and multi-key signing rotation. Item mechanics in micro_checklist.md Stage 29.8.

- **The transition map extends what already existed rather than adding a second mechanism.** `StatusTransitionRule` (Stage 26.12.9) already had exactly the right shape and an admin screen; it was simply capped at four OMS entities and only ever read for order cancellation. Widening `entity` to free text (validated in code, so a doctype added tomorrow is governable without a migration) plus one `doctype_meta.strict_status_transitions` boolean was the whole schema change. Enforcement went on `ValidateTransactionalRules` — the single choke point every generic-doc write already passes — so coverage is by construction rather than by remembering to add a call. Rejections reuse `GLOBAL-0019`, which the error catalog already defined as "Invalid status transition"; no new code was invented for a scenario that was already named.
- **Opt-in strict is what makes it shippable.** A globally fail-closed map would have to be complete on day one or it takes production down, including the engine-driven paths that write statuses in SQL. Fail-open-unless-flagged means the 64 seeded doctypes are enforced and everything else behaves exactly as before, and any doctype can be un-flagged instantly if a matrix turns out wrong.
- **Generating beats listing, and testing proved why.** The masters' `Active`↔`Inactive` pairs and the approval-engine edges are derived from each doctype's own live `options` string. The explicit transactional matrices were first hand-written from `db/migration.sql` — and testing them against a **clone of the dev database** before touching anything showed four doctypes had since gained statuses (`PurchaseOrder`: `Pending Approval`/`Rejected`; `ProductionOrder`: `In Process`; `TransferOrder`: `Packed`; `CycleCountLine`: `Recount Requested`), with a real PurchaseOrder sitting in `Pending Approval` that strict mode would have frozen permanently. The same check found a `SalesInvoice` in status `Active` — not even one of its declared options — which no rule could ever free, since a rule can't name a `from_status` the schema doesn't know. That produced a deliberate escape: a write **leaving** an undeclared status is always allowed, because the destination is still constrained by `ValidateDocument`, so it can only move legacy debris back into a legal state, never into a made-up one. Neither bug would have been visible from reading the code.
- **Session staleness: the honest gap was bigger than "revocation".** `ParseToken` is pure HMAC and never touched the database, so every claim was frozen at issue time. Deactivating a user blocked new logins but left their existing token working for up to `JWT_EXPIRY_HOURS` (24h by default) — the QC report's "Deactivate Employee → login blocked ✅" was true and incomplete. A jti denylist, the obvious answer, would have fixed deactivation and done nothing at all for the role half: a demoted user's token was never revoked in the first place and keeps asserting the old role. Re-reading the user's row per request (30s cache, `AUTH_STATE_CACHE_SECONDS`) fixes both, needs no new table, no logout endpoint and no expiry sweeper, and makes the database authoritative for role and location too. A database failure returns a retryable 503 rather than a 401 — mistaking a replica hiccup for a mass deactivation would turn a blip into an outage.
- **Key rotation, without trusting the payload to pick the key.** `JWT_SECRET_<n>`: highest number signs, all configured keys verify, so rotation is add-key → wait one token TTL → delete-old-key with nobody logged out. Plain `JWT_SECRET` is unchanged and, with no numbered key set, the emitted token is byte-identical to before — the feature is inert until opted into. Verification tries every key rather than selecting by the token's own `kid`, deliberately: `kid` sits inside the payload and is attacker-controlled until the HMAC has already passed, so using it to choose the trust anchor means trusting unverified input to pick what verifies it. With a handful of keys the extra comparisons are microseconds. `kid` is still emitted so ops can tell which key signed a token; it is simply never load-bearing.
- **Two existing tests were wrong and were fixed, not accommodated.** Both minted tokens for user ids with no row in `users` — now correctly a dead session. One even documented itself as "indistinguishable at the JWT layer from a token a real successful login would have issued", which stopped being true; both now seed the row a real login would have required.

## 66. Stage 29.7 — QC exhaustive-report follow-ups: gl_postings reporting index + production sslmode docs (2026-07-29, code + docs)

User asked for the two non-blocking observations in `QC_EXHAUSTIVE_REPORT.md` (O1 index, O2 sslmode) to be fixed, plus any other open items. Item-by-item mechanics in micro_checklist.md Stage 29.7.

- **O1 — the recommendation as written did not work, and measuring is what surfaced that.** QC asked for a composite `(account_code, created_at)` on `gl_postings` to stop the trial balance full-scanning at 10M+ rows. Built it, seeded a throwaway database with 1M postings, and the planner produced a *byte-identical* Seq Scan plan with the index present and absent. The reason is structural: these reports need `debit`/`credit` for every matching row, so a non-covering index buys a heap visit per row — strictly more expensive than the seq scan it would replace, which is why the planner correctly refused it. Shipping the literal recommendation would have added write cost to every GL posting and bought nothing. The index that ships is `(account_code, created_at) INCLUDE (debit, credit, cost_center)`; the payload is what flips the plans to index-only scans (`Heap Fetches: 0`). `cost_center` earns its 8MB because `GetCostCenterPL` groups by it; `department` is deliberately excluded — nothing groups by it, so it would be dead weight on every row.
- **The index alone is still inert — the date predicates had to change with it.** Nine gl_postings report queries wrote their range as `created_at::date BETWEEN $1 AND $2`. The cast wraps the indexed column in a function call, so the date could never enter an `Index Cond`; the queries scanned every posting for an account and threw most away with a filter. Rewritten to the equivalent half-open `created_at >= $1::date AND created_at < ($2::date + 1)` across `finance_reports_stage26.go`, `gl_cost_center.go`, `reports.go` and `report_definitions.go`, with the convention written down once at the top of `finance_reports_stage26.go` so the next query inherits it instead of re-introducing the cast. Index and rewrite are one change in two files' worth of edits — neither half is worth shipping alone. At 1M rows: P&L for a quarter 87ms/2,480 buffers → 5ms/162; cash flow 109ms/20,402 → 4ms/933; cost-centre P&L 95ms/20,359 → 9ms/158.
- **Equivalence was proved, not assumed.** Every rewritten predicate was run side by side with its original against the seeded data: zero differing rows on P&L and balance sheet, matching totals on cash flow, GST net balance, GST drill-down and the statutory export, and an explicit boundary case confirming a posting at `23:59:59.999` on the final day is still counted while `00:00:00` the next day is not — the one thing a half-open rewrite can plausibly get wrong.
- **A latent duplicate-index trap, found by testing the tenant path.** `ProvisionTenantSchema` clones with `LIKE ... INCLUDING ALL`, which copies indexes but **does not preserve their names** — a tenant provisioned after this migration carries the index under a server-generated name. A name-only `CREATE INDEX IF NOT EXISTS` would therefore not recognise it and would build a second, redundant copy on that tenant's ledger, doubling the write cost of every posting. The backfill loop matches on index *definition* instead. (The pre-existing `gl_postings_idempotency_key_idx` clones the same way, so this is a general property of the provisioning path, not something this migration introduced.)
- **O2 — sslmode.** `deploy/erp.env.example` now states why the shipped `sslmode=disable` is valid *only* for a same-box loopback DB, what to use off-box (`require` minimum, `verify-full` + `sslrootcert=` preferred), and how to check what was actually negotiated via `pg_stat_ssl`. ## 65. Stage 28.5 — UI defect batch: dialog legibility, flyout reliability, global search (2026-07-28, code)

Four defects reported by the user in one session, all fixed in `public/app.js` + `public/styles.css` — no Go, no schema change, no new dependency. Item-by-item mechanics in micro_checklist.md Stage 28.5.

- **Popup text invisible in dark mode.** `.custom-dialog-body` had a literal `color: #334155` against the dark `--panel-bg`, ~1.3:1 — the message in every alert/confirm/prompt was effectively unreadable. Rather than patch that one rule, the fix removed the whole class of bug: Stage 28.2's token block claimed in its own comment to be "the single source of color for the whole app", but 25 rules below it still used literal hexes and never re-themed. Added semantic tokens (`--on-primary`, `--text-placeholder`, and `-color`/`-hover`/`-strong`/`-soft-bg`/`-soft-border` sets for danger/warning/success) to all three token blocks and routed every one of those rules — plus 9 inline `style="color:#..."` strings in `app.js` — through them. Light-theme token values are the exact previous hexes, so light mode is unchanged by design. The comment above the dark block is now a stated rule (no literal colours below it) with its two sanctioned exceptions named: the print-only `.receipt`/`.sticker-label` rules, which are always ink-on-paper, and translucent rgba scrims/glows, which read on either theme. That comment is the thing that keeps this fixed for the next feature, not the 25 individual edits.
- **"In POS nothing is working — if I click anything it is not opening anything."** Not a routing bug: driving all 38 sidebar entries programmatically showed 37 navigating correctly (the 38th being Dashboard, already the current view). The flyout was closing before the pointer got to it, so the click landed on the page behind. Four separate causes, each reproduced with a scripted pointer path before and after the fix — a per-container hide timer that called the *global* close (so module A's timer shut module B's just-opened menu); an 8px gap between row and panel that sits outside the container's box, so crossing or pausing in it started the close; `mouseleave` bound alongside `pointerenter`, where pointer events fire ahead of their compatibility mouse events and the leave handler therefore ran *after* the next row had already cancelled the pending close; and sibling entries with no flyout of their own acting as dead zones with nothing listening. Plus a 140ms dwell (500ms when the pointer is measurably heading at the open panel) before a different module can take the menu, so a diagonal reach across the rows in between no longer steals it. Worst realistic case — a continuous diagonal corner-cut — went from 6/34 to 32/34; the ordinary path is 34/34.
- **Long flyouts running off the bottom of the screen.** Found while verifying the above. Flyout height was capped to the space *below* its trigger, so Stock's 12 screens and Setup's ~25 master doctypes put their tail off-screen when anchored low — nominally scrollable, but not actually reachable, since getting to the scrollbar meant leaving the panel. Panels now take their natural height and slide up to stay on screen, scrolling internally only when taller than the viewport.
- **Global search did nothing.** The box promised "Search menu, category, type or HSN" but only filtered a table you already had open — on the dashboard it was inert. It now suggests every matching destination (sidebar entries, including those only reachable by hovering the right module) and every registered record type, ranking name hits above module hits. Picking one dispatches a click on the real sidebar element where one exists, so routing, permission filtering and active-item highlighting stay in a single place rather than being re-implemented in the search path; the index reads the same `perm-hidden`/`module-hidden` classes the sidebar uses, so hidden entries can't leak through it. Reuses the existing `.typeahead-menu` vocabulary; the pre-existing table filtering still runs alongside. The `category`/`HSN` half of the placeholder is deliberately still unimplemented — searching product records across entities needs a new server-side endpoint, which is a feature, not this bug fix.

**Verified**: `node --check` clean; live Playwright against the running dev server as `manager1` — all 38 entries navigate, hover→click 34/34 on a realistic pointer path, the three original flyout repro scenarios all pass, search suggestions and both Enter- and click-to-navigate confirmed, zero console/page errors. Dark and light screenshot-checked with computed contrast ratios recorded in the checklist (dialog body 1.3:1 → 12.99:1).

**Follow-up the same day (28.5.5)**: the user reported two further symptoms immediately after the above landed, and both traced back to the flyout change itself rather than to anything older. The click handler had been written as a toggle, so clicking a module row already hovered open `closed` it - experienced as "it has to be clicked twice or thrice before it opens". A row now only ever opens on click; closing is moving away, clicking outside the nav, or Escape, and the pin bookkeeping the toggle needed is gone. Separately, while a cursor rests on a row no further `pointerenter` ever fires, so anything that closed the menu meanwhile - navigating away from it, an outside click, Escape, or the sidebar re-rendering and swapping the DOM node under a stationary pointer - left it shut with the cursor still sitting on it; `pointermove` now re-opens when nothing is open, so the smallest movement brings it back. 8/8 on a dedicated repro, with the 34/34 navigation pass and the three flyout scenarios re-run green. Worth carrying forward: sidebar module labels are tenant-configurable and did in fact change under this session mid-run (Buying -> Procurement, Accounting -> Financial Accounting), so UI tests here must key off element IDs or DOM order, never the visible label.
