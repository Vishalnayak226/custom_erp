# Custom ERP — Full Project Blueprint

**Purpose of this document**: a single, self-contained snapshot of this project meant to travel outside the repository — hand it to an outside reviewer (including an AI like ChatGPT) with no other context, and they should be able to form an informed opinion on where this project stands. It is written from five perspectives in turn — CEO, Product Head, CTO/Architect, Developer, and Project Tech Lead — because those are the five questions this project actually gets asked, and each one wants a different cut of the same facts.

Everything below is a synthesis of documents already in this repository, cited by path. This document does not introduce new facts — it exists to make the existing facts legible to someone who hasn't read the other ~20 documents. **Snapshot date: 2026-08-31.** (Previous snapshot: 2026-07-19 — six weeks and roughly 30 build stages ago. If you read the old version, discard it: the single biggest fact below, that the system is now live in production, was not true when it was written.)

## 1. Executive Summary (the CEO question: "what have we built, and what can a customer actually use right now?")

This is a custom-built, multi-tenant Enterprise Resource Planning (ERP) system, written from scratch in Go with a PostgreSQL backend, targeting small-to-mid-size retail/distribution businesses (jewelry, F&B, apparel, and similar verticals) that need POS, inventory/warehouse, procurement, finance/GL, order management, product information management (PIM), and omnichannel (Shopify/BigCommerce/Magento/Amazon/Flipkart/WooCommerce + six Indian quick-commerce platforms) sync in one system, without paying for or being locked into a large incumbent platform (SAP, NetSuite, Odoo Enterprise).

**The system is live in production**, at `https://app.wholeops.in` (own registered domain, `wholeops.in`, since 2026-08-14), served over real TLS through a DigitalOcean droplet. This is the single biggest change since the last snapshot of this document, which described a system that had never been deployed anywhere outside a developer's laptop.

**But there is a large and growing gap between what is live and what is built.** Production has been frozen at one commit (`2575097`, deployed 2026-08-21) for ten days as of this writing. In that window, engineering closed three entire benchmark-parity programs in the tree that have **not yet reached production**:

- **All of Stage 42** — a from-scratch Warehouse Management System built to SAP Extended Warehouse Management / Infor WMS depth (batch/serial traceability, a real warehouse task-dispatch spine, dock/yard/appointment scheduling, wave picking, slotting, multi-owner 3PL billing — 58 items, 6 phases). Committed to git, not deployed.
- **The rest of Stage 35** — Order Management System parity with Unicommerce/Uniware (settlement reconciliation against real invoices, exchange/reverse-pickup returns depth). Committed to git, not deployed.
- **All of Stage 36** — Product Information Management parity with Unbxd (task/workflow engine, import/export/syndication depth, a Digital Asset Management library, GS1 barcode generation, related products, bulk translation). Partially committed, partially still sitting as uncommitted files in the working tree.

**What this means in plain terms**: engineering has, in ten days, roughly doubled the system's functional depth in warehouse operations, order management, and product data management — and none of a real user has been able to touch any of it yet. Closing that gap is a deploy operation (commit the remaining PIM files, run migrations, ship a binary), not further engineering work — but it is real work that has not been scheduled, and every day it doesn't happen is a day the sales/demo story understates what actually exists. See §5 for what closing it requires.

**Biggest open risks, plainly stated**:
1. **The production-vs-tree gap above.** Nobody should describe "what the product does" from a demo of `app.wholeops.in` today without knowing this — the live instance is materially behind the codebase.
2. **A meaningful slice of go-live readiness is genuinely blocked on business inputs, not engineering.** Real escalation contacts, a real ops alerting webhook URL, non-production connector/GSP/payment-terminal credentials, an external penetration-test engagement, and UAT participant sign-off are all named, scoped, and waiting — the code side of each is either done or has nothing left to build until the input arrives. See §5's table.
3. **Concurrent-session build process.** Most of this codebase is built by AI coding agents working from a human's direction, with explicit git-hygiene conventions adopted to manage more than one session editing the same tree in overlapping windows (§6). This remains both the reason for the velocity in §4 and a real operational habit that has to keep being followed.
4. **No real-world transaction volume yet.** Everything has been tested with synthetic/small data, unit+integration tests, and live-verification passes against throwaway instances — not a real business's live order volume, and not yet through the newly-built WMS or the deepened OMS/PIM.
5. **Deep ERP-core work (Stage 37: multi-entity/intercompany, landed-cost costing, budgeting, a real financial-statement builder, projects, service management) is still mostly unbuilt** — only its multi-currency foundation (37.1) has shipped. If a prospect specifically needs those, they are not there yet; see §2.

## 3. Architecture (the CTO/Architect question: "how is this actually built, and does it hold up?")

**Stack**: Go 1.22 (single static binary, no runtime dependency), PostgreSQL 16 (schema-per-tenant, UTF-8/ICU across every database as of a 2026-08-13 encoding fix), a hand-written vanilla-JS SPA frontend (no framework) served as static files. Deliberately minimal-footprint — the whole rationale (`docs/architecture/architecture_evaluation.md`) is that a Go binary idles far lighter than a Python/Node equivalent, which matters at the target scale (many small-margin tenants, not a handful of enterprise accounts). This constraint has held for six more weeks of building: **zero new third-party dependencies** were added across the entire WMS Parity Plan (58 items) and PIM parity work — a hand-rolled Code128 barcode encoder, a hand-rolled 54-country phone-normalization table, and a hand-rolled Markdown renderer were all built in plain Go rather than reached for as a library.

**Core pattern — metadata-driven document engine**: unchanged in shape since the last snapshot. Most DocTypes go through one generic `documents` table per tenant schema (`id`, `doctype`, `data JSONB`, `status`, audit columns) plus a `doctype_meta`/`doctype_fields` registry that validates server-side. New subsystems (WMS's `WarehouseTask`, `Batch`, `Zone`; PIM's `PIMTask`, `PIMExportTemplate`) all sit on this same engine rather than growing bespoke tables — the one recurring exception being a handful of *breakdown* tables (`bin_stock_batch`, `bin_stock_owner`) built specifically to avoid forcing a new dimension into an existing table's primary key on a live system, the same non-destructive-migration discipline the whole codebase follows (see §6).

**Money is now paise-precision internally.** `gl_postings.debit`/`.credit` moved from whole-rupee `INT` to `BIGINT` paise (Stage 46, deployed) — closing a real, silently-compounding under-collection of GST that had been present since the earliest GL work. Every money-surfacing API response still converts back to rupees at its own boundary, so the external contract and the frontend's existing formatting needed zero changes.

**Multi-tenancy** gained a second resolution path: host-based, not just claim/header-based. `<slug>.wholeops.in` resolves to a tenant ahead of `X-Tenant-ID` in the pre-auth chain, gated by an on-demand-TLS `ask` endpoint that refuses to let Let's Encrypt issue a certificate for anything that isn't a live tenant. The session token's own tenant claim stays authoritative regardless of which hostname a request arrived on — a deliberate, narrower guarantee than "host wins," chosen specifically to avoid a cross-tenant escalation path.

**Event-driven omnichannel sync**: unchanged in principle — no user-facing transaction makes a synchronous outbound call to a 3rd-party system; everything drains through `integration_event_outbox`. The connector layer was generalized into a real capability contract this cycle (auth/order-pull/inventory-push/catalog-publish/status-push/error-mapping/capabilities) so the sync scheduler and UI stopped branching on platform name — new channels (Amazon, Flipkart, WooCommerce, six Indian quick-commerce platforms) implement the contract rather than extending a conditional.

**Security posture**: everything in the 2026-07-19 snapshot, plus what §2's Security row lists. Worth flagging for an outside reviewer specifically: a real privilege-escalation defect (claim-delimiter smuggling in the session-token payload) was found and fixed in-house this cycle, not by an external tester — the process is finding real defects, but an actual third-party penetration test still hasn't happened (see §5).

**Build-quality gate**: `go build ./...`, `go vet ./...`, `go test ./... -p 1`, `govulncheck`, `gitleaks` in CI on every push — unchanged. The working convention (build → test → live-verify against a real throwaway instance → document) has held across every stage cited in this document; both were re-confirmed clean (`go build`/`go vet`) against the full current working tree, including every uncommitted file, as part of writing this snapshot (2026-08-31).

**Deployment model**: now two real paths rather than one aspirational one. The original 3-environment dev/test/live worktree pipeline (`promote.ps1`) is unchanged. A second, newer path stands up the public-internet production instance: `deploy/deploy.ps1` ships a binary to a DigitalOcean droplet behind Caddy, which handles TLS (both a static platform-host certificate and, once Stage 44 deploys, on-demand per-tenant certificates). No containerization, still a deliberate decision.

## 6. How Build Quality Was Actually Controlled

Unchanged in method since the last snapshot, and continued to hold under six more weeks and roughly 200 more checklist items:

- **Live-verification discipline**: a real throwaway server instance is spun up and the feature actually exercised (hit the endpoint, read the resulting database row, and for frontend work, drive a real headless browser) before an item is marked done — recorded per-item in `docs/micro_checklist.md` and, for closed stages, in `docs/archive/micro_checklist_closed_stages.md`.
- **Real bugs found and fixed along the way, listed rather than glossed over**: a live privilege-escalation defect in the session-token encoding (43.1); a nightly backup that had silently never run at all on production, closed by absence-detection rather than assumed-fixed (43.2); a `renderView` re-entrancy bug that had been double-rendering panels across roughly 45 screens; a GRN validation gate that had never actually been reachable through the live UI for four new WMS master types; a field-write-permission bypass reachable only through bulk-edit/CSV import, not the single-record path; a floor-truncated GST calculation that had been silently under-collecting tax on every fractional-rupee sale since the earliest GL work.
- **Non-destructive-migration discipline, held under real production data**: every schema change across the WMS and PIM parity programs is additive; where a new dimension (batch, serial, owner) would otherwise have forced its way into an existing table's primary key, a separate breakdown table was built instead specifically to avoid rewriting a live table's constraints.
- **Concurrent-session discipline**: `git status`/`git diff` before staging anything, only the specific files actually reviewed staged — never a blanket `git add -A` — because more than one AI session has genuinely edited this tree in overlapping windows, repeatedly, across this six-week window.
- **Documentation-as-you-go**: `docs/micro_checklist.md`, `docs/project_ledger.md`, and `docs/ai_handover.md` (the "big 3") are kept in sync after every unit of work by standing repository convention. This document itself — and the archival/cleanup pass that produced this snapshot — is an instance of that convention being applied to the doc that had drifted furthest.

## 7. What We'd Want Outside Feedback On

Since this document's stated purpose is to go into an outside review (including an AI reviewer) for a second opinion, here's what would actually be useful feedback:

1. **Given the production-vs-tree gap in §1, what's the right sequencing** — close the deploy gap first (so the WMS/OMS/PIM depth already built becomes real for users), or keep building Stage 37's ERP-core depth first (so the *next* deploy carries more)? This is a real prioritization call, not a technical one.
2. Is the metadata-driven DocType approach (§3) still the right long-term bet six weeks and three benchmark-parity programs later, or is the JSONB-plus-registry pattern showing strain anywhere specific (WMS's breakdown-table pattern is one place it had to bend)?
3. **Is now the time for the external penetration test** named in §5, given a real in-house-found privilege-escalation defect already exists in this system's history (43.1) and production has real traffic for the first time?
4. Given Stage 39.13's content gap, is a written module handbook actually the highest-leverage next Knowledge Center investment, or would a smaller number of high-traffic "getting started" flows (POS day-one, WMS receiving-to-putaway) cover more real usage per hour spent writing?
