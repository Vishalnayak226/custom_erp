## Stage 31 — Silent printing (QZ Tray) 🚧 (opened 2026-08-03 from the user's marketplace-OMS print request; 31.1 built, live printer verification outstanding)

User request: *"For Myntra and other Marketplaces OMS, I want to crack QZ print automation"* + Myntra support's setup mail, clarified as **one-click print for all** — ERP documents *and* the marketplace documents channels supply. - [x] **31.1.1 The signing contract, verified from QZ's source — closed 2026-08-03.** A wrongly-signed call is rejected *silently* (QZ falls back to prompting per label), so this had to be established as fact, not inferred. `qz-tray.js` hashes the request and passes the **hash** to the backend, which makes both obvious backend implementations wrong. Settled from source: `qz/auth/Certificate.java:363` → `verifier.update(getBytesUtf8(sha256Hex(data)))` with `SHA512withRSA`, over `new JSONObject(message, {"call","params","timestamp"}).toString()` (`PrintSocketClient.java:218`). So: sign the **UTF-8 bytes of the lowercase hex digest**, key order `call,params,timestamp`. Also confirmed there is **no 2.1-vs-2.2 fork** to handle — the tray does its own hashing from the raw JSON, so both client generations agree. Ports `[8181,8282,8383,8484]` secure / `[8182,8283,8384,8485]` insecure; handshake is unsigned `getVersion` → certificate → signed calls.

Only ESC-POS gets commands; every other language (PDF/HTML/ZPL/unset) gets rasterisable HTML through the OS driver. Do not "simplify" this back to `isRawLanguage`.
  - **`escposColumns` defaults an unset `label_width_mm` to 42 columns (80mm roll).** A 58mm till needs `label_width_mm = 58` on its Printer record or lines are laid out too wide. Every line is clipped to the column count and `escposRow` clips the *description*, never the amount — a receipt is checked on its numbers.
  - **Real bug found and fixed in the existing browser receipt**: `printPOSReceipt` never deducted `offer_discount`. Checkout returns `amount_due = sale_total - loyalty_discount - offer_discount`, so any sale with a Stage 30.7 offer applied printed a total **higher than the cash actually collected**. Now takes a 7th defaulted `offerDiscount` argument and prints Subtotal / Offer discount / Loyalty lines. The stored `applied_offers` are also named on the ESC-POS receipt, which is what the comment on `handlers_pim_pos_finance.go`'s `storedPayload["applied_offers"]` asked for in the first place.

  - **`qzTryPrint` gained a `quiet` option, and the three new call sites use it.** "No Printer record is Default For Receipt" is the *normal* state of a tenant that has not set QZ up — without `quiet` a cashier would get a `DEVICE-0298` modal on every single sale before the browser sheet appeared. Quiet suppresses the payload-preparation dialog and the unmapped-printer dialog (both `console.debug`'d instead) and falls through. A failure at the tray itself stays loud in every case: that one means printing was really attempted and really failed.
  - **Print Label falls back to the on-screen label modal, not to `window.print()`** — the plain-text label is not a printable sheet, and someone whose QZ Tray is down still needs to read the AWB off the screen to write the docket. The read-only **Label** button is unchanged and still sits next to it.
  - **Verified.** `go build` / `go vet` / `node --check` clean; **`go test ./... -p 1` fully green** (including the finance-9500 test the notes warn can false-fail). **5 new Go tests** (`engines/qz_receipt_invoice_test.go`) covering column arithmetic, the amount-survives-clipping rule, ESC-POS-vs-label-language selection, the Paid-only guard, coded not-found, offer-discount arithmetic and the DRAFT stamp. Then driven **live over HTTP** on a scratch :8261 as `manager1`: all three job types role-resolved to the right printer and produced correct payloads (receipt 500.00 subtotal → 450.00 due after a 50 offer; shipping label emitted a real `^BCN` Code 128 of the AWB; invoice marked DRAFT), plus every error path (unknown job type, missing `document_ref`, missing document, unpaid cart). Finally **18/18 Playwright checks** against the real `index.html`+`app.js` with QZ absent, so every assertion exercised the fallback.

## Stage 32 — Interaction responsiveness ⏳ (opened 2026-08-04 from the user's report; 32.1 closed, 32.2 open)

User report, after using the deployed app: *"The interface is not at all smooth. I have to click many times. Then it is working. Hover is also not working. I have to click on arrow then it is showing permanently else it is going away."*

- [x] **32.1.1 The sidebar's hover "aim test" was structurally always-true — closed 2026-08-04.** Root cause of the whole hover complaint. `pointerAimingAtOpenFlyout()` decided whether a module row must be dwelt on for 140ms or 500ms before it may take the open menu, and it asked `flyoutPointerTrail.dx > 0 && r.left >= flyoutPointerTrail.x`. The flyout panel **always** sits to the right of the sidebar, so `r.left >= x` is true for essentially every pointer position in the nav; the whole decision therefore collapsed to `dx > 0`, measured **frame-to-frame**, which at 120Hz is a sub-pixel sample dominated by hand jitter. Result: hovering a module while another menu was open waited **500ms on roughly half of all approaches, at random**. Replaced with a real trajectory test — velocity sampled over a 90ms window, a 12px minimum travel to count as a deliberate reach, and the pointer's projected crossing point required to land inside the panel's **vertical** span (±24px) before the grace applies.
- [x] **32.1.2 The pending open re-evaluates instead of locking in — closed 2026-08-04.** The delay was chosen once at `pointerenter` and then ran to term: `container`'s `pointermove` handler was guarded by `!flyoutOpenTimer`, so while a timer was pending every subsequent move was a no-op. A pointer that had stopped aiming still served the full aim grace. Dwell is now measured from a `hoverStart` stamp and recomputed on every move, so the required wait only ever counts **down** — stop aiming and the menu opens on the next move.
- [x] **32.1.3 Open-timer ownership — closed 2026-08-04.** `cancelFlyoutOpen()` was global, so row B's `pointerleave` could cancel an open row C had already scheduled. It now takes an optional owner (`flyoutOpenTarget`) and leaves another row's pending open alone.
- [x] **32.1.4 Delays cut to what the gesture actually needs — closed 2026-08-04.** Switch 140 → **60ms** (below the ~100ms that reads as instant; it exists only to stop a fast sweep down the sidebar strobing every menu), aim grace 500 → **220ms**, hide 260 → **200ms**. The blanket dwell was doing the job the aim test was supposed to do, which is why it had to be so long.
- [x] **32.1.5 Interaction feedback decoupled from the layout duration — closed 2026-08-04.** Every hover state in the sheet ran on `transition: all var(--transition-speed)` = **250ms**, the duration meant for sidebar-width and panel slides. Hover feedback at 250ms reads as the UI lagging a beat behind the cursor. Added `--transition-fast: 0.11s` / `--transition-med: 0.16s` / `--ease-out`, and pointed `.menu-item`, `.submenu-item`, `.btn` and `.action-btn` at them with **named properties instead of `all`** (`all` was also animating the geometry — padding, border-width — on `.menu-item.active`).
- [x] **32.1.6 Press feedback added — closed 2026-08-04.** There was no `:active` state anywhere. A button that looks identical the instant it is pressed reads as "didn't register", which is precisely what makes a user click again — and on a submit a second click is a duplicate request, not a cosmetic issue. Added `:active` to `.btn` (1px depress), `.action-btn` (0.9 scale), `.menu-item`/`.submenu-item` (background), plus `user-select: none` and `-webkit-tap-highlight-color: transparent` on the nav rows and buttons so a double-click never selects the label text.
- [x] **32.1.7 Flyout entrance + reduced motion — closed 2026-08-04.** The panel appeared by flipping `display:none → block` with no motion while everything around it moved at 250ms; it now slides 6px in 160ms (`transform`/`opacity` only, so it cannot disturb the `scrollHeight` measurement `openFlyout()` takes immediately after). Closing stays instant. Added the sheet's first `prefers-reduced-motion` block.
- **Verified 2026-08-04, live in Chromium against the real `index.html`/`styles.css`/`app.js`** (harness serves `public/` statically and seeds an `erp_token`; `setupModuleFlyouts()` runs synchronously at the top of `init()`, before the first `await`, so the nav binds fully even with every API call 404ing). 12 assertions, 5 consecutive clean runs. The decisive pair, run against `HEAD` and against the fix:
  - *jittery approach, 6 runs* — **before: `[2, 81, 3, 445, 70, 477]`ms** (the randomness the user was feeling); **after: `[4, 1, 4, 2, 7, 4]`ms.**
  - *hover a module, wait a beat, then reach right for the menu* — **before: no menu at all** (leaving the row cancelled the pending open *and* scheduled the hide, so clicking the arrow was genuinely the only thing that worked — exactly the reported behaviour); **after: the menu is there.**
  - Also asserted: cold hover opens < 150ms; a fast sweep across 10 rows still opens ≤ 2 menus en route; crossing the 8px gap into the panel keeps it open; the diagonal reach to the item at the bottom of an 11-item flyout survives the trip and that item ends up `:hover`ed; leaving the nav closes within 400ms. A straight synthetic path down the sidebar has `dx == 0` and so **never trips the old bug** — reproducing it needed a jittering pointer, which is why this is worth keeping as a harness rather than a one-off check.
- [x] **32.1.8 The user was never running this code — `localhost:8080` is production, not the tree. Closed 2026-08-04.** The whole reason 32.1 "did not fix it": `Open-ERP.cmd` runs `ssh -N -L 8080:127.0.0.1:8080 root@139.59.17.16`, so the app the user tests is a **DigitalOcean droplet**, and it was still serving a **Stage-28-era build (2026-07-27)** — 589KB `app.js` vs the tree's 658KB, with `menu-flyout-bridge` **absent** entirely. - [x] **32.1.9 The "AllocationRule needs two clicks" report, root-caused and reproduced — closed 2026-08-04.** From the user's screen recording: the frame at 15.25s shows **Stock's flyout open under the pointer while the page and the highlighted row are HR** — a menu belonging to one module while the app sits on another. That is the pre-28.5 defect exactly: `hideTimer` was **per-container** but `closeSubmenus()` is **global**, so module A's already-armed 200ms timer fires after B's menu has opened and closes it; the menu vanishes from under the pointer and the click lands on the page behind it. - [x] **32.1.11 `deploy/deploy.ps1` bug found by using it — closed 2026-08-04.** Its remote script did a plain `source /etc/erp/erp.env`. That file is a systemd `EnvironmentFile` (bare `KEY=value`, no `export`), so `DATABASE_URL` stayed a shell variable and never reached `migrate.sh` as a child process, which then died on its own `${DATABASE_URL:?}` guard. - [ ] **32.3 Nightly backup cron is not installed on production — OPEN.** `/opt/erp/backups` was empty and `crontab -u erp -l` is empty, so before 2026-08-04 that droplet had **no backups at all**. `deploy/backup.sh` exists and works (it produced the pre-deploy dump); it just needs the cron line from its own header installed, plus a restore drill. [needs user go-ahead: retention period and whether backups should ship off-box]
- [ ] **32.5 MFA has no recovery path — a lost/replaced admin phone locks the tenant out of every HR/Admin screen. OPEN, found 2026-08-04.** Verified by reading the code, not assumed: the only MFA endpoints are `/auth/mfa/enroll`, `/activate`, `/verify` (`routes.go:115-117`), **there are no backup/recovery codes anywhere in the tree** (grep for `recovery_code`/`backup_code` returns nothing), and there is **no endpoint for one admin to reset another's MFA**. `handleMFAEnroll` is gated on `Resolved-Purpose == "mfa_enroll"`, a token `/api/v1/login` only issues to an account that is *not yet* enrolled — so an enrolled user **cannot re-enroll from inside the app**, i.e. there is no "move my authenticator to a new phone" flow. The only recovery is `cmd/reset_mfa` (host-shell + DB access), which on production means SSH to the droplet, and that box has **no Go toolchain**, so it needs a cross-compiled binary or a hand-run `UPDATE users SET mfa_enabled=false, mfa_secret=NULL`. With a single HR/Admin account on prod, that SSH key is the *only* way back in. Mitigations, cheapest first: (a) transfer the authenticator entry with the app's own export feature *before* switching phones — zero code, but only works while the old device still exists; (b) a second HR/Admin account enrolled on a different device, so a lost phone costs one login rather than all admin access; (c) the actual fix — issue single-use recovery codes at enrollment and accept one in place of a TOTP code at `/mfa/verify`. [needs design decision: (c) is the right fix but adds a credential to store and display-once UI — confirm before building]

And the login/MFA rate budget is **5 requests per minute per IP** (`rateLimitCategory`, `middleware.go:168`), which covers `/login`, `/mfa/verify` *and* `/mfa/activate` — four wrong codes in half a minute puts the next attempts into 429 regardless of correctness. IPv4 `127.0.0.1` and IPv6 `::1` are **separate buckets**, so a curl test can pass while the browser is still throttled.

## Stage 33 — Dialog viewport fit & responsive form layout ✅ (opened + closed 2026-08-04 from the user's screenshot; **not yet deployed**)

User report, with a screenshot of the New Location dialog: *"Nothing is visible here. So, set up. Make it more 2 column or 3 if required so it will be visible. All screen and config it should auto adjust with 100% to any percent 40% or whatever. If 120% also it should get auto adjusted."*

- [x] **33.1.1 Every dialog in the app could be taller than the screen with no way to scroll — closed 2026-08-04.** The real defect behind "nothing is visible". `.modal-container` had **no `max-height` and no scroll region**, and `body` is `overflow: hidden`. So a form taller than the viewport got centred by `.modal-overlay`'s flexbox and then clipped off **both** ends — the first fields *and* the Save/Cancel footer were unreachable, with nothing anywhere to scroll. The container is now a flex column bounded by `calc(100dvh - 40px)` (with a `vh` fallback line), the header and footer are `flex: 0 0 auto`, and `.modal-body` takes the overflow (`flex: 1 1 auto; min-height: 0; overflow-y: auto`). `min-height: 0` is the load-bearing part — without it a flex child refuses to shrink below its content and the container overflows again. Also added `padding: 20px 16px` to the overlay so the dialog can never touch the viewport edge.
- [x] **33.1.2 The `<form>` wrapper was swallowing the flex chain — closed 2026-08-04.** Found by the harness, not by reading: 33.1.1 alone still failed at ≤1280x720. In `index.html` most dialogs wrap body+footer in `<form>`, so the **form** is the container's flex child, not `.modal-body` — the form stayed a content-sized block, the body never received leftover height to scroll in, and the footer was clipped exactly as before. Fixed with `.modal-container > form { display: flex; flex-direction: column; flex: 1 1 auto; min-height: 0 }`, written as `> form` so the handful of JS-built modals that put `.modal-body` directly in the container are unaffected.
- [x] **33.1.3 The generic document form is a 1/2/3-column intrinsic grid — closed 2026-08-04.** `openDynamicModal()` (every master and document create/edit screen) is the one dialog with an unbounded field count — Item renders ~20, and one column made it taller than any screen. `#dynamic-modal-body` is now `grid-template-columns: repeat(auto-fit, minmax(min(240px, 100%), 1fr))`: **no breakpoints and no media queries** — the column count follows the width actually available, which is exactly what makes it zoom-proof (zoom only changes the CSS-pixel viewport, and both the grid and the `dvh` bound are recomputed from it). Scoped to `#dynamic-modal-body`, so the table/summary modals that share `.modal-body` are untouched.
- [x] **33.1.4 Wide dialog is opt-in above 4 fields; composite editors span the row — closed 2026-08-04.** A 3-field master in a 920px box would be two-thirds empty row, so `openDynamicModal` sets `.modal-container-wide` only above 4 fields; below that the dialog stays 520px and the 240px grid minimum yields one column on its own, i.e. **small masters look exactly as they did**. The JSONTable/JSONMap line editors (30.5.3) get `.form-group-wide` → `grid-column: 1 / -1`, since squeezing a multi-column table into a 240px track defeats the point. Column count itself stays the stylesheet's job; the field count is the only thing JS needed to know.
- [x] **33.1.5 Same fix applied to the second dialog system — closed 2026-08-04.** `.custom-dialog-box` (`showCustomAlert`/`showCustomConfirm`/`showApiError`/`showCustomPrompt`) had the identical structure and the identical bug: a long `showApiError` detail list clipped off-screen with its OK button unreachable. Given the same flex column, `dvh` bound, pinned header/footer and scrolling body. Verified with a 40-row error list.
- **Verified 2026-08-04 in Chromium, two harnesses, all cases passing.** (1) The real `styles.css` against the DOM `openDynamicModal` builds, at 8 viewport sizes standing in for zoom **40% → 300%** plus a deliberately short 1400x380 window: 3 columns down to 1097px, 2 at 768px, 1 at 520px; container inside the viewport and the **Save button reachable in every case**; body scrolls precisely when it needs to. Before the fix, the 120%/140%/200%/300%/short cases put Save *below* the viewport bottom (e.g. `save=[720,757]` in a 720px-tall window) with `scrolls=false`. (2) A regression pass on the **real `index.html`+`app.js`** served over HTTP at 3 sizes: `add-field`, `edit-prefix`, `add-label` and `bulk-import` all still measure `cols=1 display=flex w=520` — the grid rule leaked into nothing — and the long custom dialog scrolls with its footer on screen. No page errors.
- [x] **33.1.6 Cache-buster versions bumped — closed 2026-08-04.** `index.html` referenced `styles.css?v=14` / `app.js?v=20`; both files changed, so a browser holding the old query string would have served the **cached pre-fix files and shown no change at all** — including on production behind the tunnel. Now `?v=15` / `?v=20`. Note this also covers Stage 32.1's `app.js` edits, which never bumped it. **Any future change to either file must bump its `?v=`** or the fix ships invisibly.
