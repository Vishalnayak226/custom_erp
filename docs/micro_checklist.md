- [x] **26.1.1** Production hosting decision (provider, domain, TLS, secrets store) — **decided and formalised 2026-08-06** (user: "formalise the droplet"). The provider question turned out to be already settled in practice: a DigitalOcean droplet has been serving the real build, `systemd`-supervised, Go binary bound to `127.0.0.1`, `ufw` active, nightly encrypted backups. What this pass actually found and fixed was that the *formalisation* had never happened:
  - **`ENV=production` was never set.** All three gates it controls were therefore off: the seed-admin credential hard-stop (`engines/auth.go:331`), the non-UTF8 database hard-stop (`db/db.go:88`), and removal of the `/api/v1/debug/panic` route (`internal/server/routes.go:564`). Both hard-stop preconditions were **verified before flipping it** — `SHOW server_encoding` returned `UTF8`, and the absence of the `[SECURITY]` seed-password warning in the startup journal confirmed the admin password was already rotated — because either condition failing would have made the server refuse to boot. Applied with an automatic rollback guard; verified after: service active, `/api/v1/health` 200, `debug/panic` now **404**.
  - **Caddy was serving the stock Debian welcome page.** `/etc/caddy/Caddyfile` was still the packaged default — `root * /usr/share/caddy` + `file_server`, with `reverse_proxy localhost:8080` **commented out**. The repo's own `deploy/Caddyfile` had never been installed, so Caddy had been running and doing nothing while the app was reached solely through the SSH tunnel. Replaced with a new `deploy/Caddyfile.holding` (returns a blank 404 on `:80`), stock config backed up first.

That is strictly worse than the tunnel-only posture, so it was refused; `Caddyfile.holding` documents the reasoning inline so the next session doesn't "fix" it. New `deploy/enable_tls.sh <domain> <email>` does the whole switch in one command when a domain exists: validates the hostname/email, **checks DNS actually resolves to this box before touching anything** (a premature ACME run burns Let's Encrypt's weekly failed-authorization quota and can lock out the real attempt for days), `caddy validate`s the generated config, backs up the current one, and auto-rolls-back if the reload fails.

## Stage 31 — Silent printing (QZ Tray) 🚧 (opened 2026-08-03 from the user's marketplace-OMS print request; 31.1 built, live printer verification outstanding)

User request: *"For Myntra and other Marketplaces OMS, I want to crack QZ print automation"* + Myntra support's setup mail, clarified as **one-click print for all** — ERP documents *and* the marketplace documents channels supply. Scope answers given up front: drive both, self-signed/fully silent authorisation, support all printer types.

- [x] **31.1.1 The signing contract, verified from QZ's source — closed 2026-08-03.** A wrongly-signed call is rejected *silently* (QZ falls back to prompting per label), so this had to be established as fact, not inferred. `qz-tray.js` hashes the request and passes the **hash** to the backend, which makes both obvious backend implementations wrong. Settled from source: `qz/auth/Certificate.java:363` → `verifier.update(getBytesUtf8(sha256Hex(data)))` with `SHA512withRSA`, over `new JSONObject(message, {"call","params","timestamp"}).toString()` (`PrintSocketClient.java:218`). So: sign the **UTF-8 bytes of the lowercase hex digest**, key order `call,params,timestamp`. Also confirmed there is **no 2.1-vs-2.2 fork** to handle — the tray does its own hashing from the raw JSON, so both client generations agree. Ports `[8181,8282,8383,8484]` secure / `[8182,8283,8384,8485]` insecure; handshake is unsigned `getVersion` → certificate → signed calls.
- [x] **31.1.2 `engines/qz_print.go` — key material and signing — closed 2026-08-03.** RSA-2048 self-signed cert, `QZ_PRIVATE_KEY_PATH`/`QZ_CERTIFICATE_PATH` else auto-generated once into the OS per-user config dir — the same shape `channel_credentials.go` already uses, except it never `log.Fatalf`s: printing is optional and must not take the server down. **The sign endpoint is not a blind oracle** — it accepts exactly one SHA-256 hex digest (`^[0-9a-f]{64}$`) and nothing else, so it cannot be talked into signing an attacker-chosen document, which QZ's own reference backends allow.
- [x] **31.1.3 `Printer` Master extended rather than a new registry — closed 2026-08-03.** Six fields added (`qz_printer_name`, `print_role`, `printer_language`, `label_width_mm`, `label_height_mm`, `dpi`) via `db/migrations_stage31_1_qz_print.sql`, so the whole config screen comes free from the generic Master machinery. `print_role` is what makes it one-click — the server resolves role → printer so no operator picks one per job. Migration also creates `print_job_log` and **catches up existing tenant schemas** with a `DO` block, the failure mode Stage 30.2.2 existed to clean up. Routes share the existing `stickers` module key deliberately; a new key would 403 every existing tenant (the SAAS-0191 trap from 30.7).
- [x] **31.1.4 `public/qz-print.js` — vanilla client, no dependency — closed 2026-08-03.** ~330 lines vs the official ~150KB (which carries a promise shim, its own SHA-256 and remote-relay logic unused here). **A pure-JS SHA-256 fallback is mandatory, not defensive**: `crypto.subtle` is absent outside a secure context, and a packing bench on `http://192.168.x.x` is exactly that. Verified against Node's `crypto` — 8 vectors + 300 random-length fuzz cases, specifically across the 55/56/64-byte padding boundaries.
- [x] **31.1.5 Payloads: raw ZPL/TSPL/ESC-POS or PDF/HTML per printer — closed 2026-08-03.** `engines/qz_payload.go`. **Marketplace PDFs pass through byte-for-byte** — re-rendering a courier's label risks altering a barcode they scan — with 4x6 sizing applied as driver options instead. ERP-native shipping labels *are* generated and gained a real Code 128 AWB symbol on thermal, which `engines/marketplace.go`'s `GenerateShippingLabel` explicitly could not do ("prints text, not a real scannable symbology/PDF"). Stickers route through the existing `engines.PrintStickers`, so SKU validation, the DEVICE-0298 check and `sticker_print_log` are unchanged.
- [x] **31.1.6 UI + graceful degradation — closed 2026-08-03.** Print Setup panel on Sticker Printing: connection status, **Detect Printers** (the OS names must match verbatim — `ZDesigner ZD220-203dpi ZPL`, not "Zebra ZD220"), Test Print, and a file picker that prints any marketplace label/invoice. If QZ isn't running, `qzTryPrint` returns false and every caller falls back to the existing `@media print` sheet; non-thermal sticker printers take the same route via the server's `fallback: "browser"` reply. Nobody is blocked because the bridge is down.
- [x] **31.1.7 Rollout tooling + operator guide — closed 2026-08-03.** `cmd/qzcert` exports `override.crt` (public cert only; the private key never leaves the server) and prints the per-OS install paths. `docs/guides/QZ_PRINTING_SETUP.md` covers Java/QZ install, the certificate, **Chrome's Local Network Access gate** (the step Myntra's own mail spends most of its length on, and the usual cause of "the print button does nothing"), printer-language selection, and a troubleshooting table keyed to the actual error strings.
- **Verified**: `go build ./...`, `go vet ./...`, `node --check` clean. 7 new Go tests green — signature validates under the reproduced `Certificate.java` algorithm; **signing the raw digest bytes is asserted to fail** (the most likely future regression); non-hash input refused; deterministic signing; ZPL escaping; payload shapes. Client then run end-to-end against a **mock QZ Tray** implementing that verification with the real generated key: 15 assertions over handshake order, message shape, the exact signed string and key order, print params, plus a tampered-signature negative control.
- [ ] **31.1.8 Live verification against a real QZ Tray and a real printer — OPEN.** Not done, and cannot be done from this machine: **no PostgreSQL and no Docker are running here**, so the DB-backed endpoints (`/printers`, `/payload`, `/log`) were never exercised over HTTP, the migration was never applied to a real database, and no physical print was produced. What this leaves genuinely unproven: (a) the migration SQL executing — in particular the nested `$f$` dollar-quoting inside the `DO $$` catch-up block; (b) the ZPL actually rendering correctly on a 203dpi 4x6 roll; (c) the real tray accepting our certificate as `override.crt`. The signing chain itself is proven and is the part that could not be checked by eye.
- [x] **31.1.9 Wire one-click print into the remaining screens — closed 2026-08-05.** All three landed: **Print Label** on the logistics-booking row, **POS receipt via ESC-POS** at checkout, and **Print** on the Sales Invoice row. Two new job types (`Receipt`, `Invoice`) with server-side payload builders, plus the frontend wiring and its fallbacks. `print_role` already offered both names (the Stage 31.1 migration seeded `Shipping Label,Invoice,Sticker,Receipt,General`), so **no migration was needed** — a Printer record just needs `Default For` set.
  - **Both new documents are re-read server-side from their stored document, not taken from the browser.** `BuildReceiptPayload` reads the `POSCart`, `BuildInvoicePayload` the `SalesInvoice`. That is what makes a reprint honest — a receipt printed an hour later shows what was actually rung up — and it means a tampered client cannot print a receipt for a bill that never existed. `fetchPrintableDocument` is a deliberately separate small reader rather than a call into `PostSalesInvoice`/`FinalizePOSCheckout`: those sit inside write paths (`FOR UPDATE`, "only a Draft may be posted") that a print has no business running.
  - **Only a `Paid` cart prints a receipt** (`GLOBAL-0019`, 422). A Pending Approval cart is money not yet collected and a Failed one is a sale that did not happen; a printed receipt is what a customer walks out with, so this refuses rather than printing with a caveat. An **invoice prints at any status** on purpose — a Draft invoice is a legitimate proforma — but is stamped `DRAFT` so it cannot be mistaken for a posted one.
  - **`isESCPOS` is deliberately narrower than the existing `isRawLanguage`.** ZPL and TSPL are label languages with no concept of a continuous feed, so a receipt emitted as raw commands to a ZPL unit comes out blank. Only ESC-POS gets commands; every other language (PDF/HTML/ZPL/unset) gets rasterisable HTML through the OS driver. Do not "simplify" this back to `isRawLanguage`.
  - **`escposColumns` defaults an unset `label_width_mm` to 42 columns (80mm roll).** A 58mm till needs `label_width_mm = 58` on its Printer record or lines are laid out too wide. Every line is clipped to the column count and `escposRow` clips the *description*, never the amount — a receipt is checked on its numbers.
  - **Real bug found and fixed in the existing browser receipt**: `printPOSReceipt` never deducted `offer_discount`. Checkout returns `amount_due = sale_total - loyalty_discount - offer_discount`, so any sale with a Stage 30.7 offer applied printed a total **higher than the cash actually collected**. Now takes a 7th defaulted `offerDiscount` argument and prints Subtotal / Offer discount / Loyalty lines. The stored `applied_offers` are also named on the ESC-POS receipt, which is what the comment on `handlers_pim_pos_finance.go`'s `storedPayload["applied_offers"]` asked for in the first place.
  - **Second real bug fixed in the same area**: `#receipt-print-area` had **no on-screen `display: none`** — only the `@media print` block ever hid it — so after a POS receipt printed, its markup stayed rendered at the bottom of the live page until the next navigation. `styles.css` now hides all three print areas on screen (`#sticker-print-area` always did; the receipt one never has).
  - **`qzTryPrint` gained a `quiet` option, and the three new call sites use it.** "No Printer record is Default For Receipt" is the *normal* state of a tenant that has not set QZ up — without `quiet` a cashier would get a `DEVICE-0298` modal on every single sale before the browser sheet appeared. Quiet suppresses the payload-preparation dialog and the unmapped-printer dialog (both `console.debug`'d instead) and falls through. A failure at the tray itself stays loud in every case: that one means printing was really attempted and really failed.
  - **Print Label falls back to the on-screen label modal, not to `window.print()`** — the plain-text label is not a printable sheet, and someone whose QZ Tray is down still needs to read the AWB off the screen to write the docket. The read-only **Label** button is unchanged and still sits next to it.
  - **Verified.** `go build` / `go vet` / `node --check` clean; **`go test ./... -p 1` fully green** (including the finance-9500 test the notes warn can false-fail). **5 new Go tests** (`engines/qz_receipt_invoice_test.go`) covering column arithmetic, the amount-survives-clipping rule, ESC-POS-vs-label-language selection, the Paid-only guard, coded not-found, offer-discount arithmetic and the DRAFT stamp. Then driven **live over HTTP** on a scratch :8261 as `manager1`: all three job types role-resolved to the right printer and produced correct payloads (receipt 500.00 subtotal → 450.00 due after a 50 offer; shipping label emitted a real `^BCN` Code 128 of the AWB; invoice marked DRAFT), plus every error path (unknown job type, missing `document_ref`, missing document, unpaid cart). Finally **18/18 Playwright checks** against the real `index.html`+`app.js` with QZ absent, so every assertion exercised the fallback.

## Stage 34 — Market intelligence / competitor pricing ⏳ (opened 2026-08-06; 34.1-34.3 built 2026-08-07, 34.4-34.6 still gated)

**Source:** [docs/specs/market_intelligence_reference.md](specs/market_intelligence_reference.md), the knowledge kept from the retired OmniCore/"Buying Catalog" Python project (see `project_ledger.md` §81). **Nothing in this Stage is approved work** — it is the buildable shape of the one genuinely net-new concept that project held, written down so the analysis isn't repeated. `engines/marketplace.go` covers courier serviceability, labels/manifests, delivery/RTO and settlement reconciliation; it does **not** do competitor-price or catalog harvesting.

**The constraint that shapes the whole Stage.** `go.mod` carries exactly two dependencies (`lib/pq`, `x/crypto`) and there is no vendor directory, so **there is no HTML parser available**. Anything needing DOM traversal means a new dependency, and a headless browser (the retired project used Playwright) means a new *runtime*, not just a library — both against `CLAUDE.md`'s first principle. That single fact is what splits 34.1-34.3 (buildable now, stdlib only) from 34.4-34.5 (gated).

**Sequencing:** 34.6 is the real gate. Do not start 34.4 before it is answered, and 34.1-34.3 are worth doing regardless of how it lands, because they are how the data gets *used* no matter where it comes from.

### 34.1-34.3 — buildable now, zero new dependencies

- [x] **34.1** `CompetitorPrice` doctype + CSV ingestion — built 2026-08-07. `db/migrations_stage34_1_competitor_price.sql`: 12 fields (`code`, `our_item` Link→Item, `competitor_product`, `competitor_sku`, `platform` Select, `competitor_price`, `mrp`, `rating`, `review_count`, `observed_at` Date, `source_url`, `status`), `role_permissions` for HR/Admin (full) and Store Manager (read/create/update), and the standard backfill loop over already-provisioned tenant schemas.   - **Found and fixed a real bug affecting 89 doctypes, not just this one.** `GenerateCSVTemplate` (`import.go:377`) deliberately omits `id`/`status` from the header row it emits, and `ValidateDocument` (`doctype.go:314`) skips the mandatory check for those same two system fields — but `missingMandatoryColumns` (`import.go:137`) did neither, so **any** doctype declaring a mandatory `status` field rejected its own generated template with `DATAIM-0164 "missing mandatory column(s): status"`. - [x] **34.2** Price-gap report via `RegisterReport` — built 2026-08-07 as `competitor-price-gap` (Category "Sales") in `engines/market_intelligence.go`. Live-verified over HTTP end to end: CSV import → catalog listing → run → correct cheapest-wins pick → correct gap math (599 vs 499 → ₹100, 20.04%, "Above") → platform filter changing which competitor row wins.

### 34.4-34.5 — gated, do not start before 34.6

- [ ] **34.4** JSON-endpoint harvester, **stdlib only**. Adopt the retired project's two-phase shape: harvest raw responses to disk under a bounded worker pool, skip any file already present and non-trivial (free resumability *and* cache), then parse offline in a second pass so a parser bug costs no re-fetch and no re-ban. **[needs user decision — gated on 34.6]**
- [ ] **34.5** DOM-based extraction for Amazon/Flipkart/Meesho/eBay. **Recommend NOT building.** It needs an HTML parser dependency at minimum and realistically a headless browser (all four sites are JS-rendered and actively anti-bot), which is a new runtime on a 454MB droplet. - [ ] **34.6** Legal/ToS position on automated collection.
