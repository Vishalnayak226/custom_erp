## Stage 31 — Silent printing (QZ Tray) 🚧 (opened 2026-08-03 from the user's marketplace-OMS print request; 31.1 built, live printer verification outstanding)

- [x] **31.1.1 The signing contract, verified from QZ's source — closed 2026-08-03.** A wrongly-signed call is rejected *silently* (QZ falls back to prompting per label), so this had to be established as fact, not inferred. `qz-tray.js` hashes the request and passes the **hash** to the backend, which makes both obvious backend implementations wrong. Settled from source: `qz/auth/Certificate.java:363` → `verifier.update(getBytesUtf8(sha256Hex(data)))` with `SHA512withRSA`, over `new JSONObject(message, {"call","params","timestamp"}).toString()` (`PrintSocketClient.java:218`). So: sign the **UTF-8 bytes of the lowercase hex digest**, key order `call,params,timestamp`. Also confirmed there is **no 2.1-vs-2.2 fork** to handle — the tray does its own hashing from the raw JSON, so both client generations agree. Ports `[8181,8282,8383,8484]` secure / `[8182,8283,8384,8485]` insecure; handshake is unsigned `getVersion` → certificate → signed calls.
- [x] **31.1.2 `engines/qz_print.go` — key material and signing — closed 2026-08-03.** RSA-2048 self-signed cert, `QZ_PRIVATE_KEY_PATH`/`QZ_CERTIFICATE_PATH` else auto-generated once into the OS per-user config dir — the same shape `channel_credentials.go` already uses, except it never `log.Fatalf`s: printing is optional and must not take the server down. **The sign endpoint is not a blind oracle** — it accepts exactly one SHA-256 hex digest (`^[0-9a-f]{64}$`) and nothing else, so it cannot be talked into signing an attacker-chosen document, which QZ's own reference backends allow.

## Stage 41 — User-reported batch: schema edit, sticky headers, country/phone, setup guidance, POS location ✅ (opened + built 2026-08-10)

Five gaps the user reported directly. **Numbered 41, not 34.4** — 34.4 is the *gated* JSON-endpoint harvester in Stage 34, blocked behind 34.6's legal/ToS decision, and reusing that number would have read as the gate being crossed. Same reasoning Stage 40 gives for not being numbered 35.

- [x] **41.1** **Database Schema Design had no Edit.** `SaveFieldDefinition` is create-only by design (META-0201 treats a re-submitted fieldname as a collision, not an edit), so the only way to fix a typo'd label or a wrong fieldtype was delete-and-recreate — which discards that field's stored data on every existing document. Added `UpdateFieldDefinition` (addressed by row id, so the *fieldname itself* is editable) + `PUT /api/v1/meta/{doctype}/fields/{id}`, keeping both guards: META-0197 unsupported fieldtype, META-0201 rename-onto-another-field's-name (excluding the row's own id, so "save without renaming" works). A zero-row UPDATE is reported rather than silently succeeding.
  - **Found an orphan.** `#add-field-modal` had been sitting in `index.html` since it was written with **nothing in `app.js` referencing it** — the screen used a chain of six `showCustomPrompt` dialogs, each losing everything typed so far if cancelled, with fieldtype typed free-hand against a list the server would then reject. Its inputs also carried `class="form-control"`, a class this stylesheet **does not define**, so it would have rendered unstyled had anything opened it. Wired up for both verbs (hidden `add-field-id`: empty = POST, set = PUT), classes corrected to `form-input`/`form-select`, errors shown inline so a bad value doesn't discard the form. New fields now default to `max(display_order)+1` instead of the old hardcoded 10, so several added fields no longer collide on one position. A rename shows an explicit warning that data under the old key stops being displayed (it is not deleted; renaming back restores it).
- [x] **41.2** **Scrolled rows painted over the frozen table header.** `styles.css` had `position: sticky` on `thead` with a comment concluding this was an unfixable cross-browser rough edge, listing four things tried (opaque `td` backgrounds, `border-collapse: separate`, a forced compositor layer, `isolation: isolate`). The diagnosis was right and the conclusion wrong: CSS2.1 §17.5.1 has the browser paint table backgrounds in table-layer order, and a **row group** stays in that layer whatever its `position` is — which is why all four attempts failed, they were fighting the paint order rather than leaving it. Moving `position: sticky` down one level onto the **`<th>` cells** takes them out of the table layer and into the positioned-descendants layer, which paints above every in-flow `<td>`. `thead` keeps its own sticky/z-index for non-`<th>` header decoration; `tbody th` is reset to `static` so a future row-header can't freeze at the top of the page. `box-shadow: inset 0 -1px 0` alongside the border, because with `border-collapse: separate` the border alone leaves a hairline of the row beneath showing at fractional scroll offsets. Verified live at `scrollTop: 260` on a 103-row table: all three sample points inside the header band hit `TH`.
- [x] **41.3** **Country setup → phone rules, and OMS cleanup.** New `engines/phone.go`: a 54-country table (dial code, trunk prefix, accepted national lengths, example) and `NormalizePhone`, plus the `localization.default_country` setting registered from that same table so adding a country is one row and nothing else. Deliberately no dependency — a libphonenumber port is thousands of rules and a monthly metadata refresh; what is needed here is a table.
  - **The two concerns are separated on purpose.** *Cleaning* is unconditional and never rejects: spaces, hyphens, dots, parens, unicode dashes stripped; `+CC` and the `00CC` exit code resolved; trunk prefix dropped. *Validation* is a policy the caller applies to the cleaned result. Wired into `ValidateDocument` — the one choke point every document write already passes through — so all ~19 phone fields in the schema are cleaned with no per-screen wiring, detected by fieldname (`phone`/`mobile`/`whatsapp`/`telephone`/…) rather than a new fieldtype that would need a migration per field.
  - **Masters are strict, orders are not.** Customer keeps MASTER-0051 but against the tenant's configured country instead of the old India-only `^[6-9][0-9]{9}$`, and the message now names the shape and an example. `CreateSalesOrder` cleans and tags but **never rejects or holds** over a phone number — the three hold codes are about whether an order can be *fulfilled*, and a contact number cannot answer that, so making it a fourth gate would only block real revenue. New `SalesOrder.customer_phone` + `customer_country`; `CreateSalesOrder`'s seven positional strings became `SalesOrderInput` rather than growing an eighth.
  - **Two guards stop a valid number being eaten**: a dial code is only stripped when the remainder is a valid length (so a real 10-digit Indian number starting "91" survives), same for the trunk prefix. Both are pinned by tests.
  - **A real ordering bug, found in live verification and fixed.** A `+1 212 555 1234` saved on an India tenant was stored correctly as `2125551234` but tagged `phone_country: IN`. The cleaning pass had already stripped the `+1`, and the validation pass then re-derived the country from digits that no longer carried it — a US and an Indian 10-digit number being indistinguishable at that point. The country is now captured in the pass that can still see it, written to a `<field>_country` companion **only where the doctype declares one** (so declaring the field is the entire opt-in). Live-verified: US/AE/GB numbers now tag correctly.
  - **A collision with Stage 40.2's field formats, fixed at the shared level.** `phone_country` holds `"US"`, and substring matching saw "phone" in the name — so the server rejected a value it had just written itself. Added `IsDerivedCompanionField` (suffixes `_country`, `_status`, `_verified`, …), used by both `DetectFieldFormat` and `IsPhoneField` so the two cannot disagree, and served to the frontend alongside the format tokens for the same reason. The generic record form now renders such fields read-only with "Set automatically on save".
  - Also fixed: `rawSettingForSchema` **panicked** on a nil `db.DB` (`database/sql` panics rather than erroring), despite its own contract saying a config read must never crash a request path. Found because a pure-function unit test consulted a setting.
- [x] **41.4** **"Tell me what isn't set up, from where I am."** `GET /api/v1/setup/status` returns live/active record counts for every **Master** doctype in one query (derived from `doctype_meta`, so a record type added tomorrow is covered with no code change). Three surfaces, one vocabulary (`SETUP_MSG` — three sentences, one place):
  - **Per-field hint**, attached inside `attachLinkTypeahead` — the single door all ~45 pickers already go through, so every screen gets it including ones written later. **Loud when blocking, quiet otherwise**: an empty target list shows the hint permanently (the user genuinely cannot proceed); a populated one shows "Can't find the X you need? Add a X" *only while the field is focused*, so a form with eight pickers isn't eight permanent lines of advice. Never a dialog, never steals focus, never needs dismissing.
  - **Per-screen banner**, attached in `renderView` (the other single door), driven by `VIEW_SETUP_PREREQS`. Dismissal is **sessionStorage, not localStorage** — deliberate: a permanent dismissal means a user who clicks × once never learns the module is unconfigured again, which is how a half-set-up ERP stays half set up.
  - **Permission-aware throughout.** A user who cannot create the record never sees a link that would refuse them; they get the standard "You do not have access to add one — ask your administrator to set up X", styled muted rather than amber because there is nothing for them to fix. Live-verified as `manager1`/Store Manager on the HR screen.
  - **Real deep links** make "open in a new tab" work: `#/setup/<Doctype>` and `#/view/<view>`, parsed at boot ahead of the restore-last-view path, plus a `hashchange` listener and `history.replaceState` from `saveNavState` so the URL always describes the screen. Every hint ends with a real `<a href>` (so ctrl/middle-click and the browser's own context menu work) plus an explicit ⧉ `target="_blank"` affordance. Verified: a new tab opened on `#/setup/Vendor` lands on Vendors.
  - A picker whose target is a **transaction** gets no hint at all — "set up Purchase Orders" is not advice. Only Masters are in the status map, and an unknown doctype counts as set-up, so a slow or failed load produces no hint rather than a wrong one.
- [x] **41.5** **POS showed a location code where the cashier needs a name.** Split into a visible search box (Name, searchable by name/code/short code) and a hidden input carrying the **code**, because every downstream call — session open/close, availability, cart number, receipt — keys off it; the `change` event is dispatched on the hidden input so all existing readers needed no change. Free typing still resolves on blur (exact code, short code or name), and text that resolves to nothing clears the value rather than submitting a code that does not exist — the failure the old free-text field had. Built as a generic `attachCodeNamePicker` since 15 other screens pick a location. New **optional** `Location.short_code`, explicitly not a second identity (nothing keys off it). The Location picker label now leads with the name, de-duplicating when name equals code so a location whose name was never filled in reads "HO", not "HO — HO".
