### Phase 26.1 — Production-Like Environment
See `docs/operations/go_live_decisions.md` for the decision worksheet + execution steps for every open item in this Phase and Phase 26.2/26.4/26.11 below.
*Some items in this section are closed and archived — see [docs/archive/micro_checklist_closed_stages.md](archive/micro_checklist_closed_stages.md).*

- [ ] **26.1.3b** Activate the Cloudflare edge WAF — managed rules, L7 DDoS absorption and bot controls. The domain and zone now exist (`wholeops.in`, 2026-08-14), so the external prerequisite is met; both records are still grey-cloud.
  - **⚠️ Correction (2026-08-15): "pure activation" was wrong, and the reason is worth keeping.** The plan of record was orange-cloud + CIDRs in two places + lock the origin. That combination **breaks Let's Encrypt renewal on this box**: once the origin firewall admits only Cloudflare, ACME cannot reach it — TLS-ALPN-01 cannot work through a proxy that terminates TLS, and HTTP-01 through the Cloudflare proxy is documented as unreliable. Nothing would have failed on the day; `app.wholeops.in`'s certificate would simply have stopped renewing and expired on **2026-11-12**, with the per-tenant on-demand path breaking sooner. DNS-01 is the usual escape and is refused here for the reason 26.1.3a already gave: it needs a provider plugin, therefore `xcaddy`, therefore a custom Caddy binary to keep patched.
  - **Resolution (user decision, 2026-08-15): a Cloudflare Origin CA certificate** — free, 15-year, wildcard, issued by Cloudflare and trusted only by Cloudflare, which is exactly the CF↔origin hop. No ACME, no plugin, no renewal, and it is what makes a fully locked-down origin possible rather than merely aspirational.
  - **Repository work for this is DONE (2026-08-15) and was not previously counted:** `deploy/enable_tls.sh` gained a `--cloudflare --origin-cert --origin-key` mode and `deploy/Caddyfile` was parameterised so **one** file describes both postures instead of two files drifting. `--cloudflare` fetches Cloudflare's published CIDRs at install time (never hardcoded — a stale list silently mis-attributes client IPs), **fails closed if the fetch fails** rather than installing a partial trust list, writes them into *both* Caddy's `trusted_proxies` (with `trusted_proxies_strict`) *and* `TRUSTED_PROXY_CIDRS` in `/etc/erp/erp.env`, and restarts the app. One command owns both halves because their drift is silent: an unlisted edge node is mistaken for the client and every visitor collapses into one rate-limit bucket. It also **inverts the DNS pre-flight check** instead of skipping it — in `--cloudflare` mode the name must resolve *into* a Cloudflare range, because installing an Origin CA certificate while the record is still grey-cloud serves browsers a certificate only Cloudflare trusts and takes the site down.
  - **Still open — the parts that are genuinely portal-side:** orange-cloud both records, SSL/TLS mode → Full (strict), generate the Origin CA certificate, enable the free managed WAF ruleset + Bot Fight Mode + Authenticated Origin Pulls, a rate-limiting rule on `/api/v1/login`, a cache-bypass rule (Cloudflare caches `.js`/`.css` by default and `public/app.js` has no content hash in its name, so a deploy would otherwise serve stale JS), and restricting inbound 80/443 in the **DigitalOcean cloud firewall** — not just `ufw`, which was never what was blocking traffic here (44.9).

- [ ] **31.1.9 Replace QZ Tray with our own lightweight agent — core built and proven 2026-10-04; pixel paths + hardware verification open.** Opened from *"Can we build our own QZ tray?"*. **Research outcome:** the licensing fear the QZ-alternative vendors market against doesn't apply to us (upstream is LGPL-2.1, commercial use free; the $749/$3,499 tiers buy support + a QZ-root-chained cert we don't need, since `cmd/qzcert` + `override.crt` already gives free silent printing). None of the four surveyed alternatives (XP_PRINT, BrioLabel, electron-hiprint, JSPrintManager) are adoptable — each swaps the Java runtime for a Node/Electron runtime, a closed binary, or a protocol that would break `public/qz-print.js`. **First attempt** was a rebranded source build of `qzind/tray` with install-time provisioning; it worked (real installer produced, all 6 provisioning steps `[SUCCESS]`) but came out at **138.5MB installer / 226MB installed**, failing CLAUDE.md's lightweight principle — so it was scrapped and its ~2.3GB toolchain removed. **Current approach:** a clean-room **Go** agent at `../PrintBridge/agent/` implementing QZ's wire protocol exactly, so `public/qz-print.js` needs **zero changes**. **6.6MB single binary, no runtime, no dependencies, no LGPL obligation** (protocols aren't copyrightable; no QZ source used). **Proven end-to-end on this machine:** hand-written RFC 6455 WebSocket server; signature verification against the same contract `engines/qz_print.go` signs (9/9 protocol tests incl. *signed-call-before-certificate refused* and *tampered-signature rejected*); real Win32 `EnumPrinters` discovery with correct default detection; and **raw ZPL printing verified byte-exact — 120 bytes sent, 120 bytes arrived at a real Windows print queue, SHA-256 identical** (tested via a temporary Generic/Text-Only printer on a FILE: port, removed afterwards). **Open:** (a) **pixel paths (PDF/HTML/image) not written yet** — designed to call the OS renderer (`Windows.Data.Pdf`/WebView2) so they add ~0MB; they currently return a clear error rather than silently printing nothing, so the ERP's marketplace-PDF and A4-invoice paths do NOT work on this agent yet; (b) USB/HID/serial, file comms, status listeners, tray UI, installer, `wss://` all still to build; No ERP code changed. Marketplace-panel printing is a separate workstream (user, 2026-10-04) but still in scope.

## Stage 34 — Market intelligence / competitor pricing ⏳ (opened 2026-08-06; 34.1-34.3 built 2026-08-07, 34.4-34.6 still gated)

**Source:** [docs/specs/market_intelligence_reference.md](specs/market_intelligence_reference.md), the knowledge kept from the retired OmniCore/"Buying Catalog" Python project (see `project_ledger.md` §81). **Nothing in this Stage is approved work** — it is the buildable shape of the one genuinely net-new concept that project held, written down so the analysis isn't repeated. `engines/marketplace.go` covers courier serviceability, labels/manifests, delivery/RTO and settlement reconciliation; it does **not** do competitor-price or catalog harvesting.

**The constraint that shapes the whole Stage.** `go.mod` carries exactly two dependencies (`lib/pq`, `x/crypto`) and there is no vendor directory, so **there is no HTML parser available**. Anything needing DOM traversal means a new dependency, and a headless browser (the retired project used Playwright) means a new *runtime*, not just a library — both against `CLAUDE.md`'s first principle. That single fact is what splits 34.1-34.3 (buildable now, stdlib only) from 34.4-34.5 (gated).

**Sequencing:** 34.6 is the real gate. Do not start 34.4 before it is answered, and 34.1-34.3 are worth doing regardless of how it lands, because they are how the data gets *used* no matter where it comes from.

### 34.4-34.5 — gated, do not start before 34.6

- [ ] **34.4** JSON-endpoint harvester, **stdlib only**. This is feasible precisely because of the reference doc's headline finding: **Myntra ships its whole search result set as an embedded `window.__myx` JSON blob** (fallback `window.__m_initial_state`), so `net/http` + `regexp` + `encoding/json` are sufficient — **no browser and no HTML parser**. Adopt the retired project's two-phase shape: harvest raw responses to disk under a bounded worker pool, skip any file already present and non-trivial (free resumability *and* cache), then parse offline in a second pass so a parser bug costs no re-fetch and no re-ban. **[needs user decision — gated on 34.6]**
- [ ] **34.5** DOM-based extraction for Amazon/Flipkart/Meesho/eBay. **Recommend NOT building.** It needs an HTML parser dependency at minimum and realistically a headless browser (all four sites are JS-rendered and actively anti-bot), which is a new runtime on a 454MB droplet. It is also the part that rots fastest — the retired project's own final commit was "Fix: Myntra scrapping logic", and its Flipkart parser was already dead code by the time it was abandoned. If competitor coverage beyond a JSON-endpoint source is genuinely needed, a **paid pricing-data API** is the lighter answer than owning scrapers. **[needs design decision: buy vs build vs skip]**

### 34.6 — the gate

- [ ] **34.6** Legal/ToS position on automated collection. Marketplace terms generally prohibit scraping, and this is a **multi-tenant SaaS** — harvesting on tenants' behalf carries a different risk profile than a single merchant scraping for their own buying decisions, which is what the retired project was. Needs an explicit answer on: which sources are acceptable, whether `robots.txt` is to be honoured, request-rate ceilings, and whether harvested competitor data may be retained per-tenant or only shown transiently. **[needs user input — this is a business/legal decision, not an engineering one, and 34.4/34.5 stay blocked until it lands]**

## Stage 49 — Evidence-driven maximum-security program ⏳ (planned 2026-09-03; ≈40-60 sessions, continuous release gate)

**North-star, not a marketing claim:** “most secure in the world” is not an objectively provable permanent state. The product goal is the strongest practical, independently evidenced security posture for each supported deployment and industry configuration. Never claim “unhackable,” universally secure, certified or compliant. Publish the exact scope, release, configuration, controls tested, residual risks, exceptions, assessor and expiry behind every assurance statement.

**Security constitution:** secure by default; deny and fail closed; least privilege; explicit tenant/entity/location/owner scope; server-authoritative business decisions; one durable outcome per command; no shared or hidden support access; no hard-coded/default credential; no secret or sensitive payload in source, URL, client storage, ordinary log or documentation; no control silently disabled to improve speed; no security-through-obscurity; no production claim without prevention, detection, response and recovery evidence. A security control that operators cannot understand, users route around, or the team cannot patch is not complete.

**Dependency and ownership rule:** Stage 49 does not reopen or duplicate work. **47.0-47.7** remain the P0 stop-ship remediation; **47.8** owns browser/session containment; **47.11** owns bounded request/worker/side-effect safety; **47.16** owns India-first control implementation; **47.17** owns reference-journey release evidence; **48.6** owns the normative security/privacy/legal documents; existing **20.5/26.11.1** own the external penetration-test engagement; **38.2d** owns OAuth2 client credentials. Stage 49 turns those controls into one threat-led security system and adds the missing platform, SDLC, detection, recovery and continuous-assurance gates. Security, privacy, infrastructure, product, finance/control, data, SRE and qualified legal/audit owners approve their domains; an AI/developer may draft and test but cannot self-certify them.

**Lightweight security rule:** retain one Go application plus PostgreSQL and the vanilla-JS client. No mandatory WAF appliance, service mesh, SIEM cluster, secrets platform, message broker, policy engine, antivirus daemon, Node toolchain or security sidecar merely to obtain a checkbox. Prefer compile-time route contracts, shared middleware, PostgreSQL constraints/transactions, OS/reverse-proxy controls, bounded structured events and optional export adapters. A new dependency/service requires 47.18.4 evidence and an ADR. Every 49.x item records binary/static-byte, cold-start, request CPU/latency, idle/peak RSS, DB/index/WAL/log/backup growth and operator burden. Security evidence obeys approved retention/legal holds and may not recreate the audit-log space failure Stage 47 found.

**Priority rule:** 49.S0 and the applicable Stage 47 P0 items are release-blocking. 49.S1-S3 must close before an internet-facing multi-tenant Production claim. 49.S4 must close before the corresponding enterprise, regulated or contractual assurance claim. Existing module work may continue only when it does not alter the same security boundary without updating its threat model and tests.

bypasses the multi-tenancy engine already built. Hosting many clients is the goal; separate
instances are not the mechanism. A contractual physical-isolation requirement from a single large
client is the one legitimate exception, and is a priced premium tier, not the default.
