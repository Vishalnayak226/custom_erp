# GST and Companies Act record controls

Stage 47.16.4. What this product does to keep an Indian business's tax invoices and books as the law expects them kept: invoices that cannot be quietly changed, reversals that leave their own entry, closed periods that stay closed, an edit log, retention and legal hold, and e-invoice / e-way bill applicability with the IRP's evidence.

Each row names the place the control is enforced and the test that proves it. A row with no test says **Gap**. `TestStage47164ControlMapNamesLiveTests` fails if a named test stops existing or a row loses both.

Live IRP / GSP / e-way credential work is not repeated here. It stays with tracker items 20.30, 20.31, 26.2.3 and 26.2.4.

This is an engineering map, not legal advice. Whether a control is enough for a particular client is decided with that client's auditor.

## Gaps (each needs a decision before it is built)

- **G1 - The edit log on every tenant.** Every tenant should get old and new values for each change, as `tenant_default` already does. The trigger function writes straight into `tenant_default.audit_logs`, so it cannot simply be attached to another schema. It needs a schema-aware function, plus the trigger added in `ProvisionTenantSchema` and in a migration for existing tenants. *Recommended:* build it, writing one row per save rather than one per field, so `audit_logs` stays within the 49.18 weight budget. It needs an OK because it adds audit rows to production. **Approved and built (Stage 47.16.4a, 2026-10-29); see C12.**
- **G2 - Ledger rows the database will not change.** *Built (47.16.4b).* The scale test runs only in a sandbox client. The three paths that re-dated rows (`journal_voucher.go`, `asset_depreciation.go`, and the offline sale in `pos_offline_sales.go`) now write the date on insert. The `gl_postings_guard` trigger refuses the rest; see C11.
- **G3 - An 8-year floor on audit retention.** Add a setting floor so `delete_after_days`, if it is ever acted on, cannot go below 2,922 days, and so an archive file is not deleted inside that window. *Recommended:* yes, as a 49.6 / 47.16.2 retention-matrix entry. **Approved and built (Stage 47.16.4c, 2026-10-29); see C14.**
- **G4 - Turnover-based applicability.** An IRP profile's `turnover_band` is only a label. Whether a GSTIN must e-invoice is decided by an administrator switching its profile on; the product does not calculate aggregate turnover. *Recommended:* keep it that way, and show a readiness warning when sales of the type the profile covers exceed ₹5 crore in a financial year while the profile is off. *Built 2026-10-29 (47.16.4d):* the setup path's tax step carries the warning check `tax-einvoice-turnover` (engines/setup_readiness.go) - posted sales invoices, before tax, B2B and B2C, per GSTIN (through each store's legal entity) and financial year, credit notes not deducted; never blocking. Aggregate turnover across the PAN's other GSTINs and the till's bills is not counted.
- **G5 - E-way bill value basis.** *Built (47.16.4e).* A line's `amount` already includes GST (sale prices include it). But a line with only `taxable` counted its pre-tax value, and a package bill's lines (`line_total`) counted nothing. Each line is now read as the e-invoice reads it, and tax is added to a taxable-only line. Decision rules are now `EWB-R138-2026.2`.
- **G6 - Raw IRP response and immutable acknowledgements.** *Built (47.16.4f).* See C18.
